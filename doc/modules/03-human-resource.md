# Module 3: Human Resource (จัดการพนักงาน + ผูกบัญชีผู้ใช้)

> Foundation Module ลำดับที่ 3 — เชื่อมโยงระหว่าง "คนที่ทำงาน" กับ "บัญชีที่ใช้ระบบ"

---

## 1. Module นี้คืออะไร

ระบบจัดการข้อมูลพนักงาน (HR) ของร้านอาหาร เก็บข้อมูลทุกอย่างที่ร้านควรรู้เกี่ยวกับพนักงาน ตั้งแต่ข้อมูลส่วนตัว ที่อยู่ ประวัติการศึกษา ประวัติการทำงาน รูปถ่าย และเชื่อมต่อกับบัญชีล็อกอินของระบบ POS

ทุกการกระทำในระบบ (สั่งอาหาร, ส่งครัว, ปิดบิล, ฯลฯ) จะถูกบันทึกว่า **พนักงานคนไหนเป็นผู้ทำ** (Audit Trail) — ข้อมูลพนักงานทั้งหมดอ้างมาจาก Module นี้

---

## 2. ช่วยธุรกิจร้านอาหารในเรื่องใด

| ปัญหาแบบดั้งเดิม | สิ่งที่ระบบนี้แก้ |
| --- | --- |
| ข้อมูลพนักงานเก็บในกระดาษ/Excel กระจัดกระจาย | ศูนย์กลางข้อมูลพนักงาน 1 ที่ ค้นหาได้ทันที |
| สร้างบัญชี Login ของพนักงานใช้เวลานาน (ต้องรู้รหัสผ่าน + ส่งให้) | สร้างบัญชีจากหน้าพนักงาน → ระบบส่งรหัสผ่านเริ่มต้นไปอีเมลพนักงานอัตโนมัติ |
| ไม่รู้ใครเป็นคนสั่งอาหาร / ใครเสิร์ฟผิด | ทุกการกระทำในระบบมี "ผู้ทำ" ติดไว้ — สอบสวนได้ |
| พนักงานพาร์ทไทม์ vs ฟูลไทม์ ไม่แยก ค่าจ้างคิดผิด | แยกประเภท Full Time (เงินเดือน) / Part Time (รายชั่วโมง) ในระบบ |
| สาขาหนึ่งพนักงานลาออก ไม่รู้ว่าใครรับงานต่อ | บันทึก StartDate / EndDate + EmploymentStatus ติดประวัติพนักงาน |
| ข้อมูลที่อยู่/การศึกษา/ประวัติทำงาน ต้องเขียนใส่ใบสมัครซ้ำๆ | บันทึก Sub-entities ครั้งเดียว เพิ่ม-แก้-ลบได้เรื่อยๆ |

**คุณค่าทางธุรกิจ**: ระบบ HR ขนาดเล็กในตัวเอง + Audit Trail ที่สมบูรณ์ + ลดข้อพิพาทเรื่องใครทำอะไร + รองรับการคิดค่าจ้างต่างประเภท

## 3. Business Logic หลัก

### 3.1 โครงสร้างข้อมูลพนักงาน

```
TbEmployee (พนักงานหลัก)
├── ข้อมูลส่วนตัว: คำนำหน้า, ชื่อ-นามสกุล ไทย/อังกฤษ, ชื่อเล่น, เพศ, วันเกิด, สัญชาติ, ศาสนา
├── ข้อมูลติดต่อ: เบอร์โทร, อีเมล, Line ID
├── เอกสาร: เลขบัตรประชาชน
├── ข้อมูลการจ้าง: ตำแหน่ง (FK→Position), วันเริ่มงาน (StartDate), วันสิ้นสุดการทำงาน (EndDate, nullable), IsActive (true=กำลังทำงาน / false=พ้นสภาพ)
├── ประเภทการจ้าง: IsFullTime (true=เงินเดือน, false=รายชั่วโมง)
│   ├── ถ้า FullTime: Salary (เงินเดือน/เดือน)
│   └── ถ้า PartTime: HourlyRate (ค่าจ้าง/ชั่วโมง)
├── ข้อมูลธนาคาร: ชื่อบัญชี, เลขบัญชี, ธนาคาร (สำหรับโอนเงินเดือน)
├── รูปโปรไฟล์: ImageFileId (FK→TbFile)
├── ลิงก์ User Account: UserId (FK→TbUser) — nullable
│
├── ที่อยู่: TbEmployeeAddress (1:M)
│   ├── ประเภท: House (บ้าน) / Office (ทำงาน) / Other
│   └── รายละเอียด: บ้านเลขที่, หมู่, ซอย, ถนน, ตำบล, อำเภอ, จังหวัด, รหัสไปรษณีย์
│
├── การศึกษา: TbEmployeeEducation (1:M)
│   └── ระดับการศึกษา, สาขา, สถาบัน, ปีจบ, เกรดเฉลี่ย
│
└── ประวัติการทำงานเดิม: TbEmployeeWorkHistory (1:M)
    └── สถานที่ทำงาน, ตำแหน่ง, วันเริ่ม-สิ้นสุด
```

### 3.2 กฎสำคัญ

1. **เลขบัตรประชาชนและอีเมลห้ามซ้ำ** — ระบบเช็คก่อนสร้าง/แก้ไข
2. **พนักงาน 1 คนผูกได้ 1 ตำแหน่ง** — ตำแหน่งใหม่ = สิทธิ์ใหม่ทันที (ผ่าน Authorization)
3. **บัญชี User Account สร้างได้ทีหลัง** — พนักงานในระบบไม่จำเป็นต้องมีบัญชีล็อกอินทุกคน (เช่น พนักงานบางคนใช้แค่ Self-Order)
4. **เมื่อสร้าง User Account จาก Employee:**
   - ระบุ Username (ฝ่ายบุคคลกรอกเอง — แนะนำให้ใช้ Employee ID หรือชื่อย่อ)
   - ระบบสร้างรหัสผ่านสุ่ม + ส่งไปอีเมลพนักงาน
   - บันทึก `LastPasswordChangedDate` ตอนสร้าง — แนะนำให้พนักงานเปลี่ยนรหัสผ่านเองในการเข้าใช้ครั้งแรก (ระบบไม่ได้บังคับ)
5. **ลบพนักงาน** ใช้ Soft Delete (DeleteFlag = true) — ข้อมูลยังอยู่เพื่อ Audit แต่ไม่แสดงในรายการ
6. **Sub-entities (Address/Education/WorkHistory)** เพิ่ม-แก้-ลบได้อิสระ ไม่กระทบข้อมูลพนักงานหลัก
7. **รูปโปรไฟล์** ลบของเก่าออกจาก S3 อัตโนมัติเมื่ออัพโหลดใหม่ (กันไฟล์ค้าง)

### 3.3 สถานะของพนักงาน

ระบบใช้ฟิลด์ `IsActive` (boolean) ใน `TbEmployee` ร่วมกับ `EndDate` เพื่อสะท้อนสถานะ:

| ค่า IsActive | EndDate | ความหมาย | สิทธิ์เข้าระบบ |
| :---: | :---: | --- | :---: |
| `true` | NULL | กำลังทำงาน | เข้าได้ (ถ้ามี User Account + `TbUser.IsActive = true`) |
| `false` | กำหนดวันที่ | พ้นสภาพ (ลาออก/เลิกจ้าง) | เข้าไม่ได้ — ต้องปิดบัญชี User แยกผ่าน User Management |

> **หมายเหตุ**: ระบบไม่ได้แยกประเภท "ลาออก / เลิกจ้าง / พักงาน" ที่ระดับ Employee — ใช้แค่ `IsActive` + `EndDate` หากต้องการแยกประเภทต้องบันทึกในช่องหมายเหตุ (Note) เอง

## 4. Workflow การทำงานจริง

### Workflow A — รับพนักงานใหม่เข้าทำงาน

```
1. ฝ่ายบุคคล → /human-resource/employees → กด "เพิ่มพนักงาน"
2. กรอกข้อมูลพื้นฐาน:
   ─ คำนำหน้า + ชื่อไทย/อังกฤษ + ชื่อเล่น + เพศ + วันเกิด
   ─ เบอร์โทร + อีเมล + เลขบัตรประชาชน
   ─ ตำแหน่ง (เช่น "พนักงานเสิร์ฟ")
   ─ ประเภทการจ้าง: Part Time + ค่าจ้าง 60 บาท/ชั่วโมง
   ─ วันเริ่มงาน: 1 มิ.ย. 2569
3. อัพโหลดรูปโปรไฟล์ (เก็บใน S3 ผ่าน File Module)
4. (ไม่บังคับ) เพิ่มที่อยู่ → "บ้าน" + รายละเอียดที่อยู่
5. (ไม่บังคับ) เพิ่มประวัติการศึกษา → "ปริญญาตรี" + สถาบัน + ปีจบ
6. (ไม่บังคับ) เพิ่มประวัติงานเดิม → "ร้านอาหาร XX" + วันเริ่ม-สิ้นสุด
7. กดบันทึก → ระบบเช็คเลขบัตรประชาชน + อีเมล ห้ามซ้ำ
8. พนักงานถูกบันทึก แต่ยังไม่มีบัญชี Login
```

### Workflow B — สร้างบัญชี Login ให้พนักงาน

```
1. หน้ารายการพนักงาน → เลือกพนักงานที่ต้องการ → กด "สร้างบัญชี"
2. ระบบขอ Username (default = ใช้ EmployeeId หรือชื่อย่อ)
3. กดสร้าง → ระบบ:
   ─ สร้างรหัสผ่านสุ่ม (Hash ด้วย BCrypt)
   ─ บันทึก TbUser ผูกกับ TbEmployee (Employee.UserId = User.UserId)
   ─ บันทึก LastPasswordChangedDate ตอนสร้าง
   ─ ส่งอีเมลแจ้ง Username + รหัสผ่านเริ่มต้น
4. พนักงานเข้าอีเมล → กดลิงก์ไปหน้า Login → ใช้รหัสที่ได้
5. แนะนำพนักงานเปลี่ยนรหัสผ่านเองที่หน้า Profile (ระบบไม่บังคับ แต่มี Password History ป้องกันรหัสซ้ำ 3 ครั้งล่าสุด)
```

### Workflow C — พนักงานดูและแก้ไขโปรไฟล์ตัวเอง

```
1. พนักงานล็อกอิน → /profile (ทุกพนักงานเข้าได้ ไม่ต้องมี permission พิเศษ)
2. เห็นข้อมูลตัวเอง:
   ─ รูปโปรไฟล์ + ชื่อ + ตำแหน่ง
   ─ ข้อมูลส่วนตัวทั้งหมด
   ─ ที่อยู่ / การศึกษา / ประวัติงาน
3. แก้ไขข้อมูลส่วนตัว (ชื่อเล่น, เบอร์โทร, อีเมล ฯลฯ) ได้
4. เปลี่ยนรูปโปรไฟล์ → ระบบลบรูปเก่าออกจาก S3 → อัพโหลดใหม่
5. ตั้ง/เปลี่ยน PIN Code 6 หลัก (สำหรับงานเฉพาะ)
6. เปลี่ยนรหัสผ่าน (ต้องยืนยันรหัสเดิม)
```

### Workflow D — พนักงานลาออก

```
1. ฝ่ายบุคคล → /human-resource/employees → เลือกพนักงาน → กดแก้ไข
2. เอาติ๊ก "เปิดใช้งาน" ออก (IsActive = false)
3. กรอก "วันที่สิ้นสุดการทำงาน" (EndDate)
4. บันทึก → ข้อมูลพนักงานเก็บไว้สำหรับ audit แต่พนักงานหายจากรายการ Active
5. (ขั้นตอนแยก) ฝ่ายบุคคล → /admin-setting/users → เลือกผู้ใช้ → ปิดบัญชี (TbUser.IsActive = false)
   ─ พนักงานล็อกอินไม่ได้อีก (audit log ยังคงอ้างถึงพนักงานคนนี้)
```

> **หมายเหตุ**: การปิดบัญชีพนักงาน ≠ ปิดบัญชี User โดยอัตโนมัติ — ฝ่ายบุคคลต้องดำเนินการปิดบัญชี User เพิ่มเองที่หน้า User Management

### Workflow E — แก้ไข Sub-entities (ที่อยู่ / การศึกษา / ประวัติงาน)

```
1. เข้าหน้าแก้ไขพนักงาน → เลื่อนไปที่แท็บ "ที่อยู่" (หรือการศึกษา / ประวัติงาน)
2. กด "เพิ่มที่อยู่" → Dialog เปิดขึ้น
3. เลือกประเภท (บ้าน / ทำงาน / อื่นๆ) + กรอกรายละเอียด
4. บันทึก → ระบบบันทึกเป็น record ใหม่ใน TbEmployeeAddress
5. แก้ไข/ลบที่อยู่ → ทำในรายการได้ทันที (ไม่กระทบข้อมูลพนักงานหลัก)
```

## 5. ข้อดี

| ข้อดี | คำอธิบาย |
| --- | --- |
| **ฐานข้อมูล HR ในระบบเดียว** | ไม่ต้องใช้ Excel แยก — ทุกข้อมูลพนักงานพร้อมใช้ |
| **ผูก User Account ทีหลังได้** | พนักงานบางคนไม่จำเป็นต้องล็อกอิน (เช่น พ่อครัวที่ดูจาก KDS ของหัวหน้าก็พอ) |
| **สร้างบัญชีล็อกอินอัตโนมัติ** | ฝ่ายบุคคลกรอกแค่ Username — ระบบสุ่มรหัสผ่านแล้วส่งอีเมล + Hash ด้วย BCrypt |
| **Audit Trail สมบูรณ์** | ทุก transaction ในระบบมี CreatedBy + UpdatedBy ติด — ตรวจสอบใครทำได้ |
| **แยก Full Time / Part Time** | คิดค่าจ้างได้ถูกต้อง ตามประเภทการจ้าง |
| **Sub-entities ยืดหยุ่น** | ที่อยู่ของพนักงานมีได้หลายที่ (บ้าน + ทำงาน + ฯลฯ) — เพิ่มได้ไม่จำกัด |
| **Soft Delete** | ลบพนักงาน → ข้อมูล audit ยังอยู่ (ไม่ orphan reference) |
| **รูปโปรไฟล์ S3** | ไม่กิน disk ของเซิร์ฟเวอร์ + scale ได้ |
| **เช็คเลขบัตร/อีเมลซ้ำ** | กันการใส่ข้อมูลพนักงานซ้ำคน |

## 6. ข้อเสีย / ข้อจำกัด

| ข้อจำกัด | ผลกระทบ + วิธีรับมือ |
| --- | --- |
| **ไม่มีระบบลงเวลาทำงาน (Time Attendance)** | ระบบไม่บันทึกว่าพนักงานเข้า-ออกเมื่อไหร่ — ต้องใช้ระบบ HR แยก |
| **ไม่มีคำนวณเงินเดือนอัตโนมัติ** | บันทึก Salary/HourlyRate ไว้ แต่ระบบไม่คิดเงินเดือนให้ — ต้องใช้ระบบบัญชีแยก |
| **ไม่มีหน้าจอจัดการ User โดยตรง (สร้างบัญชีเปล่าๆ ไม่ได้)** | User ต้องผูกกับ Employee เสมอ — หากต้องการ "admin" ที่ไม่ใช่พนักงานจริง ต้องสร้าง Employee dummy |
| **ลบ Sub-entity ไม่ได้ Restore** | ที่อยู่/การศึกษา/ประวัติงานที่ลบไปแล้ว ไม่มี Trash — ต้องสร้างใหม่ |
| **อีเมลพนักงานสำคัญ** | ระบบส่งรหัสผ่านเริ่มต้น + Forgot Password ผ่านอีเมล — ถ้าไม่มีอีเมลจริง ใช้งานไม่ได้ |
| **ไม่มีบันทึกการลาป่วย/พักร้อน** | ระบบมีแค่ IsActive + EndDate — ไม่รองรับ Vacation tracking |
| **ปิดสถานะพนักงาน ≠ ปิดบัญชี User อัตโนมัติ** | เปลี่ยน IsActive = false ของ Employee → User ยังเข้าระบบได้อยู่ ต้องปิดบัญชี User เพิ่มที่หน้า User Management |
| **ไม่บังคับเปลี่ยนรหัสผ่านครั้งแรก** | พนักงานใหม่ใช้รหัสเริ่มต้นตลอดได้ — แนะนำให้พนักงานเปลี่ยนเอง |
| **ไม่แยกประเภทการพ้นสภาพ** | ลาออก/เลิกจ้าง/พักงาน — ไม่มี enum แยก ต้องบันทึกในช่องหมายเหตุเอง |
| **รูปโปรไฟล์ขนาดใหญ่ทำให้ Mobile Web ช้า** | ไม่มีการ resize อัตโนมัติ — แนะนำให้พนักงานอัพโหลดรูปขนาดเหมาะสม |

## 7. ความสัมพันธ์กับ Module อื่น

### Module นี้ส่งข้อมูลไปให้ใคร

| Module ปลายทาง | ส่งอะไรไป | ใช้ทำอะไร |
| --- | --- | --- |
| **ทุก Module** | EmployeeId (CreatedBy / UpdatedBy) | บันทึก Audit Trail ของทุก transaction |
| **Admin (Auth)** | EmployeeId + PositionId | ใส่ใน JWT Token หลังล็อกอินสำเร็จ |
| **Authorization** | PositionId ของพนักงาน | หาว่ามีสิทธิ์อะไรบ้าง |
| **Order** | EmployeeId + ชื่อพนักงาน | บันทึก OrderedBy + CancelledBy ใน OrderItem |
| **Payment** | EmployeeId | บันทึก ReceivedByEmployeeId ใน Payment |
| **Cashier Session** | EmployeeId (ผู้เปิด/ปิดกะ) | ผูกกะกับพนักงาน |
| **Notification** | UserId | ส่ง Notification ไปคนที่เกี่ยวข้อง |

| Module ต้นทาง | ดึงอะไรมา | ใช้ทำอะไร |
| --- | --- | --- |

## 8. สรุปสำหรับรายงาน (1 ย่อหน้า)

> Module Human Resource เป็นระบบจัดการข้อมูลพนักงานของร้านอาหารที่เก็บข้อมูลครบครันตั้งแต่ข้อมูลส่วนตัว ที่อยู่ ประวัติการศึกษา ประวัติการทำงาน รูปโปรไฟล์ และข้อมูลการจ้างงานที่รองรับทั้งพนักงานประจำ (Full Time) และพาร์ทไทม์ (Part Time) ฟีเจอร์สำคัญคือการเชื่อมโยงข้อมูลพนักงานกับบัญชีล็อกอินของระบบ POS แบบ 1:1 (TbEmployee ↔ TbUser) ทำให้สามารถสร้างบัญชีล็อกอินอัตโนมัติพร้อมส่งรหัสผ่านเริ่มต้นไปอีเมลพนักงานได้ในคลิกเดียว และที่สำคัญที่สุดคือทุกการกระทำในระบบ (สั่งอาหาร, ชำระเงิน, แก้ไขข้อมูล) จะถูกบันทึกว่าพนักงานคนใดเป็นผู้ทำ (Audit Trail) ทำให้เจ้าของร้านสามารถตรวจสอบและจัดการความรับผิดชอบของพนักงานได้อย่างชัดเจน
