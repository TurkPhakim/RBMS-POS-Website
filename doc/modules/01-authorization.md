# Module 1: Authorization (ระบบสิทธิ์ตามตำแหน่งงาน)

> Foundation Module — ทุกระบบในร้านต้องผ่านการตรวจสิทธิ์จาก Module นี้

---

## 1. Module นี้คืออะไร

ระบบกำหนด "สิทธิ์การเข้าถึง" ของพนักงานแต่ละคนตาม **ตำแหน่งงาน** (Position) — แทนที่จะกำหนดสิทธิ์ให้รายบุคคลทีละคน ระบบจะกำหนดสิทธิ์ให้ "ตำแหน่ง" แล้วผูกพนักงานเข้ากับตำแหน่งนั้น (Role-Based Access Control — RBAC)

ตัวอย่าง: ตำแหน่ง "พนักงานครัว" → ดูออเดอร์ในครัวได้ + อัพเดตสถานะอาหารได้ + **ห้าม** เข้าถึงข้อมูลยอดขายหรือพนักงานคนอื่น

---

## 2. ช่วยธุรกิจร้านอาหารในเรื่องใด

| ปัญหาแบบดั้งเดิม | สิ่งที่ระบบนี้แก้ |
| --- | --- |
| เจ้าของร้านต้องคอยควบคุมว่าพนักงานเข้าถึงข้อมูลอะไรได้บ้าง โดยใช้คน | ระบบบังคับสิทธิ์อัตโนมัติ ไม่ต้องพึ่งความซื่อสัตย์ของพนักงาน |
| เปลี่ยนพนักงาน ต้องจำว่าใครเข้าถึงอะไรได้ | กำหนดสิทธิ์ที่ "ตำแหน่ง" ครั้งเดียว → พนักงานคนใหม่รับสิทธิ์ตามตำแหน่งทันที |
| พนักงานครัวเปิดดูยอดขายได้ ทำให้ข้อมูลรั่วไหล | แต่ละตำแหน่งเห็นเฉพาะส่วนที่จำเป็นต่องาน |
| ปลดพนักงานออก แต่ลืมปิดสิทธิ์ → เสี่ยงข้อมูลรั่ว | ปิดบัญชี/ล็อคบัญชีจุดเดียว ตัดสิทธิ์ทั้งหมดทันที |

**คุณค่าทางธุรกิจ**: ลดความเสี่ยงด้านความปลอดภัยของข้อมูล + ลดภาระการจัดการสิทธิ์เมื่อพนักงานเข้า-ออก + ป้องกันการทุจริต (พนักงานเสิร์ฟแก้บิลเองไม่ได้, พนักงานครัวลบรายงานยอดขายไม่ได้)

## 3. Business Logic หลัก

### โครงสร้าง 3 ระดับ

```
ตำแหน่งงาน (Position)        เช่น "ผู้จัดการ", "พนักงานครัว", "แคชเชียร์"
       │
       │ ผูกหลายต่อหลาย กับ
       ▼
Permission Matrix             เช่น "menu-food.read", "order-manage.create"
   (โมดูล × การกระทำ)
       │
       └── โมดูล (Module) เช่น เมนูอาหาร, ออเดอร์, แดชบอร์ด
       └── การกระทำ (Permission) เช่น อ่าน, สร้าง, แก้ไข, ลบ
```

### กฎสำคัญ

1. **พนักงานทุกคนต้องผูกกับตำแหน่ง 1 ตำแหน่ง** — เพื่อให้ระบบรู้ว่าทำอะไรได้บ้าง
2. **เมื่อสร้างตำแหน่งใหม่** ระบบให้สิทธิ์ทั้งหมด (Grant All) เป็นค่าเริ่มต้น — เจ้าของร้านค่อยตัดสิทธิ์ที่ไม่ต้องการออก
3. **ลบตำแหน่งได้เฉพาะตำแหน่งที่ไม่มีพนักงานผูกอยู่** — ป้องกันพนักงานหลุดจากระบบสิทธิ์
4. **ชื่อตำแหน่งห้ามซ้ำ** — ป้องกันความสับสนตอนกำหนดสิทธิ์
5. **ข้อมูลสิทธิ์ถูก cache 10 นาที** ในระบบ + cache ภายในการเรียกแต่ละครั้ง — เพื่อความเร็วในการตรวจสอบ (ไม่ต้องค้นฐานข้อมูลทุกครั้งที่กดปุ่ม)
6. **เมื่อแก้สิทธิ์ของตำแหน่ง** ระบบล้าง cache ของตำแหน่งนั้นทันที — สิทธิ์ใหม่มีผลทันทีไม่ต้อง logout

### ระดับการกระทำ (Permission Types)

| สิทธิ์ | ความหมาย | ตัวอย่าง |
| :---: | --- | --- |
| `read` | อ่าน / ดู | ดูรายการเมนู, ดูยอดขาย |
| `create` | สร้างใหม่ | เพิ่มเมนู, สร้างออเดอร์ |
| `update` | แก้ไข | แก้ราคาเมนู, อัพเดตสถานะอาหาร |
| `delete` | ลบ | ลบเมนู, ลบโต๊ะ |

## 4. Workflow การทำงานจริง

### Flow ที่ 1 — เจ้าของร้านตั้งค่าตำแหน่งใหม่ "พนักงานเสิร์ฟ"

```
1. เจ้าของร้าน → เข้าเมนู "ตำแหน่งงาน" → กด "เพิ่มตำแหน่ง"
2. กรอกชื่อ "พนักงานเสิร์ฟ" + คำอธิบาย → บันทึก
3. ระบบสร้างตำแหน่งพร้อม "สิทธิ์ทั้งหมด" เป็นค่าเริ่มต้น
4. เจ้าของร้าน → เข้าหน้า "กำหนดสิทธิ์" ของตำแหน่งนั้น
5. ตัดสิทธิ์ที่ไม่ต้องการออก เช่น:
   ☐ ดูยอดขาย  ☐ จัดการเมนู  ☐ จัดการพนักงาน
   ☑ ดูออเดอร์  ☑ สั่งอาหารแทนลูกค้า  ☑ เสิร์ฟอาหาร
6. กดบันทึก → ระบบล้าง cache → สิทธิ์ใหม่มีผลทันที
```

### Flow ที่ 2 — พนักงานเสิร์ฟล็อกอินและใช้งาน

```
1. พนักงานล็อกอินด้วย Username/Password
2. ระบบดึงตำแหน่งของพนักงาน → ดึงรายการสิทธิ์ของตำแหน่งนั้น
3. ระบบส่ง "Token + รายการสิทธิ์" กลับให้ Frontend
4. Frontend ใช้รายการสิทธิ์เพื่อ:
   - แสดงเมนูใน Sidebar เฉพาะที่มีสิทธิ์เข้า
   - ซ่อน/แสดงปุ่ม (เช่น ปุ่ม "ลบ" แสดงเฉพาะคนที่มีสิทธิ์ลบ)
5. ทุกครั้งที่พนักงานกดปุ่มทำงาน → Backend ตรวจสิทธิ์อีกครั้งก่อนทำ
   (ป้องกันการโจมตีผ่าน API ตรงๆ)
```

### Flow ที่ 3 — พนักงานเปลี่ยนตำแหน่ง (เลื่อนเป็นผู้จัดการกะ)

```
1. ฝ่ายบุคคล → หน้าจัดการพนักงาน → เลือกพนักงาน → เปลี่ยน "ตำแหน่ง"
2. ระบบบันทึกการเปลี่ยน + ล้าง cache ของพนักงานคนนั้น
3. ครั้งถัดไปที่พนักงาน refresh หน้าจอ → เห็นเมนูใหม่ตามตำแหน่งใหม่ทันที
   (ไม่ต้อง logout/login ใหม่)
```

## 5. ข้อดี

| ข้อดี | คำอธิบาย |
| --- | --- |
| **กำหนดครั้งเดียว ใช้ตลอด** | ตั้งค่าสิทธิ์ที่ตำแหน่ง พนักงานใหม่รับสิทธิ์ทันทีโดยไม่ต้องตั้งใหม่ |
| **ปลอดภัยตามมาตรฐาน** | ใช้แนวคิด RBAC ซึ่งเป็นมาตรฐานในระบบองค์กรขนาดใหญ่ |
| **ตรวจสิทธิ์ 2 ชั้น** | ทั้ง Frontend (ซ่อนปุ่ม) และ Backend (ปฏิเสธ API) — แม้พนักงานพยายาม bypass หน้าจอก็ทำไม่ได้ |
| **ปรับสิทธิ์เรียลไทม์** | แก้สิทธิ์ปุ๊บ มีผลปั๊บ ไม่ต้องให้พนักงาน logout |
| **เร็ว — ไม่กระทบประสิทธิภาพ** | ใช้ Cache 2 ชั้น (memory + request-scope) ไม่ต้อง query DB ทุกครั้งที่ตรวจสิทธิ์ |
| **ปรับขนาดได้ตามร้าน** | ร้านเล็กใช้แค่ 2-3 ตำแหน่ง, ร้านใหญ่กำหนดได้หลายตำแหน่ง (เชฟ, ผู้ช่วยเชฟ, บาร์เทนเดอร์, ฯลฯ) |

## 6. ข้อเสีย / ข้อจำกัด

| ข้อจำกัด | ผลกระทบ + วิธีรับมือ |
| --- | --- |
| **กำหนดสิทธิ์ระดับ "การกระทำ" ไม่ใช่ระดับข้อมูล** | เช่น พนักงานครัวเห็นออเดอร์ "ทั้งร้าน" ไม่สามารถจำกัดให้เห็นเฉพาะออเดอร์โซน A ได้ — ต้องแก้ในระดับ Logic หากต้องการ |
| **พนักงานคนเดียวมีได้แค่ 1 ตำแหน่ง** | กรณีพนักงานทำหลายหน้าที่ (เช่น แคชเชียร์ + เสิร์ฟ) ต้องสร้างตำแหน่งใหม่ที่รวมสิทธิ์ทั้งสอง |
| **Cache 10 นาที** | ในบางกรณี (เช่น ทดสอบ) หากแก้สิทธิ์ที่ DB โดยตรง ต้องรอ cache หมดอายุ หรือ restart ระบบ |
| **ไม่มีการบันทึก audit log การเปลี่ยนสิทธิ์** | หากต้องสอบสวนว่าสิทธิ์ถูกเปลี่ยนเมื่อไหร่ ใครเปลี่ยน — ต้องดูจาก audit fields ของ AuthorizeMatrixPosition |
| **ตั้งสิทธิ์ครั้งแรกใช้เวลา** | ร้านที่เพิ่งเปิด ต้องวางแผนโครงสร้างตำแหน่งให้ดีก่อน — หากเปลี่ยนภายหลังต้องไล่แก้ทุกตำแหน่ง |

## 7. ความสัมพันธ์กับ Module อื่น

### Module นี้ส่งข้อมูลไปให้ใคร

| Module ปลายทาง | ส่งอะไรไป | ใช้ทำอะไร |
| --- | --- | --- |
| **ทุก Module** | รายการสิทธิ์ของพนักงาน | ตรวจก่อนอนุญาตให้ทำการกระทำใดๆ |
| **Human Resource** | รายการตำแหน่งงาน | ใช้ใน Dropdown ตอนสร้าง/แก้ไขพนักงาน |
| **Notification** | สิทธิ์ของผู้ใช้ปัจจุบัน | ใช้จัดกลุ่ม SignalR (Kitchen / Floor / Cashier / Manager) เพื่อส่งแจ้งเตือนถูกกลุ่ม |
| **Admin (Sidebar)** | รายการสิทธิ์ | ใช้ซ่อน/แสดงเมนูใน Sidebar ของผู้ใช้แต่ละคน |

### Module นี้ดึงข้อมูลจากใคร

| Module ต้นทาง | ดึงอะไรมา | ใช้ทำอะไร |
| --- | --- | --- |
| **Human Resource** | EmployeeId + PositionId ของพนักงาน | ใช้หาว่าพนักงานคนนี้อยู่ตำแหน่งอะไร → มีสิทธิ์อะไรบ้าง |
| **Admin (Auth)** | UserId จาก JWT Token | ใช้หาพนักงานที่ล็อกอินอยู่ |

## 8. สรุปสำหรับรายงาน (1 ย่อหน้า)

> Module Authorization เป็นรากฐานของระบบความปลอดภัยใน RBMS-POS โดยใช้แนวคิด Role-Based Access Control (RBAC) ที่กำหนดสิทธิ์การเข้าถึงผ่าน "ตำแหน่งงาน" แทนการกำหนดรายบุคคล ทำให้การจัดการสิทธิ์ของพนักงานเป็นเรื่องง่ายเมื่อมีการเข้า-ออกของพนักงานบ่อย ระบบบังคับการตรวจสอบสิทธิ์ทั้งฝั่งหน้าจอ (Frontend) และเซิร์ฟเวอร์ (Backend) ครอบคลุมการกระทำหลัก 4 ประเภท (อ่าน/สร้าง/แก้ไข/ลบ) ทุกโมดูล โดยมีระบบ Cache 2 ชั้นเพื่อรักษาประสิทธิภาพในการตรวจสอบสิทธิ์ที่เกิดขึ้นทุกครั้งที่พนักงานใช้งานระบบ
