## 3. รูปแบบการเขียน + ตัวอย่างจริง

### 3.1 หัวข้อ 3.1 สถาปัตยกรรมระบบ (System Architecture) ⭐

#### 🎯 ตัวอย่างที่ 2 — Pattern: รูป Diagram + คำอธิบายเป็นลำดับ Flow
> "3.1 สถาปัตยกรรมระบบ (System Architecture)
>
> [รูปที่ 3.1 สถาปัตยกรรมระบบของการพัฒนาเว็บแอปพลิเคชันร้านค้าออนไลน์สำหรับอุปกรณ์ไอที]
>
> แผนภาพสถาปัตยกรรมระบบแสดงความสัมพันธ์และการทำงานร่วมกันของเทคโนโลยีต่างๆ ที่ใช้ในการพัฒนาเว็บไซต์ โดยมีลำดับขั้นตอนและการทำงานดังนี้:
>
> 1. กลุ่มผู้ใช้งาน (Users) ประกอบด้วย 2 กลุ่มหลัก คือ ลูกค้า (Customer) และผู้ดูแลระบบ (Admin) ซึ่งเป็นจุดเริ่มต้นของการใช้งานระบบ
>
> 2. ส่วนแสดงผล (Frontend) เป็นส่วนที่ผู้ใช้งานจะโต้ตอบกับระบบผ่าน Web Browser โดยใช้เทคโนโลยีหน้าบ้าน ได้แก่ HTML, CSS และ JS ซึ่งทำหน้าที่รับคำสั่งจากผู้ใช้และแสดงผลลัพธ์
>
> 3. เว็บเซิร์ฟเวอร์ (Web Server) ในส่วนนี้เบราว์เซอร์จะส่งคำขอ (HTTP Request) มายัง Apache HTTP Server ซึ่งทำหน้าที่เป็นตัวกลางในการรับ-ส่งข้อมูลระหว่างผู้ใช้กับระบบหลังบ้าน โดยมีการสื่อสารแบบสองทาง (ไป-กลับ)
>
> 4. ส่วนประมวลผล (Backend) ในส่วนนี้เซิร์ฟเวอร์ Apache จะส่งต่อคำสั่งมาให้ PHP Engine ทำหน้าที่ประมวลผลตรรกะทางธุรกิจ (Business Logic) ของแอปพลิเคชันทั้งหมด
>
> 5. ฐานข้อมูล (Database) ระหว่างการประมวลผล PHP Engine จะมีการเชื่อมต่อแบบสองทางกับ MySQL Database เพื่อดึงข้อมูลมาแสดงผล หรือนำข้อมูลใหม่ไปบันทึกจัดเก็บ (เช่น ข้อมูลสินค้า, ตะกร้าสินค้า, ประวัติการสั่งซื้อ)
>
> 6. การเชื่อมต่อบริการภายนอก (External API) ในส่วนของ PHP Engine ยังมีการส่งข้อมูลออกไปยังบริการภายนอก 2 ระบบหลัก คือ Omise Payment Gateway ใช้สำหรับประมวลผลและจัดการธุรกรรมการชำระเงิน และ Email ใช้สำหรับระบบส่งอีเมลแจ้งเตือน"

**สังเกต Pattern (สำคัญมาก)**:
- **รูปขึ้นก่อน** + ตามด้วยคำอธิบายเป็น **Numbered list** (1. 2. 3. ...)
- ลำดับการอธิบาย: **User → Frontend → Web Server → Backend → Database → External API**
- ขึ้นต้นแต่ละข้อด้วย **"ชื่อชั้น (English Name)"** + คำอธิบายเชื่อมโยงกับ layer ก่อนหน้า
- ระบุ "ตัวกลาง" / "สื่อสารแบบสองทาง (ไป-กลับ)" ชัดเจน

#### Pattern แนะนำสำหรับ RBMS-POS — 3.1 System Architecture

```markdown
3.1 สถาปัตยกรรมระบบ (System Architecture)

[รูปที่ 3.1 สถาปัตยกรรมระบบของระบบบริหารจัดการร้านอาหาร RBMS-POS]

แผนภาพสถาปัตยกรรมระบบแสดงความสัมพันธ์และการทำงานร่วมกันของเทคโนโลยีต่างๆ
ที่ใช้ในการพัฒนาระบบ โดยมีการแบ่งสถาปัตยกรรมแบบ N-Tier ออกเป็น 5 ชั้น ดังนี้:

1. กลุ่มผู้ใช้งาน (Users) ประกอบด้วย 5 กลุ่มหลัก ได้แก่ เจ้าของร้าน/ผู้จัดการ
   แคชเชียร์ พนักงานครัว พนักงานเสริฟ และลูกค้าที่ใช้ระบบ Self-Order

2. ส่วนแสดงผล (Frontend) แบ่งออกเป็น 2 แอปพลิเคชัน ได้แก่ Frontend Client
   (สำหรับ Desktop) และ Mobile Web (สำหรับ Customer Self-Order) ทั้งสอง
   พัฒนาด้วย Angular 19.1 + PrimeNG + Tailwind CSS

3. ชั้นเชื่อมต่อ (API Gateway) ระบบใช้ ASP.NET Core 9.0 เป็นชั้น Web API
   โดยมี Nginx Reverse Proxy ทำหน้าที่กระจาย Request ระหว่าง HTTP API
   และ WebSocket (SignalR)

4. ส่วนประมวลผล (Backend) ในส่วนนี้ Web API จะส่งต่อคำสั่งมาให้ชั้นบริการ
   (Business Layer) ซึ่งประกอบด้วย 8 Business Modules และชั้นเก็บข้อมูล
   (Repository Layer) ที่จัดการการเชื่อมต่อกับฐานข้อมูลผ่าน Entity Framework
   Core 9 (ORM)

5. การสื่อสารแบบเวลาจริง (Real-time Layer) ระบบใช้ SignalR 2 Hubs ได้แก่
   OrderHub (สำหรับการ broadcast ข้อมูล Order ไปยังครัวและหน้าร้าน) และ
   NotificationHub (สำหรับการแจ้งเตือนแก่กลุ่มผู้ใช้งานตามบทบาท)

6. ฐานข้อมูลและการจัดเก็บไฟล์ (Database & Storage) ระบบใช้ SQL Server 2022
   เป็นฐานข้อมูลเชิงสัมพันธ์ และใช้ MinIO (S3-compatible Object Storage)
   สำหรับจัดเก็บไฟล์รูปเมนู สลิปโอน และรูปพนักงาน

7. การเชื่อมต่อบริการภายนอก (External Services) ระบบเชื่อมต่อกับบริการ
   ภายนอกสำหรับ OCR Slip Verification ผ่าน API Provider ภายนอก
```

### 3.2 หัวข้อ 3.2 Use Case Diagram ⭐

#### 🎯 ตัวอย่างที่ 2 — Pattern: รูป Use Case + แยก Actor ระบุ Use Case
> "3.2 แผนภาพกรณีการใช้งาน (Use Case Diagram)
>
> [รูปที่ 3.2 แผนภาพกรณีการใช้งาน (Use Case Diagram)]
>
> การวิเคราะห์ความต้องการของผู้ใช้งานในระบบจัดจำหน่ายอุปกรณ์ไอทีออนไลน์ สามารถแบ่งผู้ใช้งาน (Actor) ออกเป็น 2 กลุ่มหลัก ได้แก่ ลูกค้า (Customer) และผู้ดูแลระบบ (Admin) โดยแต่ละกลุ่มมีสิทธิและขอบเขตการใช้งานระบบ (Use Case) ดังรายละเอียดต่อไปนี้
>
> 1. ผู้ใช้งานทั่วไป / ลูกค้า (Customer) เป็นกลุ่มผู้ใช้งานที่เข้ามาในระบบเพื่อเลือกซื้อสินค้า โดยมีฟังก์ชันการทำงานที่สามารถเข้าถึงได้ ดังนี้:
>    1.1. สมัครสมาชิกและเข้าสู่ระบบ ขั้นตอนนี้ลูกค้าสามารถลงทะเบียนสร้างบัญชีผู้ใช้ใหม่ หรือเข้าสู่ระบบด้วยบัญชีเดิมเพื่อเข้าถึงฟังก์ชันต่างๆ
>    1.2. จัดการโปรไฟล์และที่อยู่จัดส่ง ลูกค้าสามารถแก้ไขข้อมูลส่วนตัว...
>    1.3. ค้นหาและดูรายละเอียดสินค้า...
>    1.4. จัดการตะกร้าสินค้า...
>    1.5. สั่งซื้อสินค้าและชำระเงิน...
>    1.6. ติดตามสถานะคำสั่งซื้อ...
>    1.7. การรีวิวสินค้า...
>
> 2. ผู้ดูแลระบบ (Admin) เป็นกลุ่มผู้ใช้งานที่มีสิทธิในการบริหารจัดการข้อมูลหลังบ้าน เพื่อให้ระบบสามารถดำเนินไปได้อย่างสมบูรณ์ โดยมีฟังก์ชันการทำงาน ดังนี้:
>    2.1. เข้าสู่ระบบ...
>    2.2. จัดการข้อมูลสินค้าคงคลัง...
>    2.3. จัดการสถานะคำสั่งซื้อ...
>    2.4. ตรวจสอบและอนุมัติสลิปโอนเงิน...
>    2.5. จัดการเนื้อหา ข่าวสาร และแบนเนอร์..."

**สังเกต Pattern (สำคัญมาก)**:
- **รูปขึ้นก่อน** Use Case Diagram ที่แสดง Actor + Use Case + ความสัมพันธ์
- คำอธิบายแบ่ง **Actor (1., 2., ...)** แล้วใต้แต่ละ Actor มี **Use Case (1.1, 1.2, ...)**
- แต่ละ Use Case เขียน "{ชื่อ Use Case} ขั้นตอนนี้/ผู้ใช้สามารถ {กระทำ}" — 1-2 บรรทัด
- รายละเอียดเพียงพอ ไม่ลงลึกเหมือน Flowchart ในหัวข้อ 3.4

#### Pattern แนะนำสำหรับ RBMS-POS — 3.2 Use Case Diagram

```markdown
3.2 แผนภาพกรณีการใช้งาน (Use Case Diagram)

[รูปที่ 3.2 แผนภาพกรณีการใช้งานของระบบ RBMS-POS]

การวิเคราะห์ความต้องการของผู้ใช้งานในระบบบริหารจัดการร้านอาหาร RBMS-POS
สามารถแบ่งผู้ใช้งาน (Actor) ออกเป็น 5 กลุ่มหลัก โดยแต่ละกลุ่มมีสิทธิและขอบเขต
การใช้งานระบบ (Use Case) ดังนี้:

1. เจ้าของร้าน/ผู้จัดการ (Owner/Manager) เป็นผู้ใช้งานที่มีสิทธิ์สูงสุดในระบบ
   1.1. ตั้งค่าระบบและร้านค้า ผู้จัดการสามารถตั้งค่า Service Charge ภาษี
        และข้อมูลพื้นฐานของร้านได้
   1.2. จัดการเมนูอาหาร สามารถเพิ่ม/แก้ไข/ลบเมนู หมวดหมู่ และตัวเลือกอาหาร
        (Option Group)
   1.3. จัดการพนักงานและตำแหน่งงาน สามารถสร้างตำแหน่งใหม่ กำหนดสิทธิ์ผ่าน
        Permission Matrix และเพิ่มข้อมูลพนักงานพร้อมที่อยู่/การศึกษา
   1.4. จัดการโต๊ะและผังร้าน สามารถจัดวางโต๊ะแบบ Drag-and-Drop พร้อม
        FloorObject เช่น ห้องน้ำ บันได
   1.5. ดูรายงานและ Dashboard สามารถเรียกดูยอดขาย จำนวนคำสั่งซื้อ และ
        วิเคราะห์เมนูยอดนิยม

2. แคชเชียร์ (Cashier) เป็นผู้รับชำระเงินและจัดการลิ้นชักเงินสด
   2.1. เปิด-ปิด Cashier Session ระบุยอดเงินสดเริ่มต้นและสิ้นสุดในลิ้นชัก
   2.2. รับชำระเงิน รองรับ Cash, QR Promtpay และ QR Bank
   2.3. ตรวจสอบสลิปโอนเงิน ระบบ OCR ตรวจสลิปอัตโนมัติ พร้อม Manual Fallback
   2.4. Split Bill / Unsplit แยกหรือรวมบิลในกรณีลูกค้าหลายคน
   2.5. พิมพ์ใบเสร็จ ผ่าน Thermal Printer

3. พนักงานครัว (Kitchen Staff) เป็นผู้รับและทำอาหารตาม Order
   3.1. ดู Kitchen Display แสดง Order ใหม่แบบ Real-time
   3.2. เปลี่ยนสถานะรายการอาหาร Pending → Sent → Preparing → Ready → Served
   3.3. ยกเลิก/Void รายการ พร้อมระบุเหตุผล
   3.4. กรองรายการตามหมวด แสดงเฉพาะอาหาร เครื่องดื่ม หรือของหวาน

4. พนักงานเสริฟ (Waiter) เป็นผู้รับ Order ที่โต๊ะและจัดการสถานะโต๊ะ
   4.1. รับ Order ที่โต๊ะ สร้าง Order ใหม่และส่งให้ครัว
   4.2. จัดการสถานะโต๊ะ Available → Reserved → Occupied → Billing → Cleaning
   4.3. จองโต๊ะ (Reservation) สำหรับลูกค้าที่จองล่วงหน้า
   4.4. ผูกโต๊ะ (Table Link) สำหรับลูกค้ากลุ่มใหญ่ที่ต้องใช้หลายโต๊ะ
   4.5. ปิดบิลและส่งให้แคชเชียร์

5. ลูกค้า (Customer Self-Order) เป็นลูกค้าที่สั่งอาหารด้วยตนเองผ่านมือถือ
   5.1. สแกน QR Code ที่โต๊ะ เข้าสู่หน้าสั่งอาหารผ่าน Mobile Web
   5.2. เลือกเมนูและสั่งอาหาร ดูรูป ราคา และเลือก Option Group
   5.3. เรียกพนักงาน แจ้งความต้องการพิเศษ
   5.4. ขอชำระเงิน เพื่อให้แคชเชียร์มาเก็บเงินที่โต๊ะ
```

### 3.3 หัวข้อ 3.3 ภาพรวมการทำงานของระบบ (Swimlane) ⭐

#### 🎯 ตัวอย่างที่ 2 — Pattern: Swimlane 3 lanes
> "3.3 ภาพรวมการทำงานของระบบ
>
> [รูปที่ 3.3 ภาพรวมการทำงานของระบบ]
>
> เพื่อให้เห็นถึงความสัมพันธ์และหน้าที่รับผิดชอบในแต่ละขั้นตอนอย่างชัดเจน จึงได้ออกแบบแผนภาพขั้นตอนการทำงานโดยแบ่งแยกตามบทบาท (Swimlane) ออกเป็น 3 ส่วนหลัก ได้แก่ ลูกค้า (Customer), ระบบประมวลผล (System), และผู้ดูแลระบบ (Admin) โดยมีรายละเอียดการไหลของข้อมูลดังนี้:
>
> 1. ส่วนของลูกค้า (Customer) เป็นผู้เริ่มต้นกระบวนการโดยการเข้าเว็บไซต์ ค้นหาอุปกรณ์ไอที และเพิ่มลงตะกร้า เมื่อกดยืนยันการสั่งซื้อ ลูกค้าจะต้องดำเนินการเลือกที่อยู่และชำระเงิน (ผ่าน Omise หรือแนบสลิป) หลังจากแอดมินจัดส่งสินค้าแล้ว ลูกค้ามีหน้าที่ติดตามสถานะ และกดยืนยันการรับสินค้าพร้อมรีวิวเมื่อกระบวนการเสร็จสิ้น
>
> 2. ส่วนของระบบ (System) จะทำหน้าที่เป็นตัวกลางในการตรวจสอบเงื่อนไขต่างๆ เช่น ตรวจสอบว่าลูกค้าเข้าสู่ระบบแล้วหรือไม่ (หากยัง จะบังคับให้เข้าสู่ระบบก่อน) จากนั้นระบบจะรับหน้าที่บันทึกข้อมูลคำสั่งซื้อลงฐานข้อมูล แล้วจะส่งอีเมลแจ้งเตือนอัตโนมัติและอัปเดตสถานะคำสั่งซื้อให้สมบูรณ์ในขั้นตอนสุดท้าย
>
> 3. ส่วนของผู้ดูแลระบบ (Admin) หลังจากระบบบันทึกคำสั่งซื้อแล้ว ผู้ดูแลระบบจะเข้ามารับช่วงต่อในการตรวจสอบความถูกต้องของสลิปหรือยอดเงิน หากพบปัญหาเกิดขึ้น ผู้ดูแลระบบสามารถยกเลิกสินค้าได้ แต่หากข้อมูลถูกต้อง ผู้ดูแลระบบจะดำเนินการจัดเตรียมสินค้าและเปลี่ยนสถานะเป็นจัดส่งแล้ว เพื่อให้ลูกค้าสามารถติดตามพัสดุต่อไปได้"

**สังเกต Pattern**:
- รูปขึ้นก่อน เป็น Swimlane Diagram
- คำอธิบายเป็น **Numbered list ตาม lane** (1. Customer / 2. System / 3. Admin)
- แต่ละ lane เล่า **"จุดเริ่มต้น → ขั้นตอนหลัก → จุดสิ้นสุด"** เป็นย่อหน้าใหญ่
- เน้นการ **เชื่อมต่อระหว่าง lane** ("หลังจาก{lane ก่อน} จะ{lane ถัดไป}")

**สังเกต Pattern (สำคัญมาก)**:
- **รูปขึ้นก่อน** — รูป Flowchart จริงๆ ของระบบนั้น
- ตามด้วย **ย่อหน้าใหญ่ 1 ย่อหน้า** อธิบายขั้นตอนการทำงาน (ไม่ใช้ Bullet)
- รูปแบบประโยค: "การทำงานของระบบ{X} **เริ่มต้นด้วย/จาก**... ระบบจะ... จากนั้น... เมื่อ... สุดท้าย{ผลลัพธ์}"
- ใส่ **รายละเอียดเชิงเทคนิค** เช่น ตัวแปร Session, การ Query DB, ข้อมูลที่เก็บ
- ปิดประโยคด้วย "**ถือเป็นการ{จบกระบวนการ}/เสร็จสิ้น/จบกระบวนการ**"

#### 🎯 ตัวอย่างที่ 2 — Pattern Sub-section ที่ละเอียดมาก (ระบบจัดสเปก)
> "การออกแบบการทำงานของ Session ในระบบจัดสเปกคอมพิวเตอร์
>

>

>
> 1. การเก็บข้อมูลเมื่อเลือกซีพียู (Store Data in Session) สมมติว่าผู้ใช้กดเลือก CPU เป็น 'AMD Ryzen 5 7600' ระบบจะทำการตรวจสอบย้อนหลังในฐานข้อมูล (products และ product_builder_specs) และนำสเปกที่สำคัญมาเก็บไว้ในเซิร์ฟเวอร์ภายใต้ตัวแปร $_SESSION['pc_build']['cpu'] โดยมีโครงสร้างข้อมูลที่ถูกจำไว้ (ตัวอย่าง) ดังนี้:
>    • id = 101
>    • name = AMD Ryzen 5 7600
>    • socket = AM5 (ข้อมูลสำคัญสำหรับเมนบอร์ดและซิงค์ระบายความร้อน)
>    • ram_type = DDR5 (ข้อมูลสำคัญสำหรับเมนบอร์ดและแรม)
>    • tdp = 65W (ข้อมูลสำคัญสำหรับคำนวณพาวเวอร์ซัพพลาย)
>
> 2. การประมวลผลเมื่อเปลี่ยนไปหมวดหมู่เมนบอร์ด (Filter & Query) เมื่อผู้ใช้คลิกเปลี่ยนหน้ามาที่หมวดหมู่ 'เมนบอร์ด' ระบบฝั่ง Backend จะยังไม่ดึงข้อมูลเมนบอร์ดทั้งหมดมาแสดง แต่จะทำการตรวจสอบก่อนว่า ใน Session มีข้อมูลซีพียูถูกเลือกไว้แล้วหรือไม่..."

**สังเกต Pattern (สำหรับระบบซับซ้อนที่ต้องอธิบายเชิงลึก)**:
- เพิ่ม **Sub-section** หลัง Flowchart หลัก เพื่ออธิบายกลไกภายใน
- ใช้ **ตัวอย่างสถานการณ์จริง** ("สมมติว่าผู้ใช้กดเลือก CPU เป็น...")
- ระบุ **ตัวแปร/Code structure** จริง (เช่น `$_SESSION['pc_build']['cpu']`)
- ใช้ **Bullet "•"** สำหรับโครงสร้างข้อมูล (id, name, socket, ...)

>
> ระบบประวัติการเข้าชมและถามตอบ (History & Q&A) ผู้ใช้งานสามารถดูประวัติรายการสินค้าที่ตนเองเคยเข้าชมล่าสุดได้ นอกจากนี้ยังสามารถตั้งคำถามหรือข้อสงสัยเกี่ยวกับสินค้า (Q&A) ในหน้ารายละเอียดสินค้านั้นๆ เพื่อให้ผู้ดูแลระบบเข้ามาตอบได้"

**สังเกต Pattern (สำคัญมาก)**:
- **ย่อหน้าเปิด** ระบุจำนวนตาราง + ลิสต์ชื่อตารางทั้งหมด (ก่อนรายละเอียด)
- **ER Diagram ขึ้นก่อน Data Dictionary** (รูป overview)
- **Data Dictionary** มี 4 คอลัมน์: **Field Name | Data Type | Description | Example**

- ใต้ตารางมี **caption "ตารางที่ 3.X {ชื่อตาราง}"** + คำอธิบายสั้นว่าตารางเก็บอะไร

#### 📋 ตัวอย่างที่ 1 — Pattern Data Dictionary 5 คอลัมน์ (เปรียบเทียบ)
> | ชื่อฟิลด์ | ชนิด | คีย์ | Null | คำอธิบาย |
> | id | INTEGER | PK | No | รหัสลำดับผู้ใช้งาน |

**ความต่าง**:
- ตัวอย่าง 2: 4 คอลัมน์ (Field/Type/Description/Example) — **เน้นตัวอย่างจริง**
- ตัวอย่าง 1: 5 คอลัมน์ (Field/Type/Key/Null/Description) — **เน้น metadata เชิงเทคนิค**

**สำหรับ RBMS-POS แนะนำใช้แบบไหน?**
→ **ใช้รูปแบบของตัวอย่างที่ 2 (4 คอลัมน์)** เพราะ:
- มี Example ช่วยให้ผู้อ่านเห็นภาพ
- ลดความซับซ้อนของตาราง (ไม่ต้องมี Key/Null column)
- ระบุ PK/FK ใน Description ก็พอ (เช่น "รหัสประจำตัวผู้ใช้งาน (Primary Key)", "รหัสลำดับโต๊ะ อ้างอิง TbTable.Id")

```markdown
3.7 การออกแบบฐานข้อมูล

จากขั้นตอนการทำงานของการออกแบบและการพัฒนาระบบบริหารจัดการร้านอาหาร
RBMS-POS ผู้จัดทำได้ออกแบบฐานข้อมูลเพื่อใช้ในการจัดเก็บข้อมูลที่เกี่ยวข้อง
กับการบริหารร้าน การสั่งอาหาร และการชำระเงิน โดยฐานข้อมูลประกอบด้วย
ทั้งหมด 37 ตาราง แบ่งตาม 8 Business Module ดังนี้:

- Module Admin/Authorization: ตารางเก็บข้อมูลผู้ใช้ ตำแหน่งงาน สิทธิ์การ
  เข้าถึง และประวัติการเข้าสู่ระบบ
- Module HumanResource: ตารางเก็บข้อมูลพนักงาน ที่อยู่ การศึกษา และ
  ประวัติการทำงาน
- Module Menu: ตารางเก็บข้อมูลเมนูอาหาร หมวดหมู่ และตัวเลือกอาหาร
- Module Order: ตารางเก็บข้อมูลออเดอร์ รายการอาหาร และบิล
- Module Payment: ตารางเก็บข้อมูลการชำระเงิน Cashier Session และสลิป
- Module Table: ตารางเก็บข้อมูลโซน โต๊ะ การจอง และผังร้าน
- Module Notification: ตารางเก็บข้อมูลการแจ้งเตือน
- Module Admin: ตารางเก็บข้อมูลตั้งค่าระบบและ Audit Log

สำหรับการนำเสนอในรายงานนี้ ผู้จัดทำเลือกแสดงเฉพาะ 10 ตารางหลักที่
เป็นแกนกลางของแต่ละ Module ส่วนตาราง Master Data และตาราง junction
อยู่ในภาคผนวก ก ซึ่งมีรายละเอียดดังนี้
```

## 4. Pattern ENUMS (ใส่ในส่วน 3.7 ก่อน Data Dictionary)

#### 🎯 ตัวอย่างที่ 1 มี ENUMS — ตัวอย่างที่ 2 ไม่มี (เก็บ enum ใน column type)

**สำหรับ RBMS-POS แนะนำใส่ ENUMS** เพราะระบบมี enum หลายตัว:

```markdown
การกำหนดตัวเลือกที่ตายตัว (Enumerations)

ระบบ RBMS-POS ใช้ enum เพื่อระบุสถานะหรือประเภทที่มีค่าตายตัว ดังนี้:

1. EOrderStatus: สถานะของออเดอร์
   • Open (0) — ออเดอร์ที่กำลังเปิด รับรายการอาหารได้
   • Billing (1) — ออเดอร์ที่กำลังปิดบิล รอชำระเงิน
   • Completed (2) — ออเดอร์ที่ชำระเงินสำเร็จและเสร็จสิ้น

2. EOrderItemStatus: สถานะของรายการอาหาร (7 สถานะ)
   • Pending (0) — รอส่งครัว
   • Sent (1) — ส่งครัวแล้ว
   • Preparing (2) — กำลังปรุง
   • Ready (3) — เสร็จแล้ว รอเสริฟ
   • Served (4) — เสริฟแล้ว
   • Voided (5) — ยกเลิกหลังเริ่มทำ
   • Cancelled (6) — ยกเลิกก่อนเริ่มทำ

3. ETableStatus: สถานะของโต๊ะ
   • Available (0), Reserved (1), Occupied (2), Billing (3),
     Cleaning (4), Unavailable (5)

4. EPaymentMethod: วิธีการชำระเงิน
   • Cash (0), QrPayment (1)

5. EPaymentStatus: สถานะการชำระเงิน
   • Pending (0), Paid (1), Refunded (2)

6. ESlipVerificationStatus: สถานะการตรวจสอบสลิป
   • None (0), Matched (1), Mismatched (2), Manual (3)

7. ECategoryType: ประเภทของหมวดหมู่เมนู
   • Food (0), Beverage (1), Dessert (2)

8. EMenuTag: แท็กของเมนู
   • Recommended (0), Seasonal (1), SlowPreparation (2)

9. ENotificationGroup: กลุ่มผู้รับการแจ้งเตือน
   • Kitchen, Floor, Cashier, Manager

10. EFloorObjectType: ประเภทวัตถุภายในร้าน
    • Restroom, Stairs, Counter, Kitchen, Exit, Cashier, Plant, Decoration
```
