ในบทนี้จะกล่าวถึงทฤษฎี แนวคิด และเทคโนโลยีที่เกี่ยวข้องกับการพัฒนาระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS ประกอบด้วยทฤษฎีและแนวคิดที่ใช้ในการออกแบบ ตลอดจนเครื่องมือและเทคโนโลยีที่ใช้ในการพัฒนา ซึ่งมีรายละเอียดดังนี้

## 2.1 อุตสาหกรรมร้านอาหารและปัญหาของระบบบริหารแบบดั้งเดิม

ธุรกิจร้านอาหารเป็นหนึ่งในอุตสาหกรรมที่มีการแข่งขันสูงและมีความหลากหลายของรูปแบบการให้บริการ [1] ประเภทของร้านอาหารที่ปรากฏในตลาดสามารถจำแนกได้หลายรูปแบบ เช่น ร้านอาหารตามสั่ง (À la carte) ที่เน้นการสั่งอาหารจากเมนูแบบรายจาน ร้านอาหารญี่ปุ่นและเกาหลีแบบบุฟเฟ่ต์ (Buffet) ที่ลูกค้าสามารถสั่งอาหารได้ไม่จำกัดในเวลาที่กำหนด ร้านชาบูและสุกี้ที่มีรูปแบบการสั่งซ้ำเป็นรอบ ตลอดจนร้านกาแฟและคาเฟ่ที่ลูกค้าใช้เวลาในร้านนาน รูปแบบที่แตกต่างกันส่งผลให้แต่ละร้านมีกระบวนการรับออเดอร์ การจัดการครัว และการชำระเงินที่แตกต่างกันออกไป

จากการศึกษาสภาพการดำเนินงานของร้านอาหารในปัจจุบัน คณะผู้จัดทำพบว่าระบบบริหารแบบดั้งเดิมยังคงมีปัญหาสำคัญหลายประการ ซึ่งส่งผลต่อประสบการณ์การให้บริการและประสิทธิภาพในการบริหารจัดการ โดยสามารถสรุปปัญหาหลักได้ดังต่อไปนี้

1. **ความล่าช้าในการรับออเดอร์**: ลูกค้าต้องเรียกพนักงานเพื่อขอเมนูและจดรายการ ทำให้เกิดเวลารอที่ยาวนานในช่วงที่ร้านมีผู้ใช้บริการจำนวนมาก
2. **ความผิดพลาดของการสื่อสารระหว่างหน้าร้านและครัว**: การจดออเดอร์ผ่านกระดาษทำให้เกิดปัญหาครัวอ่านลายมือไม่ออก ใบออเดอร์หาย หรือตกหล่นรายการในกระบวนการส่งต่อ
3. **ความช้าและความผิดพลาดในการตรวจสอบสลิปโอนเงิน**: การตรวจสลิปด้วยตาเปล่าทำให้แคชเชียร์ใช้เวลามากและมีความเสี่ยงในการอ่านยอดเงินผิด
4. **ความซับซ้อนในการแยกบิลของลูกค้ากลุ่ม**: เมื่อลูกค้าต้องการแยกชำระตามรายการหรือตามจำนวนเงิน การคำนวณด้วยมือสร้างความสับสนและใช้เวลานาน
5. **ข้อจำกัดของระบบ POS ในตลาด**: ระบบ POS ที่มีอยู่ส่วนใหญ่ให้บริการในรูปแบบ Software-as-a-Service (SaaS) ที่มีค่าใช้จ่ายรายเดือนต่อเนื่อง และไม่ยืดหยุ่นต่อการปรับแต่งให้เหมาะกับโครงสร้างของร้านอาหารแต่ละประเภท

อย่างไรก็ตาม การนำเทคโนโลยีสารสนเทศมาใช้ในร้านอาหารยังคงมีอุปสรรคและความเสี่ยงในการดำเนินงานจริง [2] ซึ่งคณะผู้จัดทำได้พิจารณาประกอบ ได้แก่ ค่าใช้จ่ายเริ่มต้นด้านอุปกรณ์ฮาร์ดแวร์และการติดตั้งระบบ ความซับซ้อนในการเรียนรู้การใช้งานของพนักงาน และเสถียรภาพของเครือข่ายอินเทอร์เน็ตในบางพื้นที่ ซึ่งล้วนเป็นปัจจัยที่ต้องคำนึงถึงในการออกแบบระบบให้รองรับการใช้งานในสภาพแวดล้อมที่แตกต่างกัน

## 2.2 ระบบจุดขาย (Point of Sale: POS) — แนวคิดและองค์ประกอบหลัก

ระบบจุดขาย หรือ Point of Sale (POS) [3] คือระบบสารสนเทศที่ใช้บริหารจัดการกระบวนการซื้อขายสินค้าและบริการ ณ จุดที่ลูกค้าทำการชำระเงิน ในบริบทของธุรกิจร้านอาหาร ระบบ POS ทำหน้าที่ครอบคลุมตั้งแต่การรับรายการสั่งอาหาร การส่งรายการไปยังครัว การคำนวณยอดรวมและภาษีมูลค่าเพิ่ม การจัดการสถานะของโต๊ะ ไปจนถึงการรับชำระเงินและการบันทึกข้อมูลการขาย

ระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS ที่คณะผู้จัดทำพัฒนาขึ้น ได้ออกแบบให้ครอบคลุมองค์ประกอบหลักของระบบจุดขายในร้านอาหาร ซึ่งประกอบด้วย 6 องค์ประกอบ ดังนี้

1. **ระบบจัดการคำสั่งซื้อ (Order Management)**: เป็นกระบวนการรับและจัดเก็บรายการสั่งอาหารของลูกค้า ระบบจะผูกออเดอร์ (Order) เข้ากับโต๊ะ (Table) ที่ใช้บริการ และจัดเก็บรายการอาหารแต่ละชิ้น (OrderItem) พร้อมตัวเลือก (Option) เช่น ระดับความเผ็ดหรือขนาดของแก้วเครื่องดื่ม ตลอดจนแยกประเภทของรายการตามหมวดหมู่ ได้แก่ อาหาร เครื่องดื่ม และของหวาน เพื่อการประมวลผลที่แตกต่างกัน

2. **ระบบบริหารบิล (Billing)**: เป็นกระบวนการคำนวณยอดเงินตามรายการที่สั่ง พร้อมรองรับการแยกบิล (Split Bill) ในกรณีที่ลูกค้ากลุ่มต้องการชำระเงินแยก โดยออเดอร์หนึ่งครั้งสามารถมีบิล (OrderBill) ได้หลายใบ ระบบยังคำนวณค่าบริการ (Service Charge) และภาษีมูลค่าเพิ่ม (VAT) ตามการตั้งค่าของร้านโดยอัตโนมัติ

3. **ระบบจัดการโต๊ะและผังร้าน (Table Management)**: เป็นการบริหารสถานะของโต๊ะในร้าน เพื่อให้พนักงานสามารถจัดการที่นั่งของลูกค้าได้อย่างมีประสิทธิภาพ โดยระบบรองรับการแบ่งโต๊ะตามโซน (Zone) และการกำหนดสถานะของโต๊ะ เช่น พร้อมใช้งาน กำลังใช้งาน รอชำระเงิน และอยู่ในระหว่างการทำความสะอาด

4. **ระบบครัว (Kitchen Display System: KDS)**: เป็นหน้าจอแสดงผลในครัวที่แสดงรายการอาหารที่ลูกค้าสั่งเข้ามา โดยระบบจะแยกการแสดงผลตามสถานี (Station) 3 ประเภท ได้แก่ สถานีอาหาร สถานีเครื่องดื่ม และสถานีของหวาน เพื่อให้พนักงานครัวแต่ละสถานีโฟกัสกับรายการที่ตนรับผิดชอบโดยตรง

5. **ระบบรับชำระเงิน (Payment)**: เป็นกระบวนการรับเงินจากลูกค้า ระบบรองรับการชำระเงินสด การชำระผ่านคิวอาร์โค้ด (QR Code) และการตรวจสอบสลิปโอนเงินด้วยระบบรู้จำตัวอักษรด้วยภาพ (OCR) นอกจากนี้ยังมีระบบกะของแคชเชียร์ (Cashier Session) ที่ใช้บริหารลิ้นชักเงินสดและการตรวจสอบยอดเมื่อสิ้นกะ

6. **ระบบแจ้งเตือนแบบเวลาจริง (Real-time Notification)**: เป็นกลไกการสื่อสารข้อมูลระหว่างหน้าร้าน ครัว และลูกค้า เพื่อให้ทุกฝ่ายได้รับข้อมูลสถานะของออเดอร์อย่างทันท่วงที โดยใช้เทคโนโลยี SignalR ในการกระจายข้อมูลแบบ Server-to-Client ซึ่งจะอธิบายในรายละเอียดเพิ่มเติมในหัวข้อ 2.4

ระบบทั้งหมดที่กล่าวมานี้ได้รับการออกแบบในรูปแบบสถาปัตยกรรมแบบหลายชั้น (N-Tier Architecture) ประกอบด้วย 8 โมดูลธุรกิจ (Business Module) ได้แก่ Admin, Authorization, HumanResource, Menu, Notification, Order, Payment และ Table ซึ่งให้บริการผ่าน Web API จำนวน 23 Controllers และจัดเก็บข้อมูลในฐานข้อมูลเชิงสัมพันธ์จำนวน 37 ตาราง (Entity) พร้อมการสื่อสารแบบเวลาจริงผ่าน SignalR Hub จำนวน 2 Hub

## 2.3 ระบบจุดขายในตลาดที่นำมาใช้อ้างอิง

ในการออกแบบระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS คณะผู้จัดทำได้ศึกษาระบบจุดขายในตลาดที่ใช้งานในธุรกิจร้านอาหารไทยจำนวน 2 ระบบหลัก เพื่อใช้เป็นข้อมูลอ้างอิงในการวิเคราะห์จุดเด่นและจุดที่ระบบของคณะผู้จัดทำสามารถสร้างความแตกต่างได้

### 2.3.1 ระบบ FoodStory

FoodStory [4] เป็นระบบจุดขายที่พัฒนาในประเทศไทย ออกแบบมาเพื่อรองรับการบริหารธุรกิจร้านอาหารและคาเฟ่ขนาดเล็กถึงกลาง โดยปัจจุบันได้รับการเข้าซื้อกิจการโดยกลุ่ม LINE MAN Wongnai และผนวกเข้าเป็นหนึ่งในผลิตภัณฑ์ของกลุ่ม จุดเด่นของระบบ FoodStory คือการเน้นฟังก์ชันด้านการบริหารคลังสินค้า (Inventory Management) และระบบสมาชิกสะสมคะแนน (Loyalty Program) สำหรับสร้างความผูกพันกับลูกค้าระยะยาว

### 2.3.2 ระบบ Wongnai POS / LINE MAN POS

Wongnai POS หรือ LINE MAN POS [5] เป็นระบบจุดขายในกลุ่ม LINE MAN Wongnai ที่ปัจจุบันครองส่วนแบ่งทางการตลาดในธุรกิจร้านอาหารไทยอย่างมีนัยสำคัญ ระบบประกอบด้วยส่วนย่อยหลายส่วน ได้แก่ POS Manager สำหรับเจ้าของร้าน POS Staff สำหรับพนักงาน และ Mobile Order สำหรับลูกค้า โดยจุดเด่นของระบบคือการเชื่อมต่อกับแพลตฟอร์มของ LINE MAN ที่ครอบคลุมตั้งแต่การสั่งอาหารแบบ Dine-in การสั่งกลับบ้าน และการจัดส่ง

### 2.3.3 จุดที่ระบบ RBMS-POS แตกต่างจากระบบในตลาด

จากการศึกษาระบบจุดขายในตลาดทั้งสองระบบ คณะผู้จัดทำพบว่าระบบเหล่านี้ส่วนใหญ่ให้บริการในรูปแบบ Software-as-a-Service (SaaS) ที่มีค่าใช้จ่ายรายเดือนและถูกควบคุมโดยผู้ให้บริการเป็นหลัก ดังนั้นคณะผู้จัดทำจึงออกแบบระบบ RBMS-POS ให้มีจุดต่างจากระบบในตลาด 4 ข้อ ดังนี้

1. **รูปแบบ Open Source และ Self-hosted**: ระบบ RBMS-POS เผยแพร่ในรูปแบบโอเพนซอร์ส (Open Source) ที่ผู้ใช้งานสามารถนำไปติดตั้งบนเซิร์ฟเวอร์ของตนเองได้ โดยไม่ต้องเสียค่าใช้จ่ายรายเดือนต่อเนื่องเหมือนระบบ SaaS
2. **ระบบตรวจสอบสลิปอัตโนมัติด้วย OCR**: ระบบ RBMS-POS ผสานเทคโนโลยีการรู้จำตัวอักษรด้วยภาพ (OCR) ในกระบวนการตรวจสอบสลิปโอนเงิน ซึ่งเป็นจุดที่ระบบในตลาดส่วนใหญ่ไม่ได้เน้นเป็นพิเศษ
3. **ระบบเมทริกซ์สิทธิ์การเข้าถึงแบบไดนามิก (Dynamic Permission Matrix)**: ระบบ RBMS-POS รองรับการกำหนดสิทธิ์การเข้าถึงตามตำแหน่งงานของแต่ละร้านได้เอง ทำให้สามารถปรับโครงสร้างองค์กรในระบบให้ตรงกับร้านอาหารแต่ละประเภทโดยไม่ต้องแก้ไขรหัสคำสั่ง
4. **การสื่อสารแบบเวลาจริงผ่าน WebSocket**: ระบบ RBMS-POS ใช้ไลบรารี SignalR ที่สื่อสารผ่านโปรโตคอล WebSocket ในการกระจายข้อมูลระหว่างหน้าร้านและครัว ในขณะที่ระบบในตลาดส่วนใหญ่ใช้การสอบถามซ้ำเป็นช่วง ๆ (Polling) หรือการซิงโครไนซ์ผ่านระบบคลาวด์

## 2.4 กลไกการเปลี่ยนสถานะ (State Machine) และการสื่อสารแบบเวลาจริง (Real-time Communication)

### 2.4.1 ทฤษฎีกลไกการเปลี่ยนสถานะ (State Machine)

กลไกการเปลี่ยนสถานะ หรือ State Machine [6] เป็นแนวคิดทางวิศวกรรมซอฟต์แวร์ที่ใช้ในการอธิบายและควบคุมพฤติกรรมของระบบที่มีสถานะที่ชัดเจนและจำกัด โดยกำหนดว่าระบบจะอยู่ในสถานะใดสถานะหนึ่งในช่วงเวลาหนึ่ง และสามารถเปลี่ยนจากสถานะหนึ่งไปยังอีกสถานะหนึ่งได้ก็ต่อเมื่อเกิดเหตุการณ์ (Event) ที่เป็นไปตามเงื่อนไขที่กำหนดไว้เท่านั้น แนวคิดนี้เหมาะกับการออกแบบกระบวนการในระบบจุดขาย ซึ่งออเดอร์และรายการอาหารแต่ละชิ้นต้องผ่านขั้นตอนการประมวลผลที่ลำดับชัดเจน

ในระบบ RBMS-POS คณะผู้จัดทำได้ออกแบบกลไกการเปลี่ยนสถานะออกเป็น 2 ระดับ คือ ระดับออเดอร์ (Order) และระดับรายการอาหาร (OrderItem)

**สถานะของออเดอร์ (Order State Machine)** ประกอบด้วย 3 สถานะ ดังนี้
1. **Open** — ออเดอร์ที่เปิดอยู่ ลูกค้ายังสั่งเพิ่มได้และครัวยังประมวลผลรายการได้
2. **Billing** — ออเดอร์ที่ขอบิลแล้ว รอการชำระเงิน
3. **Completed** — ออเดอร์ที่ชำระเงินสำเร็จและเสร็จสิ้นกระบวนการ

ในกรณีที่บิลถูกยกเลิกในระหว่างกระบวนการชำระเงิน ระบบจะย้อนสถานะของออเดอร์จาก Billing กลับเป็น Open เพื่อให้สามารถดำเนินการต่อได้

**สถานะของรายการอาหาร (OrderItem State Machine)** ประกอบด้วย 7 สถานะ ดังนี้
1. **Pending** — รายการที่เพิ่มเข้าตะกร้าแต่ยังไม่ส่งครัว
2. **Sent** — รายการที่ส่งครัวแล้ว ปรากฏในจอ Kitchen Display
3. **Preparing** — รายการที่ครัวเริ่มปรุง
4. **Ready** — รายการที่ปรุงเสร็จและพร้อมเสริฟ
5. **Served** — รายการที่เสริฟให้ลูกค้าเรียบร้อยแล้ว
6. **Voided** — รายการที่ถูกยกเลิกก่อนส่งครัว (ในสถานะ Pending)
7. **Cancelled** — รายการที่ถูกยกเลิกหลังส่งครัว ซึ่งต้องระบุเหตุผลในการยกเลิก

กฎสำคัญของกลไกการเปลี่ยนสถานะระดับรายการอาหาร คือ การยกเลิกรายการสามารถทำได้เฉพาะเมื่อรายการอยู่ในสถานะ Sent หรือ Preparing เท่านั้น เมื่อรายการเข้าสู่สถานะ Ready แล้ว จะไม่สามารถยกเลิกได้ เนื่องจากครัวได้ปรุงอาหารเสร็จสิ้นและเกิดต้นทุนแล้ว

### 2.4.2 ทฤษฎีการสื่อสารแบบเวลาจริง (Real-time Communication)

การสื่อสารแบบเวลาจริง [7] เป็นรูปแบบการแลกเปลี่ยนข้อมูลระหว่างเครื่องลูกข่าย (Client) และเซิร์ฟเวอร์ (Server) ที่ข้อมูลถูกส่งและแสดงผลภายในเวลาที่สั้นมากจนแทบรู้สึกได้ทันที โดยทั่วไปสามารถดำเนินการได้สองรูปแบบหลัก ได้แก่ การที่ Client สอบถามเซิร์ฟเวอร์ซ้ำเป็นช่วง ๆ (Polling) ซึ่งสร้างภาระให้กับเซิร์ฟเวอร์โดยไม่จำเป็น และการใช้โปรโตคอลที่รองรับการเปิดช่องทางการสื่อสารแบบสองทาง (Bidirectional) เช่น WebSocket ที่อนุญาตให้เซิร์ฟเวอร์ส่งข้อมูลไปยัง Client ได้โดยอัตโนมัติ

ระบบ RBMS-POS ใช้ไลบรารี SignalR ในการจัดการการสื่อสารแบบเวลาจริง โดยไลบรารีนี้สามารถเลือกโปรโตคอลที่เหมาะสมที่สุดให้อัตโนมัติ ได้แก่ WebSocket, Server-Sent Events (SSE) และ Long Polling โดยจะใช้ WebSocket เป็นทางเลือกแรก และใช้ทางเลือกอื่นเป็นกลไกสำรอง (Fallback) ในกรณีที่สภาพแวดล้อมไม่รองรับ WebSocket

ระบบประกอบด้วย SignalR Hub จำนวน 2 Hub ดังนี้
1. **OrderHub** ที่จุดบริการ `/hubs/order` — ทำหน้าที่กระจายข้อมูลที่เกี่ยวข้องกับออเดอร์และโต๊ะ โดยจัดกลุ่มผู้รับข้อมูลออกเป็น 3 กลุ่ม ได้แก่ `kitchen` (พนักงานครัว), `floor` (พนักงานเสริฟและแคชเชียร์) และ `table_{tableId}` (ลูกค้าที่สั่งอาหารผ่านมือถือของโต๊ะนั้น) เหตุการณ์ที่ระบบส่งผ่าน Hub นี้ ได้แก่ รายการใหม่ที่เพิ่งส่งครัว (NewOrderItems) การเปลี่ยนสถานะรายการ (ItemStatusChanged) การยกเลิกรายการ (ItemCancelled) การเปลี่ยนสถานะโต๊ะ (TableStatusChanged) การอัปโหลดสลิป (SlipUploaded) และการชำระเงินสำเร็จ (PaymentCompleted)
2. **NotificationHub** ที่จุดบริการ `/hubs/notification` — ทำหน้าที่กระจายการแจ้งเตือนทั่วไปไปยังกลุ่มผู้ใช้งานตามบทบาท โดยระบบจะเข้าร่วมกลุ่มอัตโนมัติตามสิทธิ์การเข้าถึงของผู้ใช้งาน ได้แก่ กลุ่ม Kitchen สำหรับพนักงานครัว กลุ่ม Floor สำหรับพนักงานเสริฟ กลุ่ม Cashier สำหรับแคชเชียร์ และกลุ่ม Manager สำหรับผู้จัดการ การแจ้งเตือนที่ส่งผ่าน Hub นี้จะปรากฏในรูปแบบ Toast Notification และเก็บไว้ใน Notification Drawer พร้อมตัวนับจำนวนข้อความที่ยังไม่ได้อ่าน

ด้วยกลไกดังกล่าว ระบบ RBMS-POS สามารถส่งข้อมูลออเดอร์ระหว่างหน้าร้านและครัวภายในเวลาประมาณ 1 วินาที (คาดการณ์ตามสถาปัตยกรรมของระบบ) ซึ่งช่วยลดความล่าช้าและความผิดพลาดในกระบวนการสื่อสาร

## 2.5 การควบคุมการเข้าถึงตามบทบาท (RBAC) และการรู้จำตัวอักษรด้วยภาพ (OCR)

### 2.5.1 การควบคุมการเข้าถึงตามบทบาท (Role-Based Access Control: RBAC)

การควบคุมการเข้าถึงตามบทบาท หรือ Role-Based Access Control (RBAC) [8] เป็นแนวคิดการจัดการสิทธิ์การเข้าถึงทรัพยากรในระบบสารสนเทศ ที่ใช้บทบาท (Role) เป็นตัวกลางในการกำหนดสิทธิ์แทนการกำหนดสิทธิ์ให้กับผู้ใช้งานรายบุคคลโดยตรง แนวคิดนี้ทำให้การบริหารสิทธิ์ในองค์กรขนาดกลางและขนาดใหญ่มีความเป็นระบบ ลดความซ้ำซ้อนของการกำหนดสิทธิ์ และง่ายต่อการปรับเปลี่ยนเมื่อโครงสร้างองค์กรเปลี่ยนแปลง

ในระบบ RBMS-POS คณะผู้จัดทำได้ออกแบบกลไก RBAC ในรูปแบบเมทริกซ์สิทธิ์การเข้าถึง (Permission Matrix) แบบไดนามิก ที่ประกอบด้วย 3 ระดับ ดังนี้
1. **ระดับโมดูล (Module)** — กำหนดขอบเขตของฟังก์ชันการทำงาน เช่น โมดูลเมนู โมดูลออเดอร์ โมดูลการชำระเงิน โมดูลครัว และโมดูลแดชบอร์ด
2. **ระดับการกระทำ (Action)** — กำหนดสิทธิ์ในแต่ละโมดูลตามประเภทของการกระทำ ได้แก่ การอ่าน (Read) การสร้าง (Create) การแก้ไข (Update) และการลบ (Delete)
3. **ระดับตำแหน่งงาน (Position)** — กำหนดสิทธิ์ผ่านการเชื่อมโยงตำแหน่งงานกับเมทริกซ์ Module × Action ในรูปแบบ Many-to-Many

นอกจากนี้คณะผู้จัดทำได้กำหนดกฎสำคัญในการบริหารสิทธิ์การเข้าถึง ดังนี้
1. พนักงานทุกคนต้องผูกกับตำแหน่งงานหนึ่งตำแหน่งเสมอ
2. เมื่อสร้างตำแหน่งใหม่ ระบบจะกำหนดสิทธิ์ทั้งหมด (Grant All) เป็นค่าเริ่มต้น เพื่อให้ผู้ดูแลปรับลดสิทธิ์ในภายหลังได้ง่าย
3. การลบตำแหน่งสามารถทำได้เฉพาะตำแหน่งที่ไม่มีพนักงานผูกอยู่
4. ชื่อตำแหน่งห้ามซ้ำกัน เพื่อความชัดเจนในการอ้างอิง
5. ระบบจัดเก็บสิทธิ์ของผู้ใช้งานใน Cache เป็นเวลา 10 นาที และล้าง Cache ทันทีเมื่อมีการแก้ไขสิทธิ์ เพื่อความรวดเร็วในการประมวลผล
6. การตรวจสอบสิทธิ์ดำเนินการในสองชั้น ได้แก่ ชั้นหน้าบ้าน (Frontend) ที่ซ่อนปุ่มหรือเมนูที่ผู้ใช้ไม่มีสิทธิ์ และชั้นหลังบ้าน (Backend) ที่ปฏิเสธคำขอ API ที่ไม่ได้รับอนุญาต

### 2.5.2 การรู้จำตัวอักษรด้วยภาพ (Optical Character Recognition: OCR)

การรู้จำตัวอักษรด้วยภาพ หรือ Optical Character Recognition (OCR) [9] เป็นเทคโนโลยีที่แปลงตัวอักษรในไฟล์ภาพหรือเอกสารที่ถูกสแกนให้กลายเป็นข้อมูลตัวอักษรที่คอมพิวเตอร์สามารถอ่านและประมวลผลได้ เทคโนโลยีนี้นิยมใช้ในกระบวนการบันทึกข้อมูลจากเอกสาร การตรวจสอบใบเสร็จ และการประมวลผลสลิปการโอนเงิน

ในระบบ RBMS-POS คณะผู้จัดทำได้ผสานเทคโนโลยี OCR ในกระบวนการตรวจสอบสลิปโอนเงินอัตโนมัติ โดยระบบจะวิเคราะห์ภาพสลิปและดึงข้อมูลสำคัญออกมาเพื่อเปรียบเทียบกับข้อมูลที่ระบบจัดเก็บ ฟิลด์ที่ระบบดึงจากสลิป ได้แก่
1. **ยอดเงินที่โอน** — เปรียบเทียบกับยอดรวมสุทธิของบิล (GrandTotal)
2. **วันที่และเวลาโอน** — ตรวจสอบว่าเป็นวันปัจจุบัน เพื่อป้องกันการนำสลิปเก่ามาใช้ซ้ำ
3. **เลขบัญชีหรือหมายเลขพร้อมเพย์ปลายทาง** — เปรียบเทียบกับข้อมูลร้านค้าใน Shop Settings

ผลลัพธ์การตรวจสอบสลิปจะถูกบันทึกในระบบในรูปแบบสถานะ 4 สถานะ ดังนี้
1. **None** — ยังไม่ผ่านการตรวจสอบด้วย OCR
2. **Matched** — ระบบ OCR อ่านข้อมูลครบถ้วนและตรงกับยอดบิล
3. **Mismatched** — ระบบ OCR อ่านข้อมูลได้แต่บางส่วนไม่ตรงกับยอดบิล
4. **Manual** — สถานะสำรองที่แคชเชียร์ยืนยันด้วยตนเอง ในกรณีที่ภาพสลิปไม่ชัดเจน หรือฟอนต์ของธนาคารไม่เป็นมาตรฐานทำให้ OCR อ่านไม่สำเร็จ

ด้วยกลไกดังกล่าว ระบบสามารถลดเวลาในการตรวจสลิปและความผิดพลาดจากการอ่านยอดด้วยตาเปล่าได้อย่างมีนัยสำคัญ

## 2.6 โปรแกรม Visual Studio และ Visual Studio Code

Visual Studio และ Visual Studio Code [10] คือโปรแกรมแก้ไขซอร์สโค้ด (Source Code Editor) และสภาพแวดล้อมการพัฒนาแบบครบวงจร (Integrated Development Environment: IDE) ที่พัฒนาโดยบริษัทไมโครซอฟท์ (Microsoft) ออกแบบมาเพื่อรองรับการเขียน แก้ไข และตรวจสอบความผิดพลาดของโค้ดในภาษาโปรแกรมที่หลากหลาย โดย Visual Studio เป็นโปรแกรมขนาดใหญ่ที่เหมาะสำหรับการพัฒนาซอฟต์แวร์ขนาดใหญ่ในระบบนิเวศ .NET รองรับการดีบักขั้นสูง การจัดการโครงการ และเครื่องมือทดสอบในตัว ในขณะที่ Visual Studio Code เป็นโปรแกรมที่มีขนาดเล็ก เปิดให้ใช้งานได้ฟรี รองรับการทำงานข้ามแพลตฟอร์ม (Cross-platform) ทั้ง Windows, macOS และ Linux และมีส่วนต่อขยายความสามารถ (Extension) จำนวนมากเพื่อรองรับการพัฒนาในภาษาและเฟรมเวิร์กต่าง ๆ

ในการพัฒนาระบบนี้ คณะผู้จัดทำใช้ Visual Studio ในการพัฒนาส่วนหลังบ้านด้วยภาษา C# โดยอาศัยฟังก์ชัน IntelliSense, การดีบักด้วย Breakpoint และเครื่องมือจัดการ NuGet Package และใช้ Visual Studio Code ในการพัฒนาส่วนหน้าบ้านด้วยภาษา TypeScript ร่วมกับส่วนขยาย Angular Language Service และ ESLint

## 2.7 ภาษา C#

ภาษา C# [11] คือภาษาโปรแกรมระดับสูงเชิงวัตถุ (Object-Oriented Programming Language) ที่พัฒนาโดยบริษัทไมโครซอฟท์ ทำงานบนแพลตฟอร์ม .NET Runtime ที่สามารถประมวลผลข้ามระบบปฏิบัติการได้ ออกแบบมาเพื่อรองรับการพัฒนาแอปพลิเคชันที่มีความซับซ้อนและขนาดใหญ่ มีคุณสมบัติและหลักการทำงานที่สำคัญ ดังต่อไปนี้

1. **ระบบชนิดข้อมูลที่เข้มงวด (Strong Typing)**: ภาษา C# กำหนดให้นักพัฒนาระบุชนิดของตัวแปรอย่างชัดเจน ระบบจะตรวจสอบความถูกต้องของชนิดข้อมูลในขั้นตอน Compile-time ทำให้สามารถค้นพบข้อผิดพลาดได้ตั้งแต่เนิ่น ๆ ก่อนที่โปรแกรมจะถูกนำไปประมวลผลจริง

2. **การประมวลผลแบบไม่ประสานเวลา (Async / Await)**: ภาษา C# รองรับการเขียนโปรแกรมแบบ Asynchronous ผ่าน Keyword `async` และ `await` ทำให้สามารถจัดการกับงาน I/O ได้อย่างมีประสิทธิภาพโดยไม่ต้อง Block Thread หลัก เหมาะสำหรับการพัฒนาระบบที่ต้องรองรับคำขอจำนวนมากพร้อมกัน เช่น การประมวลผลออเดอร์ในช่วงเวลาที่ร้านอาหารมีผู้ใช้บริการจำนวนมาก

3. **ระบบ LINQ (Language Integrated Query)**: ภาษา C# มีระบบ LINQ ที่ช่วยให้นักพัฒนาสามารถเขียนคำสั่งสอบถาม (Query) บนข้อมูลในรูปแบบที่ใกล้เคียงกับภาษา SQL ได้ภายในตัวภาษาเอง ทำให้การจัดการข้อมูลในหน่วยความจำและฐานข้อมูลมีความสะดวกและอ่านง่าย

4. **การเขียนโปรแกรมเชิงวัตถุครบรูปแบบ**: ภาษา C# รองรับหลักการเชิงวัตถุครบทั้ง 4 ข้อ ได้แก่ Encapsulation, Inheritance, Polymorphism และ Abstraction รวมถึงคุณสมบัติเพิ่มเติม เช่น Interface, Generic, Delegate และ Event ทำให้เหมาะกับการออกแบบสถาปัตยกรรมระบบที่มีความซับซ้อน เช่น ระบบ RBMS-POS ที่แบ่งเป็น 8 โมดูลธุรกิจ

## 2.8 ASP.NET Core 9.0

ASP.NET Core [12] คือเฟรมเวิร์กแบบโอเพนซอร์ส (Open-source) สำหรับการพัฒนาเว็บแอปพลิเคชันและบริการ Web API ที่พัฒนาโดยบริษัทไมโครซอฟท์ ทำงานบน .NET Runtime ที่รองรับการทำงานข้ามระบบปฏิบัติการได้ทั้ง Windows, macOS และ Linux เวอร์ชัน 9.0 เป็นเวอร์ชันที่นำเสนอประสิทธิภาพและคุณสมบัติใหม่ที่เหมาะสมกับการพัฒนา API สมัยใหม่ โดยรองรับการประมวลผลคำขอจำนวนมากพร้อมกัน (High Concurrency)

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ ASP.NET Core 9.0 ประกอบด้วย

1. **ประสิทธิภาพสูง (High Performance)**: ASP.NET Core ถูกออกแบบให้รองรับการประมวลผลแบบ Async/Await โดยตรง ทำให้สามารถรองรับคำขอจำนวนมากพร้อมกันได้อย่างมีประสิทธิภาพ เหมาะสำหรับระบบที่ต้องตอบสนองแบบเวลาจริง เช่น ระบบ RBMS-POS ที่ต้องส่งข้อมูลออเดอร์ไปยังครัวภายในเวลาน้อยกว่า 1 วินาที

2. **ระบบฉีดความสัมพันธ์ในตัว (Built-in Dependency Injection)**: เฟรมเวิร์กมาพร้อมระบบ Dependency Injection (DI) Container ในตัว ช่วยให้นักพัฒนาสามารถจัดการความสัมพันธ์ระหว่าง Service, Repository และ Controller ได้อย่างเป็นระบบ และส่งเสริมหลักการ SOLID เพื่อให้โค้ดมีความยืดหยุ่นและทดสอบง่าย

4. **รองรับการสร้าง API Documentation อัตโนมัติ**: ASP.NET Core สามารถผสาน OpenAPI (Swagger) เพื่อสร้างเอกสาร API ที่อัปเดตอัตโนมัติตามโค้ดได้ ลดภาระในการเขียนเอกสารด้วยมือและช่วยให้ทีมหน้าบ้านสามารถสร้างรหัสคำสั่งที่เชื่อมต่อ API ได้โดยอัตโนมัติ

## 2.10 SQL Server

SQL Server [14] คือระบบจัดการฐานข้อมูลเชิงสัมพันธ์ (Relational Database Management System หรือ RDBMS) ที่พัฒนาและบำรุงรักษาโดยบริษัทไมโครซอฟท์ ออกแบบมาเพื่อรองรับการจัดเก็บข้อมูลในระดับองค์กร (Enterprise) มีคุณสมบัติสำคัญในด้านความเสถียร ความปลอดภัย และประสิทธิภาพในการประมวลผลข้อมูลปริมาณมาก รองรับการประมวลผลธุรกรรม (Transaction) ที่มีความน่าเชื่อถือสูง

SQL Server รองรับภาษาคำสั่ง T-SQL (Transact-SQL) ซึ่งเป็นภาษาส่วนขยายของ SQL มาตรฐาน รวมถึงมีเครื่องมือเสริม เช่น SQL Server Management Studio (SSMS) สำหรับจัดการฐานข้อมูล และ Azure Data Studio สำหรับการพัฒนาแบบ Cross-platform นอกจากนี้ยังให้บริการในหลายรูปแบบ ตั้งแต่ Express Edition ที่ใช้งานได้ฟรีสำหรับโครงงานขนาดเล็ก ไปจนถึง Enterprise Edition สำหรับองค์กรขนาดใหญ่ ในระบบ RBMS-POS คณะผู้จัดทำใช้ SQL Server ในการจัดเก็บข้อมูลทั้งหมดของระบบ ครอบคลุมข้อมูลเมนูอาหาร พนักงาน ลูกค้า ออเดอร์ การชำระเงิน และบันทึกการแจ้งเตือน

## 2.11 SignalR

SignalR [15] คือไลบรารีโอเพนซอร์สสำหรับการสื่อสารแบบเวลาจริงระหว่างเซิร์ฟเวอร์และเครื่องลูกข่าย (Client) ที่พัฒนาโดยบริษัทไมโครซอฟท์ ออกแบบมาเพื่อรองรับการส่งข้อมูลแบบ Server-to-Client โดยอัตโนมัติ โดยไม่ต้องอาศัยการสอบถามซ้ำ ๆ จากฝั่ง Client (Polling) ซึ่งช่วยลดภาระของเซิร์ฟเวอร์และเพิ่มประสิทธิภาพการตอบสนอง

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ SignalR ประกอบด้วย

1. **การเลือก Transport อัตโนมัติ**: SignalR สามารถเลือก Transport ที่เหมาะสมที่สุดได้อัตโนมัติ ทั้ง WebSocket, Server-Sent Events (SSE) และ Long Polling โดย WebSocket เป็น Transport ที่ให้ประสิทธิภาพสูงสุด ส่วน SSE และ Long Polling จะถูกใช้เป็นทางเลือกสำรองเมื่อเครือข่ายไม่รองรับ WebSocket

2. **กลไกการเชื่อมต่ออัตโนมัติ (Automatic Reconnection)**: SignalR มีกลไกในการเชื่อมต่อใหม่อัตโนมัติเมื่อการเชื่อมต่อขาดหาย ช่วยให้ระบบสามารถทำงานต่อเนื่องได้แม้ในสภาวะเครือข่ายไม่เสถียร ซึ่งเหมาะกับการใช้งานในร้านอาหารที่อาจมีปัญหาสัญญาณ Wi-Fi ในบางช่วงเวลา

3. **ระบบ Group Management**: SignalR รองรับการแบ่งกลุ่มของ Client (Group) ทำให้สามารถส่งข้อมูลไปยังกลุ่มผู้ใช้งานที่กำหนดได้อย่างเฉพาะเจาะจง เช่น การส่งออเดอร์ใหม่ไปเฉพาะหน้าจอครัว หรือการแจ้งเตือนชำระเงินไปเฉพาะแคชเชียร์

4. **รูปแบบการเขียนแบบ Hub**: SignalR ใช้รูปแบบ Hub ที่ทำให้การเรียกเมธอดข้ามฝั่ง (Client-to-Server หรือ Server-to-Client) มีความเป็นธรรมชาติเหมือนการเรียกเมธอดในโค้ดปกติ ช่วยลดความซับซ้อนของการเขียนรหัสคำสั่งสำหรับการสื่อสารแบบเวลาจริง

ในการพัฒนาระบบนี้ คณะผู้จัดทำใช้ SignalR ในการแจ้งเตือนออเดอร์ใหม่ไปยังครัว แจ้งสถานะอาหารพร้อมเสริฟไปยังหน้าร้าน และซิงโครไนซ์ข้อมูลโต๊ะแบบเวลาจริงระหว่างหน้าจอทุกอุปกรณ์ ผ่าน OrderHub และ NotificationHub ที่กล่าวถึงในหัวข้อ 2.4

(ที่มา: https://learn.microsoft.com/en-us/aspnet/core/signalr/)

## 2.12 JSON Web Token (JWT) และ BCrypt

JSON Web Token (JWT) [16] คือมาตรฐานเปิด (RFC 7519) สำหรับการสร้าง Token ที่ใช้แลกเปลี่ยนข้อมูลระหว่างระบบในรูปแบบ JSON ที่มีการลงนามด้วย Digital Signature เพื่อยืนยันความถูกต้องของข้อมูล มาตรฐานนี้นิยมใช้ในการยืนยันตัวตน (Authentication) ของระบบเว็บแอปพลิเคชันสมัยใหม่ โดย Token จะถูกส่งกลับให้ Client หลังจากการยืนยันตัวตนสำเร็จ และ Client จะแนบ Token นี้ในทุกคำขอถัดไป

BCrypt [17] คืออัลกอริทึมการแฮชรหัสผ่าน (Password Hashing Algorithm) ที่ออกแบบมาให้มีความต้านทานต่อการโจมตีแบบ Brute Force ผ่านการเพิ่มค่า Cost Factor ที่ปรับได้ ทำให้ใช้เวลาในการคำนวณนานพอที่จะป้องกันการเดารหัสผ่านด้วยคอมพิวเตอร์ความเร็วสูง อัลกอริทึมนี้ยังผสาน Salt แบบสุ่มเข้ากับรหัสผ่านในกระบวนการแฮช ซึ่งป้องกันการโจมตีด้วย Rainbow Table ได้อย่างมีประสิทธิภาพ

ในการพัฒนาระบบนี้ คณะผู้จัดทำใช้ JWT ร่วมกับ Refresh Token สำหรับการจัดการ Session ของพนักงานในระบบ และใช้ BCrypt ในการเข้ารหัสรหัสผ่านก่อนจัดเก็บลงฐานข้อมูล เพื่อให้แน่ใจว่ารหัสผ่านของผู้ใช้งานจะไม่ถูกเปิดเผยแม้ในกรณีที่ฐานข้อมูลถูกเข้าถึงโดยไม่ได้รับอนุญาต

[ใส่รูปที่ 2.7 สัญลักษณ์ JSON Web Token]
(ที่มา: https://jwt.io/)

## 2.13 ภาษา TypeScript

ภาษา TypeScript [18] คือภาษาโปรแกรมระดับสูงแบบโอเพนซอร์สที่พัฒนาและบำรุงรักษาโดยบริษัทไมโครซอฟท์ ภาษา TypeScript ถูกสร้างขึ้นโดยการเพิ่มระบบการกำหนดชนิดข้อมูลแบบสถิต (Static Typing) เข้าไปในภาษาจาวาสคริปต์ (JavaScript) และมีสถานะเป็น "ซูเปอร์เซตแบบเคร่งครัดทางไวยากรณ์" (Strict Syntactical Superset) ของภาษาจาวาสคริปต์ ซึ่งหมายความว่ารหัสคำสั่งใด ๆ ที่เขียนด้วยภาษาจาวาสคริปต์ได้อย่างถูกต้องจะถือว่าเป็นโปรแกรม TypeScript ที่ถูกต้องด้วยเช่นกัน

คุณสมบัติและหลักการทำงานที่สำคัญของภาษา TypeScript ประกอบด้วย

1. **กระบวนการแปลงรหัสคำสั่ง (Transcompilation)**: เนื่องจากสภาพแวดล้อมการประมวลผลทั่วไปไม่สามารถอ่านภาษา TypeScript ได้โดยตรง รหัสคำสั่งจะต้องผ่านกระบวนการแปลงเป็นภาษาจาวาสคริปต์มาตรฐานก่อน จึงจะสามารถนำไปประมวลผลได้ทั้งในฝั่ง Client (เว็บเบราว์เซอร์) และฝั่ง Server (Node.js)

2. **การระบุชนิดข้อมูลและตรวจสอบขณะคอมไพล์ (Type Annotations and Compile-time Type Checking)**: นักพัฒนาสามารถระบุชนิดของตัวแปร พารามิเตอร์ และค่าส่งกลับของฟังก์ชันได้อย่างชัดเจน ซึ่งระบบจะตรวจสอบในขั้นตอน Compile-time ช่วยให้สามารถค้นพบข้อผิดพลาดได้ก่อนการนำไปใช้งานจริง ลดความเสี่ยงของ Runtime Error ในระบบขนาดใหญ่

3. **การรองรับโครงสร้างขั้นสูง (Advanced Types and OOP Features)**: ภาษา TypeScript ได้เพิ่มคุณสมบัติระดับสูง เช่น Interface, Enum, Generics, Namespace และ Tuple เพื่อช่วยให้การจัดโครงสร้างซอร์สโค้ดมีระเบียบและง่ายต่อการบำรุงรักษา เหมาะสำหรับโครงการขนาดใหญ่ที่มีการพัฒนาในทีมหลายคน

## 2.14 เฟรมเวิร์ก Angular 19.1

Angular [19] คือเฟรมเวิร์กสำหรับการพัฒนาเว็บแอปพลิเคชันแบบ Single Page Application (SPA) ที่พัฒนาและบำรุงรักษาโดยบริษัท Google เขียนด้วยภาษา TypeScript และใช้รูปแบบสถาปัตยกรรมแบบ Component-Based ที่แบ่งหน้าเว็บออกเป็นชิ้นส่วนย่อยที่สามารถนำกลับมาใช้ใหม่ได้

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ Angular ประกอบด้วย

1. **สถาปัตยกรรมแบบ Component-Based**: Angular แบ่งหน้าเว็บออกเป็น Component ย่อย ๆ ที่สามารถนำกลับมาใช้ใหม่ได้ ทำให้การพัฒนาและบำรุงรักษามีความเป็นระบบ และง่ายต่อการทดสอบแยกเป็นส่วน

2. **Angular Signals (Reactive State)**: Angular เวอร์ชันใหม่ได้เพิ่มระบบ Signals ที่เป็นกลไกการจัดการสถานะแบบ Reactive ทำให้การปรับปรุงหน้าเว็บเมื่อข้อมูลเปลี่ยนแปลงมีประสิทธิภาพสูงขึ้น โดย Component ที่อ้างอิงสัญญาณจะถูก Re-render เฉพาะเมื่อค่าของสัญญาณเปลี่ยนแปลงจริงเท่านั้น

3. **ระบบ Dependency Injection**: Angular มีระบบ DI ในตัวที่ช่วยให้สามารถจัดการความสัมพันธ์ระหว่าง Service และ Component ได้อย่างเป็นระบบ ช่วยให้สามารถแยกตรรกะทางธุรกิจออกจากการแสดงผลได้อย่างชัดเจน

4. **ระบบจัดการเส้นทาง (Routing) แบบ Lazy Load**: Angular รองรับการแบ่ง Feature Module ที่โหลดเมื่อจำเป็น (Lazy Loading) ทำให้แอปพลิเคชันมีความเร็วในการเริ่มต้น ในระบบ RBMS-POS คณะผู้จัดทำใช้กลไกนี้ในการแยกโมดูล Admin และ Mobile Web ออกจากกัน

## 2.16 เฟรมเวิร์ก Tailwind CSS

Tailwind CSS [21] คือเฟรมเวิร์ก CSS แบบโอเพนซอร์สที่ใช้แนวคิด Utility-First ออกแบบมาเพื่อช่วยให้นักพัฒนาและนักออกแบบส่วนติดต่อผู้ใช้งานสามารถสร้างหน้าเว็บได้อย่างรวดเร็วโดยการประกอบ Class ย่อยที่มีหน้าที่เฉพาะ (เช่น `bg-blue-500`, `p-4`, `text-center`) เข้าไปในโครงสร้าง HTML โดยไม่ต้องเขียนไฟล์ CSS แยกต่างหาก

จุดเด่นและหลักการทำงานที่สำคัญของ Tailwind CSS ประกอบด้วย

1. **สถาปัตยกรรมแบบเน้นอรรถประโยชน์ (Utility-First Architecture)**: Tailwind CSS เตรียม Class ย่อยจำนวนมากให้นักพัฒนานำมาประกอบเข้ากับ HTML โดยตรง ทำให้สามารถสร้าง UI ที่มีรูปแบบเฉพาะตัวได้อย่างอิสระ โดยไม่ต้องเขียน CSS ที่ซ้ำซ้อน

2. **ความสม่ำเสมอของการออกแบบ (Design Consistency)**: Tailwind CSS มีการกำหนดค่ามาตรฐานสำหรับระบบสี (Color Palette) ระยะห่าง (Spacing) และขนาดตัวอักษร (Typography) ไว้เป็นระบบ ช่วยควบคุมให้การแสดงผลในทุกหน้าจอเป็นไปในทิศทางเดียวกัน

3. **กระบวนการคอมไพล์แบบ JIT (Just-In-Time)**: Tailwind CSS รองรับการคอมไพล์เฉพาะ Class ที่ใช้งานจริง ทำให้ขนาดไฟล์ CSS สุดท้ายมีขนาดเล็ก เหมาะสำหรับการ Deploy บน Production ที่ต้องการประสิทธิภาพในการโหลดหน้าเว็บ

## 2.18 Docker และ Docker Compose

Docker [23] คือแพลตฟอร์มสำหรับการสร้างและจัดการคอนเทนเนอร์ (Container) ที่ช่วยให้นักพัฒนาสามารถแพ็คเกจแอปพลิเคชันและ Dependencies ทั้งหมดไว้ในคอนเทนเนอร์เดียว ทำให้สามารถ Deploy ระบบในสภาพแวดล้อมที่หลากหลายได้โดยไม่ต้องกังวลเรื่องความแตกต่างของระบบปฏิบัติการหรือไลบรารีที่ติดตั้ง คอนเทนเนอร์ของ Docker ทำงานในรูปแบบที่เบากว่า Virtual Machine แบบดั้งเดิม โดยใช้ทรัพยากรร่วมกันกับระบบปฏิบัติการแม่

Docker Compose เป็นเครื่องมือเสริมที่ใช้ในการจัดการคอนเทนเนอร์หลายตัวพร้อมกันผ่านไฟล์ YAML ทำให้สามารถกำหนด Dependencies และความสัมพันธ์ระหว่างคอนเทนเนอร์ได้อย่างเป็นระบบ ในการพัฒนาระบบนี้ คณะผู้จัดทำใช้ Docker Compose ในการจัดการบริการ SQL Server และ MinIO ในสภาพแวดล้อมการพัฒนา ทำให้สมาชิกในทีมสามารถเริ่มต้นการพัฒนาได้ทันทีโดยไม่ต้องติดตั้งเครื่องมือเหล่านี้ในเครื่องของตนเอง

## 2.19 Swagger / OpenAPI

Swagger / OpenAPI [24] คือมาตรฐานเปิดสำหรับการอธิบาย Web API ในรูปแบบ JSON หรือ YAML ที่ช่วยให้นักพัฒนาสามารถสร้างเอกสาร API ที่อ่านได้ทั้งโดยมนุษย์และเครื่องจักร เครื่องมือในชุด Swagger ประกอบด้วย Swagger UI สำหรับแสดงเอกสาร API บนเว็บบราวเซอร์ในรูปแบบ Interactive ที่ทดสอบการเรียก API ได้โดยตรง และ Swagger Codegen สำหรับสร้างโค้ดของ Client โดยอัตโนมัติ

นอกจากนี้ ระบบยังใช้เครื่องมือ ng-openapi-gen [25] ซึ่งเป็น Code Generator ที่อ่านเอกสาร OpenAPI Specification แล้วสร้าง TypeScript Client สำหรับ Angular โดยอัตโนมัติ ทำให้ลดเวลาในการเขียนโค้ดเชื่อมต่อ API ฝั่งหน้าบ้าน และช่วยให้ฝั่งหน้าบ้านได้รับ Type ที่ตรงกับ API ที่หลังบ้านกำหนดไว้เสมอ ในระบบ RBMS-POS ที่มี Endpoint จำนวนประมาณ 215 จุด การใช้ Code Generator ช่วยลดความผิดพลาดที่อาจเกิดจากการเขียน Client ด้วยมือได้อย่างมีนัยสำคัญ
