# Module 5: Table (จัดการโต๊ะ + ผังร้าน + การจองโต๊ะ + QR Code)

> Master Data Module — เป็นแหล่งข้อมูลของ "พื้นที่ขาย" ที่ระบบใช้ + เป็นจุดเริ่มต้นของลูกค้า Self-Order ผ่าน QR

---

## 1. Module นี้คืออะไร

ระบบจัดการโต๊ะของร้านอาหารทั้งหมด ครอบคลุม:

| ส่วน | ทำอะไร |
| --- | --- |
| **Zone (โซน)** | แบ่งพื้นที่ร้านเป็นโซน เช่น "ชั้น 1", "ระเบียง", "ห้อง VIP" |
| **Table (โต๊ะ)** | โต๊ะแต่ละตัวพร้อมตำแหน่ง ขนาด ความจุ และ QR Code |
| **Floor Object (วัตถุประดับ)** | สิ่งที่ไม่ใช่โต๊ะแต่อยู่ในผัง เช่น ห้องน้ำ บันได เคาน์เตอร์ ครัว ทางออก แคชเชียร์ ต้นไม้ |
| **Floor Plan (ผังร้าน)** | หน้าจอวางโต๊ะแบบ Drag & Drop |
| **Table Link (เชื่อมโต๊ะ)** | รวมหลายโต๊ะเป็นกลุ่มเดียว (สำหรับลูกค้ามาเป็นกลุ่มใหญ่) |
| **Reservation (จองโต๊ะ)** | ระบบจองโต๊ะล่วงหน้าพร้อม Calendar View |
| **QR Code Self-Order** | ทุกโต๊ะมี QR Code ให้ลูกค้าสแกนสั่งอาหารเอง |

## 2. ช่วยธุรกิจร้านอาหารในเรื่องใด

| ปัญหาแบบดั้งเดิม | สิ่งที่ระบบนี้แก้ |
| --- | --- |
| ผังร้านในกระดาษ — เปลี่ยนผังที ต้องวาดใหม่ | Drag & Drop วางโต๊ะในระบบ ดูเรียลไทม์ |
| ลูกค้ามา ไม่รู้ว่าโต๊ะไหนว่าง ต้องเดินตรวจ | สีโต๊ะแสดงสถานะ (ว่าง/มีลูกค้า/รอบิล/จอง/ปิดใช้) บนหน้าจอ |
| จองโต๊ะผ่านโทรศัพท์ → ลืม, จดผิดวัน | ระบบจองในระบบ + Calendar + แจ้งเตือนล่วงหน้า |
| ลูกค้ามาเป็นกลุ่มใหญ่ ต้องรวมโต๊ะ → บิลรวมยุ่งยาก | Link Table ในระบบ → ออเดอร์ Merge เป็นบิลเดียวอัตโนมัติ |
| ลูกค้านั่งแล้วเรียกพนักงาน → เสียเวลา | QR Code ที่โต๊ะ → ลูกค้าสั่งอาหารเองได้ |
| โต๊ะไม่ใช้งาน (เสีย/ปิดปรับปรุง) ลูกค้าเข้าไปนั่ง → ปวดหัว | Set Unavailable → ระบบไม่ให้เปิดโต๊ะ |
| ปิดบิลแล้วโต๊ะยังขึ้นว่าง — พนักงานยังไม่ทำความสะอาด | สถานะ "Cleaning" บังคับให้พนักงานยืนยันก่อนเปิดให้ลูกค้าใหม่ |

**คุณค่าทางธุรกิจ**: เห็นภาพรวมร้านบนหน้าจอเดียว + รองรับการจอง + เปิดทางให้ Self-Order + ลดเวลาในการบริการ

## 3. Business Logic หลัก

### 3.1 สถานะของโต๊ะ (Table Status)

| สถานะ | สี | ความหมาย | เปลี่ยนจาก |
| :---: | :---: | --- | --- |
| **Available** | เทา | โต๊ะว่าง พร้อมใช้งาน | (เริ่มต้น) / Cleaning / Reserved cancel |
| **Reserved** | ฟ้า | มีการจอง (ยังไม่มาถึง) | Available → พนักงานกด "ยืนยันการจอง + assign โต๊ะ" (Manual) |
| **Occupied** | ส้ม | มีลูกค้านั่งอยู่ (Order Open) | Available → กดเปิดโต๊ะ |
| **Billing** | เหลือง | ลูกค้าขอบิลแล้ว (รอชำระ) | Occupied → ลูกค้าขอบิล |
| **Cleaning** | น้ำตาล | ปิดบิลแล้ว รอทำความสะอาด | Billing/Occupied → ปิดโต๊ะ/Move |
| **Unavailable** | แดง | โต๊ะปิดใช้งาน (เสีย/ปิดปรับปรุง) | Available → กด Set Unavailable |

### 3.2 ขนาดและความจุของโต๊ะ

```
ETableSize
├── Small      (2 ที่นั่ง)
├── Medium     (4 ที่นั่ง — ค่าเริ่มต้น)
├── Large      (6 ที่นั่ง)
└── ExtraLarge (8+ ที่นั่ง)
```

> Capacity เก็บแยกได้ — ถ้าโต๊ะใหญ่กว่าปกติ ระบุตัวเลขจริง

### 3.3 QR Token (สำหรับ Self-Order)

ทุกโต๊ะมี QR Code ที่เปลี่ยนทุกครั้งที่เปิดโต๊ะ — เก็บใน 3 ฟิลด์:
- `QrToken` — JWT-like token อายุ 12 ชั่วโมง (Claims: tableId, nonce, exp)
- `QrTokenNonce` — random nonce กันการ replay attack
- `QrShortCode` — URL สั้น สำหรับ QR ที่เครื่อง print

**Flow:**
1. เปิดโต๊ะ → ระบบ generate QR Token ใหม่ + Short Code (ทุกครั้งจะแตกต่างกัน)
2. พนักงานพิมพ์ QR ติดที่โต๊ะ → ลูกค้าสแกน → ลิงก์ไป Mobile Web
3. ปิดโต๊ะ → QR Token หมดอายุทันที (Revoke) → สแกนใหม่ใช้ไม่ได้

### 3.4 Table Link (เชื่อมโต๊ะ)

ลูกค้ามาเป็นกลุ่มใหญ่ (10+ คน) → ต้องรวม 3-4 โต๊ะ → Link Tables:
- พนักงานเลือก 2+ โต๊ะ → กด "เชื่อมโต๊ะ"
- ระบบสร้าง GroupCode → โต๊ะทั้งหมดอยู่ในกลุ่มเดียว
- Order ของทั้งกลุ่ม **Merge** เป็นบิลเดียว
- รายการอาหารบันทึก SourceTableId เก็บไว้ว่ามาจากโต๊ะไหนเดิม
- เลิก Link → ออเดอร์แยกกลับเป็นแต่ละโต๊ะ (ใช้ SourceTableId)

### 3.5 Reservation (การจอง)

```
สถานะการจอง (EReservationStatus)
├── Pending      (รอยืนยัน — ลูกค้าจองมาแต่ยังไม่จัดโต๊ะ)
├── Confirmed    (ยืนยัน + assign โต๊ะแล้ว)
├── CheckedIn    (ลูกค้ามาถึง + เปิดโต๊ะ)
├── Cancelled   (ยกเลิก)
└── NoShow      (ลูกค้าไม่มา)
```

**กฎการจอง:**
1. ห้ามจองวันย้อนหลัง
2. ตอนยืนยัน (Confirm) → ต้อง assign TableId + ตรวจช่วงเวลา ±2 ชั่วโมง ไม่ชนกับการจองอื่นในโต๊ะเดียวกัน
3. Check-in → เปิดโต๊ะอัตโนมัติ (Reserved → Occupied) + ระบุ GuestType = Reserved
4. Cancel / NoShow → ปล่อยโต๊ะกลับเป็น Available

### 3.6 Floor Object (วัตถุประดับ)

วัตถุที่อยู่ในผังร้านแต่ไม่ใช่โต๊ะ — `EFloorObjectType` มี 8 ประเภท:
- **Restroom** (ห้องน้ำ), **Stairs** (บันได), **Counter** (เคาน์เตอร์), **Kitchen** (ครัว), **Exit** (ทางออก), **Cashier** (จุดแคชเชียร์), **Plant** (ต้นไม้), **Decoration** (อื่นๆ)
- เก็บ `PositionX`/`PositionY` (double — ตำแหน่งในผัง) + `Label` (ป้ายชื่อ)
- ขนาดและรูปร่างถูก preset ฝั่ง Frontend ตาม type — DB ไม่เก็บ Width/Height/Rotation
- เชื่อมกับ Zone ได้ (ZoneId optional) — ไม่ผูกกับ Order

## 4. Workflow การทำงานจริง

### Workflow A — Setup ผังร้านครั้งแรก

```
1. /table/zones → "เพิ่มโซน"
   ─ ชื่อโซน: "ชั้น 1", "ระเบียง", "ห้อง VIP"
   ─ Drag เรียงลำดับโซน
2. /table/zones → เข้าโซน "ชั้น 1" → "เพิ่มโต๊ะ"
   ─ ชื่อโต๊ะ: "A1", "A2", ... → ขนาด Medium + ความจุ 4
   ─ Drag วางในตำแหน่ง (PositionX, PositionY)
3. /table/floor-plan → เห็นผังร้านจริง
4. เพิ่ม Floor Object (เสา/ฉากกั้น) → Drag วางในผัง
5. บันทึก → ระบบเก็บตำแหน่งทุกโต๊ะ + Floor Object
```

### Workflow B — ลูกค้ามาที่ร้าน (เปิดโต๊ะ)

```
1. พนักงานเสิร์ฟ → /order/overview เห็นผังร้าน Real-time
2. ลูกค้ามา 4 คน → เลือกโต๊ะ "A3" (สีเทา = Available)
3. กดโต๊ะ → Dialog เปิดขึ้น
   ─ GuestCount: 4
   ─ GuestType: Walk-in
4. กด "เปิดโต๊ะ" → ระบบ:
   ─ สร้าง Order ใหม่ผูกกับ TableId
   ─ เปลี่ยนสถานะโต๊ะ → Occupied
   ─ Generate QR Token + Short Code ใหม่
   ─ ผูก ActiveOrderId กับโต๊ะ
   ─ broadcast SignalR "TableStatusChanged"
5. พนักงานพิมพ์ QR Code → เอาให้ลูกค้าสแกน
```

### Workflow C — ลูกค้ามาเป็นกลุ่มใหญ่ (Link Tables)

```
1. ลูกค้ามา 12 คน → ต้องรวม 3 โต๊ะ (A3, A4, A5)
2. พนักงาน → เปิดโต๊ะ A3 ก่อน (เป็น Anchor)
3. กด "เชื่อมโต๊ะ" → เลือก A4, A5
4. ระบบสร้าง GroupCode (เช่น "GRP001")
   ─ A3, A4, A5 อยู่ในกลุ่มเดียว
   ─ ActiveOrderId ของทั้ง 3 โต๊ะ → ออเดอร์เดียวกัน
5. ลูกค้าสั่งอาหารที่โต๊ะ A4 → บันทึก SourceTableId = A4
6. ปิดบิล → บิลเดียวรวมทุกโต๊ะ
7. (ถ้าต้องการแยก) → กด "เลิกเชื่อม" → ออเดอร์แยกกลับเป็นแต่ละโต๊ะตาม SourceTableId
```

### Workflow D — ลูกค้าจองโต๊ะล่วงหน้า

```
1. ลูกค้าโทรมาจองวันที่ 15 มิ.ย. 19:00 น. 6 คน
2. พนักงาน → /table/reservations → "เพิ่มการจอง"
   ─ ชื่อลูกค้า + เบอร์โทร
   ─ วันเวลา: 15 มิ.ย. 19:00
   ─ จำนวนคน: 6
   ─ หมายเหตุ: "โต๊ะริมหน้าต่าง"
3. บันทึก → สถานะ Pending
4. วันที่จอง — พนักงาน → กด "ยืนยัน" → เลือกโต๊ะ "B2" (Large)
   ─ ระบบเช็ค ±2 ชั่วโมง ไม่ชนกับการจองอื่นในโต๊ะ B2 → OK
   ─ สถานะ Confirmed + B2 เปลี่ยนเป็น Reserved (ฟ้า)
5. ลูกค้ามาถึง → กด "Check-In"
   ─ ระบบ: เปิดโต๊ะ B2 + สร้าง Order + สถานะ Occupied (ส้ม)
   ─ GuestType = Reserved
6. (กรณีลูกค้าไม่มา) → กด "No Show" → ปล่อยโต๊ะกลับเป็น Available
```

### Workflow E — ลูกค้าสแกน QR สั่งอาหารเอง

```
1. ลูกค้านั่งที่โต๊ะ A3 → สแกน QR ที่ติดโต๊ะ
2. QR ลิงก์ไป → https://shop.example.com/q/{shortCode}
3. ระบบ Redirect → Mobile Web: /auth?token={qrToken}
4. ลูกค้าตั้งชื่อเล่น → เริ่มดูเมนู
5. (รายละเอียดดูที่ Order Module - Self-Order)
```

### Workflow F — ปิดโต๊ะหลังลูกค้ากลับ

```
1. ลูกค้าชำระเงินเสร็จ → Payment Module ปิด Order = Completed + เปลี่ยนโต๊ะเป็น Cleaning
2. พนักงานทำความสะอาดเสร็จ → กด "ทำความสะอาดเสร็จ" (API /clean)
3. ระบบ:
   ─ Revoke QR Token (สแกนไม่ได้แล้ว)
   ─ Clear ActiveOrderId
   ─ เปลี่ยนสถานะ → Available (เทา)
4. โต๊ะพร้อมรับลูกค้าใหม่
```

> **กรณีที่ปิดโต๊ะแบบไม่มีออเดอร์** (เช่น กดปิดโต๊ะที่ Available อยู่แล้ว หรือยกเลิกการเปิด): API `/close` จะข้าม Cleaning ไป Available โดยตรง

### Workflow G — ย้ายโต๊ะ (Move)

```
1. ลูกค้าที่โต๊ะ A1 ขอย้ายไป A5 (โต๊ะใหญ่กว่า)
2. พนักงาน → กด "ย้ายโต๊ะ" จาก A1 → เลือก A5 (ต้อง Available)
3. ระบบ:
   ─ ย้าย Order จาก A1 → A5
   ─ A1 → Cleaning
   ─ A5 → Occupied + สืบทอด GuestCount, GuestType
   ─ Generate QR Token ใหม่สำหรับ A5
```

## 6. ข้อเสีย / ข้อจำกัด

| ข้อจำกัด | ผลกระทบ + วิธีรับมือ |
| --- | --- |
| **Floor Object ไม่มี Width/Height** | ขนาดของเสา/ฉากกั้น ถูก preset จาก type — ปรับขนาดเองไม่ได้ |
| **โต๊ะ 1 ตัวอยู่ Group Link ได้แค่ 1 group** | ไม่รองรับการเชื่อมซ้อน |
| **±2 ชั่วโมงตายตัว** | กฎตรวจชนของจอง — ร้านที่จัดเลี้ยงนาน 4 ชั่วโมงต้องปรับ |
| **ไม่มี Auto-Reserved** | ระบบไม่เปลี่ยนสถานะเป็น Reserved ก่อนเวลาจองอัตโนมัติ — ต้องกดยืนยันเอง |
| **QR Token อายุ 12 ชั่วโมง** | ลูกค้าที่นั่งนานๆ (เช่น 13 ชม.) จะ token หมดอายุ — ต้องสแกนใหม่ |
| **Unlink ไม่ Atomic** | ถ้าออเดอร์ซับซ้อน (split bill แล้ว link/unlink) อาจสับสน — ควรทำตอน Order ยังไม่ split |
| **ไม่มี Wait List** | ลูกค้าที่รอ — ระบบไม่มีคิว ต้องจัดการเองนอกระบบ |
| **โต๊ะ Move ไม่เก็บ Audit ละเอียด** | รู้ว่าย้ายไปไหน แต่ไม่มี history หลายขั้น |
| **ไม่ Auto-Cleaning Timeout** | ถ้าพนักงานลืมกด "ทำความสะอาดเสร็จ" → โต๊ะค้างสถานะ Cleaning |
| **ไม่มีระบบแจ้งลูกค้าจอง** | ระบบไม่ส่ง SMS/Email ยืนยันการจอง — ต้องโทรหาเอง |

## 7. ความสัมพันธ์กับ Module อื่น

### Module นี้ส่งข้อมูลไปให้ใคร

| Module ปลายทาง | ส่งอะไรไป | ใช้ทำอะไร |
| --- | --- | --- |
| **Order** | TableId + GuestCount + ActiveOrderId | สร้าง Order ผูกกับโต๊ะ |
| **Order (Self-Order)** | QrToken | ตรวจ token ลูกค้าสแกน → สร้าง CustomerSession |
| **Notification** | TableId + สถานะ | broadcast TableStatusChanged ไปกลุ่ม "floor" |
| **Dashboard** | ข้อมูลโต๊ะ (capacity, status) | ใช้ใน analytics (ถ้ามี) |
| **Payment** | TableId | แสดงในใบเสร็จ |

### Module นี้ดึงข้อมูลจากใคร

| Module ต้นทาง | ดึงอะไรมา | ใช้ทำอะไร |
| --- | --- | --- |
| **Order** | ActiveOrderId | รู้ว่าโต๊ะมีออเดอร์ที่ active อยู่ |
| **Order** | UnservedItemCount, TotalActiveItemCount | คำนวณ sub-status (รอเสิร์ฟ / เสิร์ฟครบ) |
| **Authorization** | สิทธิ์ผู้ใช้ | ตรวจว่าใครจัดการโต๊ะได้ |
| **Notification** | Permission ของผู้รับ | ส่งแจ้งเตือนการจองล่วงหน้า (ถ้ามี Background Service) |

## 8. สรุปสำหรับรายงาน (1 ย่อหน้า)

> Module Table เป็นระบบจัดการพื้นที่ขายของร้านอาหารที่ครบวงจร ตั้งแต่การออกแบบผังร้านแบบ Drag & Drop ผ่าน Floor Plan ที่รองรับทั้งโต๊ะและวัตถุประดับ (เสา, ฉากกั้น, ทางเดิน) การจัดกลุ่มโต๊ะเป็นโซน การติดตามสถานะของแต่ละโต๊ะแบบ Real-time ผ่าน 6 สถานะ (ว่าง/มีลูกค้า/รอบิล/จองแล้ว/รอทำความสะอาด/ปิดใช้งาน) ระบบการจองโต๊ะล่วงหน้าพร้อม Calendar View ที่ตรวจชนของจองอัตโนมัติ ความสามารถในการเชื่อมโต๊ะ (Link Tables) สำหรับลูกค้ากลุ่มใหญ่ที่ทำให้ออเดอร์รวมเป็นบิลเดียวได้ และที่สำคัญที่สุดคือการสร้าง QR Code อายุ 12 ชั่วโมงสำหรับทุกโต๊ะ ทำให้ลูกค้าสามารถสแกน QR สั่งอาหารเองผ่าน Mobile Web (Self-Order) ได้ทันที ลดภาระงานของพนักงานเสิร์ฟ และเป็นรากฐานของระบบ Order/Payment ทั้งหมด
