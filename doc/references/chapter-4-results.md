## 1. ภาพรวมเนื้อหาบทที่ 4

บทที่ 4 เป็นบทที่อธิบาย **"ผลการทดสอบระบบ"** ว่าระบบทำงานได้ตามที่ออกแบบหรือไม่ โดยใช้ **Screenshot + ตารางผลการทดสอบ**

**สองตัวอย่างใช้รูปแบบต่างกันชัดเจน**:

### 🎯 ตัวอย่างที่ 2 (Primary) — Test Case Table แบบมีรหัส ⭐

**โครงสร้างของแต่ละการทดสอบ**:
1. **ย่อหน้าเปิดของระบบ** — บอกว่าทดสอบอะไร
2. **ตารางผลการทดสอบ** — มีรหัส Test (เช่น MEM-01, CRT-01), สิ่งที่ต้องการทดสอบ, ผลคาดหวัง, ผลจริง, สรุปผล (รัน 3 ครั้ง)
3. **Screenshot ของแต่ละ Test Case** — ตามรหัส (รูปที่ 4.X — รหัสตรงกับ Test Code)

### 📋 ตัวอย่างที่ 1 (Secondary) — Step-by-Step แบบยาว

**โครงสร้างของแต่ละการทดสอบ**:
1. ย่อหน้าวัตถุประสงค์
2. กรณีทดสอบที่ 1.1, 1.2, ... ระบุขั้นตอนเป็น "1. ... ดังแสดงในรูปที่ X.Y"
3. ตารางผลการทดสอบ (ครั้งที่ 1-5)
4. ย่อหน้าสรุปผล

**📌 คำแนะนำสำหรับ RBMS-POS**: ใช้รูปแบบของตัวอย่างที่ 2 (Test Case Table แบบมีรหัส) เป็นหลัก เพราะ:
- กระชับ อ่านง่าย
- มี traceability (รหัสตรงกับ Screenshot)
- มีคอลัมน์ "ผลคาดหวัง vs ผลจริง" ที่ชัดเจน
- เหมาะกับรายงานเชิงวิศวกรรม

> | MEM-03 | ล็อกอินด้วยรหัสผ่านผิด | ระบบปฏิเสธการเข้าถึงและแจ้งเตือนรหัสผ่านผิด | ระบบแสดงข้อความ "อีเมลหรือรหัสผ่านไม่ถูกต้อง" | ผ่าน | ผ่าน | ผ่าน |

**สังเกต Pattern (สำคัญมาก!)**:

#### โครงสร้างคอลัมน์ (5+ คอลัมน์):
1. **รหัส** — Test Code รูปแบบ "{PREFIX}-{NN}" (3 ตัวอักษร + ตัวเลข 2 หลัก)
2. **สิ่งที่ต้องการทดสอบ** — Action ที่ทำ (เช่น "กรอกข้อมูลสมัครสมาชิกครบถ้วน")
3. **ผลลัพธ์ที่คาดหวัง** — Expected Result (เน้นเชิงเทคนิค: "บันทึกลงฐานข้อมูล", "แจ้งสำเร็จ")
4. **ผลลัพธ์ที่ได้จากการทดสอบ** — Actual Result (ละเอียดกว่าผลคาดหวัง: ระบุข้อความที่แสดงจริง)
5. **สรุปผล 1, 2, 3** — **รัน 3 ครั้ง** แต่ละครั้งระบุ "ผ่าน" / "ไม่ผ่าน"

#### Prefix ของ Test Code:
- **MEM-XX** = Member (สมาชิก)
- **CRT-XX** = Cart (ตะกร้า)
- **PAY-XX** = Payment (ชำระเงิน)
- **ADM-XX** = Admin (หลังบ้าน)
- **PRF-XX** = Profile (ข้อมูลส่วนตัว)
- **REP-XX** = Report (รายงาน)
- **PCB-XX** = PC Builder (จัดสเปค)

## 6. กลยุทธ์การจัดการ Screenshot

### 6.1 จำนวน Screenshot ที่ต้องเตรียม

- **เฉลี่ย 1 Screenshot ต่อ 1 Test Case** (ตามตัวอย่างที่ 2)
- **เฉลี่ย 5 Screenshot ต่อระบบ**
- **รวม ~50 Screenshot สำหรับ 10 ระบบ**

### 6.2 หลักการจัดเรียงรูป

- **Caption สั้น**: "รูปที่ 4.X {Test Code}" หรือ "รูปที่ 4.X {Test Code}: {คำอธิบาย}"
- รูปต้องชัด อ่านข้อความได้
- ไม่ใส่ข้อมูลส่วนตัวจริง (ใช้ test data)
- ลำดับเลขรูปต่อเนื่องตลอดบท (4.1, 4.2, ..., 4.50)

### 6.3 ขนาดและคุณภาพ

- ขนาด: ครอบครึ่งหน้า A4 (ประมาณ 14-16 cm กว้าง)
- รูป Desktop: ครอบหน้าจอแบบ Full ไม่ตัด UI
- รูป Mobile (Self-Order): ใช้ Device Frame หรือ Browser DevTools mobile view (375×667px)
- ใส่ caption ใต้รูปทุกครั้ง "รูปที่ 4.X ..."

### 6.4 หลักการ Caption

#### Option A: Caption สั้นมาก (ตามตัวอย่างที่ 2)
- "รูปที่ 4.1 AUTH-01"
- "รูปที่ 4.2 AUTH-02"

#### Option B: Caption ปานกลาง (ผสมระหว่าง 2 ตัวอย่าง)
- "รูปที่ 4.1 AUTH-01: หน้าจอการเข้าสู่ระบบของ Owner"
- "รูปที่ 4.2 AUTH-02: หน้าจอ Dashboard หลังเข้าสู่ระบบสำเร็จ"

**คำแนะนำ**: ใช้ Option B เพื่อความชัดเจน แต่อย่ายาวเกิน 12 คำ

## 7. Pattern ย่อหน้าเปิดของแต่ละระบบทดสอบ

### 🎯 ตัวอย่างที่ 2 (สั้นมาก)
> "4.1 การทดสอบและผลการทดสอบของระบบจัดการสมาชิก
>
> ตารางที่ 4.1 แสดงผลการทดสอบการทำงานในส่วนของการสมัครสมาชิกและการเข้าสู่ระบบ"

**Pattern**: 1 บรรทัด introduction + bridge ไปสู่ตารางทันที — **ไม่มีย่อหน้าวัตถุประสงค์ยาวๆ**

### 📋 ตัวอย่างที่ 1 (ยาวกว่า — ตัวเลือก)
> "การทดลองนี้มีวัตถุประสงค์เพื่อตรวจสอบความถูกต้องของการเข้าสู่ระบบ (Login) ตลอดจนการตรวจสอบสิทธิ์การเข้าถึง (Authorization) เพื่อให้มั่นใจว่าระบบสามารถคัดกรอง ยืนยันตัวตน..."

**คำแนะนำสำหรับ RBMS-POS**: ใช้ **Hybrid** — 1-2 บรรทัดอธิบายวัตถุประสงค์ของระบบนั้น แล้วต่อด้วยตารางทันที

```markdown
4.6 การทดสอบและผลการทดสอบของระบบ Self-Order ผ่าน QR Code

ตารางที่ 4.6 แสดงผลการทดสอบการสั่งอาหารด้วยตนเองโดยลูกค้าผ่าน QR Code
```

## 8. Pattern Test Result ที่ครอบคลุม Edge Cases

### Pattern สำหรับระบบที่มี Edge Case ซับซ้อน (เช่น Payment + OCR)

```markdown
ตารางที่ 4.8 แสดงผลการทดสอบระบบรับชำระเงินและ OCR Slip Verification

| รหัส | สิ่งที่ต้องการทดสอบ | ผลลัพธ์ที่คาดหวัง | ผลลัพธ์ที่ได้จากการทดสอบ | สรุปผล 1 | สรุปผล 2 | สรุปผล 3 |
|------|---------------------|---------------------|---------------------------|----------|----------|----------|
| PAY-01 | ชำระด้วยเงินสด ระบุยอด 100 บาท ลูกค้าให้ 200 บาท | ระบบคำนวณเงินทอน 100 บาท และบันทึก Payment สถานะ Paid | คำนวณเงินทอนถูกต้อง และเปลี่ยนสถานะ Order เป็น Completed | ผ่าน | ผ่าน | ผ่าน |
| PAY-02 | อัปโหลดสลิป QR Promtpay ที่ยอดตรง | OCR อ่านยอดได้ และเปรียบเทียบกับยอดบิล (Matched) | ESlipVerificationStatus = Matched และเปลี่ยน Payment Status เป็น Paid | ผ่าน | ผ่าน | ผ่าน |
| PAY-03 | อัปโหลดสลิปที่ยอดไม่ตรง | ESlipVerificationStatus = Mismatched และไม่อนุมัติอัตโนมัติ | ระบบแสดงข้อความเตือน "ยอดไม่ตรง" และให้แคชเชียร์ตรวจสอบมือ | ผ่าน | ผ่าน | ผ่าน |
| PAY-04 | อัปโหลดสลิปที่ OCR อ่านไม่ได้ (ภาพเบลอ) | ESlipVerificationStatus = Manual และให้แคชเชียร์ระบุยอดเอง | ระบบแสดงสถานะ "ตรวจสอบมือ" และให้กรอกยอดในฟอร์ม | ผ่าน | ผ่าน | ผ่าน |
| PAY-05 | Split Bill แยกตามรายการ (2 บิล) | ระบบสร้าง 2 OrderBill แยกกัน และคำนวณยอดถูกต้อง | สร้าง 2 บิล ยอด 350 + 250 = 600 ตรงกับยอดรวม | ผ่าน | ผ่าน | ผ่าน |
| PAY-06 | Unsplit Bill หลังจาก Split (ก่อนชำระ) | ระบบรวม 2 บิลกลับเป็นบิลเดียว | บิลเดิมหายไป มีบิลรวม 1 ใบ ยอด 600 บาท | ผ่าน | ผ่าน | ผ่าน |
```

**สังเกต**:
- Test Code แสดง **Happy Path → Edge Case → Failure Case** ตามลำดับ
- ผลคาดหวังระบุ **เชิงเทคนิค** (สถานะ enum, ค่าในฟิลด์)
- ผลจริงระบุ **เชิงผลลัพธ์** (ข้อความที่แสดง, การเปลี่ยนแปลงในระบบ)

```markdown
จากผลการทดสอบในตารางที่ 4.6 แสดงให้เห็นว่าระบบ Self-Order ผ่าน QR Code สามารถ
```

## 10. Checklist ก่อนเขียนจริง

### เตรียมข้อมูล
- [ ] กำหนด Test Code Prefix ของแต่ละ Module (AUTH/MEN/HR/TBL/ORD/SOR/KDS/PAY/CSH/NTF)
- [ ] กำหนด Test Cases อย่างน้อย **3 cases ต่อระบบ** (รวม happy path + edge + failure)
- [ ] เตรียม test data ที่สะอาด (ไม่มีข้อมูลส่วนตัวจริง)
- [ ] ตรวจ State Machine ของ Order/OrderItem ให้ผ่านทุก transition
- [ ] ตรวจ Permission Matrix ของแต่ละ Role
- [ ] ทดสอบ OCR ทั้ง 4 สถานะ (None/Matched/Mismatched/Manual)
- [ ] เตรียม Screenshot ~50 รูป

### ระหว่างเขียน
- [ ] ตารางทุกตารางต้องมี **5+ คอลัมน์**: รหัส, สิ่งที่ทดสอบ, ผลคาดหวัง, ผลจริง, สรุปผล 1-3
- [ ] เลขรูปต่อเนื่องตลอดบท (4.1 → 4.50)
- [ ] เลขตารางต่อเนื่อง (4.1 → 4.10)
- [ ] ใส่ Caption สั้นแต่ชัดเจน "รูปที่ 4.X TEST-CODE" หรือ "รูปที่ 4.X TEST-CODE: คำอธิบาย"
- [ ] ใช้ "ผ่าน" / "ไม่ผ่าน" ในคอลัมน์สรุปผล (ไม่ใช่ ✓ / ✗ — เพื่อ Word compatibility)
- [ ] **รัน 3 ครั้ง** สำหรับแต่ละ Test Case → ใส่ในคอลัมน์สรุปผล 1, 2, 3

### หลังเขียน
- [ ] ตรวจคำแปลภาษาไทยให้สอดคล้องกับ `writing-style-guide.md`
- [ ] ตรวจสอบว่า Screenshot คมชัด อ่านข้อความได้ทุกตัว
- [ ] ตรวจสอบ Test Code ตรงกับรูปประกอบทุกตัว
- [ ] หากใส่ย่อหน้าสรุปผล ให้เน้น **value ของระบบ** ไม่ใช่ feature

## 11. ความต่างจากตัวอย่างที่ 1

| ประเด็น | ตัวอย่างที่ 1 | ตัวอย่างที่ 2 (Primary) | RBMS-POS ใช้แบบไหน |
|---------|---------------|--------------------------|---------------------|
| Test Format | Step-by-Step + รูปแต่ละ step | Test Case Table + 1 รูปต่อ case | **แบบ 2 (Primary)** |
| จำนวนรูปต่อ Test | 3-5 รูป | 1 รูป | **1 รูป** (กระชับ) |

## 12. หมายเหตุ — บางครั้งใช้ Pattern ผสม

หาก Test Case ใดมีความซับซ้อนสูง (เช่น Multi-Device Bill Claim) สามารถใช้ **Pattern ผสม**:
1. ใช้ Test Case Table แบบหลัก (เป็นแกน)
2. ขยาย Test Case นั้นด้วย **Step-by-Step + รูปประกอบเพิ่ม** ใต้ตาราง

```markdown
รายละเอียดเพิ่มเติมของ SOR-04 (Multi-Device Block):

  1. เปิดมือถือเครื่องที่ 1 และสแกน QR Code ของโต๊ะ 5
     ระบบสร้าง Token A และอนุญาตให้เข้าหน้าสั่งอาหาร
     ดังแสดงในรูปที่ 4.X
  [รูปที่ 4.X การเข้าหน้าสั่งอาหารของเครื่องที่ 1]

  2. เปิดมือถือเครื่องที่ 2 (ลูกค้าอีกคน) และสแกน QR Code เดียวกัน
     ระบบตรวจสอบ Bill Claim Token พบว่ามี Token A อยู่แล้ว
     จึงปฏิเสธการสร้าง Token ใหม่ ดังแสดงในรูปที่ 4.X+1
  [รูปที่ 4.X+1 ข้อความปฏิเสธบนเครื่องที่ 2]
```

**คำแนะนำ**: ใช้ Step-by-Step เฉพาะกับ Test Case ที่สำคัญ/ซับซ้อน — ไม่ใช่ทุก Test Case
