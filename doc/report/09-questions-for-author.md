### B. ที่มาและจุดประสงค์ (สำหรับ 1.1 + 1.2)

#### B.1 แรงบันดาลใจ (1.1 ย่อหน้า 1)
- เคยทำงานพาร์ทไทม์ในร้านอาหารและเห็นความวุ่นวาย
- สังเกตจากการไปกินข้าวเองว่าระบบสั่งอาหารบางที่ช้ามาก/ผิดบ่อย

#### B.2 ปัญหาที่ต้องการแก้ (1.1 ย่อหน้า 2)
1. ลูกค้ารอนานเพราะต้องเรียกพนักงานจดเมนู
2. พนักงานจดออเดอร์กระดาษ → ครัวอ่านไม่ออก/ตก
3. ตรวจสลิปโอนด้วยตาเปล่า → ช้า + พลาดง่าย
4. แยกบิลลูกค้ากลุ่ม → คำนวณซับซ้อน
5. ใช้ระบบ POS เดิมที่ราคาแพง/ไม่ยืดหยุ่น
- **แก่นแกน**: อยากยกระดับธุรกิจร้านอาหารให้นำเทคโนโลยีมาใช้บริหาร

#### B.3 จุดเด่นที่เน้นในรายงาน (1.2 + 1.4)
1. **Self-Order ผ่าน QR Code**
2. **SignalR Real-time**
3. **OCR ตรวจสลิป**
4. **ความยืดหยุ่นในการนำไปใช้กับร้านหลายขนาด**

#### B.4 คู่แข่งในตลาดที่ศึกษา (1.1 ย่อหน้า 1)
- **FoodStory** (POS ของไทย — ถูก LINE MAN Wongnai ซื้อกิจการแล้ว, เน้น Inventory + Loyalty)

### F. ปัญหาและการแก้ไข (สำหรับ 5.3)

#### F.1 ปัญหาเทคนิคที่เจอ (4 ข้อหลัก)

1. **SignalR Reconnection ตอน Network หลุด**
   - จอค้าง ไม่อัพเดตอัตโนมัติ
   - แก้ด้วย: เพิ่ม Automatic Reconnection + Initial Fetch หลังเชื่อมต่อใหม่

2. **iOS ใช้ SignalR ไม่ได้** (มือถือ Samsung/Android ใช้ได้)
   - สถานะไม่อัพเดต Real-time บน iOS
   - **แก้แล้ว** (ระบุในรายงานว่า "แก้ด้วย X" — ยังรอผู้ใช้ระบุวิธีแก้ที่แท้จริง)

3. **OCR Slip — สลิปบางธนาคารอ่านผิด**
   - font/layout ไม่เป็นมาตรฐาน
   - แก้ด้วย: เพิ่มสถานะ Manual Verification เป็น Fallback

4. **Multi-Device Race Condition**
   - ลูกค้าใช้ QR เดียวกันจากหลายมือถือ
   - แก้ด้วย: Bill Claim Token แบบ Exclusive Lock

#### F.2 ฟีเจอร์ที่ตัดออกระหว่างพัฒนา
1. **ระบบจัดการ Stock** — เยอะ ยุ่งยากเกินกับการสร้างเมนูแบบ Dynamic
2. **Customer Loyalty Program** (รีวิวร้าน + สะสมแต้ม) — ต้องเก็บข้อมูลเยอะ
3. **การเชื่อมต่อ Hardware จริง** (เครื่องพิมพ์สลิป) — งบเกิน

#### F.3 ความเสี่ยงในการนำไปใช้จริง (5.3 มุมธุรกิจ)
1. ค่าใช้จ่ายเริ่มต้น (Hardware + ติดตั้ง)
2. ความซับซ้อนในการเรียนรู้การทำงานของระบบ
3. ปัญหา Internet ในพื้นที่ (ร้านที่ Wi-Fi ไม่ดี)

### H. รูปแบบและสำนวน (สำหรับทุกบท)

#### H.1 Citation Style (ยืนยันแล้ว 2026-05-31)
- ใช้ **Thai APA + [N]** (รูปแบบไทยที่ใช้เลข [N] เป็นตัวอ้างอิง)
- ยืนยันรูปแบบจากตัวอย่างปริญญานิพนธ์ที่ผู้ใช้แนบมา (ภาพเอกสารอ้างอิง)
- **รูปแบบรายการ**:
  ```
  [N] ชื่อผู้แต่ง. (ปี พ.ศ. / ม.ป.ป.). ชื่อบทความ/หน้าเว็บ. เข้าถึงเมื่อ [วัน เดือน ปี พ.ศ.].
      เข้าถึงได้จาก [URL]
  ```
- **กฎสำคัญ**:
  - ใช้ปี **พ.ศ.** (เช่น 2569) — ค.ศ. ใช้เฉพาะ Wikipedia
  - ถ้าไม่ระบุปี ใช้ **(ม.ป.ป.)** = ไม่ปรากฏปีที่พิมพ์
  - บรรทัด URL **ย่อหน้าเข้า 4 ช่อง** (indent)
  - "เข้าถึงเมื่อ" + "เข้าถึงได้จาก" เป็นภาษาไทย

#### H.2 รูปแบบรายงาน
- เขียนแบบมาตรฐานทั่วไปก่อน
- รอตัวอย่างจากสถาบันเพื่อปรับ Margin / Font / Spacing

### I. เชิงธุรกิจ (สำหรับ 1.1 + 1.4 + 5.2 + 5.4)

#### I.1 Value Proposition (1.1 ย่อหน้า 2 + 5.2)
1. **ลดเวลารับ Order และส่งครัว** จาก X นาที เหลือ Y วินาที
2. **ลดความผิดพลาดในการสื่อสารระหว่างหน้าร้านและครัวลงอย่างมีนัยสำคัญ** (ปรับจาก "เป็นศูนย์")
3. **ระบบเดียวจัดการได้ครบ** ไม่ต้องใช้หลายระบบแยกกัน
4. **ลดแรงงานพนักงานเสริฟลง X%** ผ่าน Self-Order

> **หมายเหตุ**: ตัวเลข X, Y เป็นการคาดการณ์ — ใส่ในรายงานพร้อมระบุ "คาดการณ์ตามสถาปัตยกรรม"

#### I.2 สิ่งที่ลูกค้า (ร้านอาหาร) ต้องลงทุน (5.4)
1. Hardware: PC/Tablet สำหรับแคชเชียร์ + ครัว + เสริฟ
2. Network: Wi-Fi ที่เสถียร
3. Server / Cloud: ต้องเช่า

#### I.3 ผลกระทบเชิงปริมาณ (1.4 + 5.2)
- AI คำนวณจากสถาปัตยกรรมโค้ดปัจจุบัน + คาดการณ์ตามทฤษฎี
- ระบุชัดในรายงานว่า "คาดการณ์ มิใช่ผลทดสอบจริง"

#### I.4 Decision Maker (1.1 ย่อหน้า 3)
- **เจ้าของร้าน** (ร้านเล็ก-กลาง)
- **สิ่งที่เจ้าของร้านสนใจหลัก**: ความเสถียร (ระบบไม่ล่มในช่วง peak)
- AI สามารถเสริมประเด็นรอง (ROI, ใช้งานง่าย, ราคา) ได้ตามบริบท

#### I.5 วิสัยทัศน์ 3-5 ปี (5.4)
- เป็น Product ที่ขายได้จริง มีร้านใช้งาน
- พร้อม Open Source Community ที่มีคนช่วยพัฒนาต่อ
