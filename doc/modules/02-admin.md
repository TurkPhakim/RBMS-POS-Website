# Module 2: Admin (ระบบหลังบ้าน + ตั้งค่าร้าน + ผู้ใช้งาน + แดชบอร์ด)

> Foundation Module ลำดับที่ 2 — รวมบริการพื้นฐานที่ทุก Module พึ่งพา (ล็อกอิน, ตั้งค่าร้าน, ค่าบริการ, ผู้ใช้งาน, แดชบอร์ด, ระบบไฟล์)

---

## 1. Module นี้คืออะไร

Module Admin คือกลุ่มของบริการพื้นฐาน (Shared Services) ที่ทุกระบบในร้านต้องใช้ — ไม่ได้เป็นหน้าจอเดียวแต่เป็นชุดของฟีเจอร์ 7 ส่วน:

| ฟีเจอร์ย่อย | ทำอะไร |
| --- | --- |
| **Authentication** | ล็อกอิน, ออกจากระบบ, ลืมรหัสผ่าน, เปลี่ยนรหัสผ่าน, PIN Code |
| **User Management** | จัดการบัญชีผู้ใช้ของพนักงาน (ปลดล็อค, ตั้งสถานะ) |
| **Shop Settings** | ตั้งค่าข้อมูลร้าน (ชื่อร้าน, โลโก้, QR ชำระเงิน, ธนาคาร, PromptPay, WiFi) |
| **Operating Hours** | กำหนดเวลาเปิด-ปิดร้าน 7 วัน |
| **Service Charge** | ค่าบริการ (Service Charge เปอร์เซ็นต์) |
| **Dashboard** | ภาพรวมยอดขาย + เมนูขายดี + ช่วงเวลายอดนิยม |
| **File Management** | จัดเก็บไฟล์รูปภาพ (เมนู, โลโก้, QR, รูปพนักงาน, สลิป) บน MinIO/S3 |

## 2. ช่วยธุรกิจร้านอาหารในเรื่องใด

| ปัญหาแบบดั้งเดิม | สิ่งที่ระบบนี้แก้ |
| --- | --- |
| ใครก็เปิดระบบใช้ได้ ไม่มีตัวตน ตรวจสอบไม่ได้ | บังคับล็อกอิน + บันทึกทุกการกระทำว่าใครทำ |
| ลืมรหัสผ่าน ต้องไปขอเจ้าของร้านตั้งใหม่ | ระบบ Forgot Password + OTP ผ่านอีเมล จัดการเองได้ |
| พนักงานคนเดิม login ค้าง ทำงานบนเครื่องคนอื่น → ใครก็ใช้ได้ | บัญชี Auto-lock เมื่อกรอกผิดเกินกำหนด + ระบบ PIN สำหรับงานที่ทำซ้ำบ่อย |
| ค่าบริการเปลี่ยนตามเทศกาล/วันธรรมดา-สุดสัปดาห์ | ตั้ง Service Charge ได้หลายชุด พร้อมช่วงวันที่ใช้ |
| เปลี่ยนเวลาเปิด-ปิดร้านต้องเปลี่ยนหลายที่ (ป้าย, Google Maps, ระบบ) | ตั้งครั้งเดียวที่นี่ → ระบบ Self-Order รู้ว่าร้านปิดอัตโนมัติ |
| เจ้าของร้านไม่รู้ภาพรวมยอดขาย ต้องนับเงินทุกเย็น | Dashboard สรุปยอดขาย/เมนูขายดี/ช่วงเวลาขายดี Real-time |
| รูปภาพเมนูใหญ่เก็บในเซิร์ฟเวอร์เปลือง disk | ใช้ Object Storage (S3/MinIO) แยก — ขยายเก็บได้ไม่จำกัด |

**คุณค่าทางธุรกิจ**: ระบบพื้นฐานที่ปลอดภัย + ตั้งค่าได้ยืดหยุ่น + เจ้าของร้านเห็นภาพรวมยอดขายตลอดเวลา + ลดงานธุรการประจำวัน

## 3. Business Logic หลัก

### 3.1 Authentication (การล็อกอิน)

**กฎการล็อกอิน:**
1. ต้องยืนยัน reCAPTCHA ก่อน (ป้องกัน bot โจมตี)
2. ตรวจ Username + Password (Hash ด้วย BCrypt)
3. ตรวจสถานะบัญชี:
   - ถ้า `IsActive = false` → บัญชีถูกปิด ห้ามเข้า
   - ถ้า `IsLockedByAdmin = true` → ผู้ดูแลล็อค (ต้องรอวันปลดล็อค หรือให้ผู้ดูแลปลด)
   - ถ้า `LockedUntil > เวลาปัจจุบัน` → ถูกล็อคจากการกรอกผิดบ่อย
4. ถ้ารหัสถูก → ออก JWT Access Token (อายุ 1 ชั่วโมง) + Refresh Token (7 วัน, ถ้าติ๊ก "จดจำฉัน" = 30 วัน)
5. ส่งรายการสิทธิ์ของพนักงานมาด้วยพร้อม Token

**กฎการ Auto-Lock บัญชี (ป้องกัน brute force):**

| ครั้งที่ถูกล็อค | เกณฑ์ครั้งที่กรอกผิด | ระยะเวลาล็อค |
| :---: | :---: | :---: |
| ครั้งที่ 1 | 3 ครั้ง | 1 นาที |
| ครั้งที่ 2 | 5 ครั้ง | 3 นาที |
| ครั้งที่ 3 | 7 ครั้ง | 5 นาที |
| ครั้งที่ 4 | 9 ครั้ง | 7 นาที |
| ครั้งที่ N | 2N + 1 ครั้ง | 2N - 1 นาที |

> เกณฑ์ค่อยๆ เพิ่ม ไม่ใช่เพิ่มแบบลงโทษเกินไป — เพราะพนักงานบางคนพิมพ์ผิดบ่อย

### 3.2 Forgot Password Flow

1. กรอก Username/อีเมล → ระบบส่ง OTP 6 หลักไปอีเมล (อายุ 3 นาที)
2. ผู้ใช้กรอก OTP → ระบบออก "Reset Token" (อายุ 30 นาที)
3. ใส่ Reset Token + รหัสผ่านใหม่ → ระบบตรวจว่ารหัสใหม่ไม่ซ้ำกับ **3 รหัสล่าสุด** (Password History)
4. บันทึก + ล็อก attempts รหัสผ่านเก่าใน TbPasswordHistory
5. OTP เก่าทั้งหมดถูก invalidate ทันที (กันการใช้ OTP เก่า)

### 3.3 PIN Code

PIN 6 หลักสำหรับยืนยันตัวตนซ้ำในงานที่ต้องการความปลอดภัย เช่น:
- เปิดลิ้นชักเงิน (Cash Drawer)
- ปิดรอบขายของแคชเชียร์
- แก้ไขรายการที่ส่งครัวแล้ว

**กฎ PIN:**
- ต้องตั้ง PIN ครั้งแรกในหน้า Profile
- เปลี่ยน PIN ต้องยืนยัน PIN เดิมก่อน
- ลืม PIN → ใช้รหัสผ่านยืนยันเพื่อรีเซ็ต PIN
- PIN เก็บแบบ Hash (BCrypt) เหมือนรหัสผ่าน

### 3.4 Shop Settings (ตั้งค่าร้าน — Singleton)

- มีแค่ **1 record** ในระบบ (Singleton Pattern)
- เก็บข้อมูล: ชื่อร้านไทย/อังกฤษ, ที่อยู่, เลขประจำตัวผู้เสียภาษี, ประเภทอาหาร, อีเมล
- **Branding**: โลโก้ร้าน, QR ชำระเงิน (รูป)
- **ข้อมูลธนาคาร**: เลขบัญชี, ชื่อบัญชี (สำหรับให้ลูกค้าโอน)
- **WiFi**: SSID + Password (แสดงให้ลูกค้าเห็นใน Mobile Web)
- **PromptPay**: เบอร์โทร/เลขประจำตัวผู้เสียภาษีของร้าน (ใช้ตรวจสอบสลิปลูกค้าด้วย OCR)
- **เวลาทำการ**: เก็บแยกอีก 7 record (จันทร์-อาทิตย์) แต่ละวันมี: เปิดหรือไม่, เวลาช่วงที่ 1, เวลาช่วงที่ 2 (รองรับร้านที่ปิดช่วงพักกลางวัน)

### 3.5 Service Charge

- มีหลาย record ได้ (เช่น "ค่าบริการ 10% วันธรรมดา", "ค่าบริการ 15% วันเสาร์-อาทิตย์")
- แต่ละ Service Charge มี **ช่วงวันที่ใช้งาน** (StartDate / EndDate) + สถานะ Active
- ใช้ในตอนปิดบิล (Order Module ดึงไปคำนวณ)

### 3.6 User Management

- รายชื่อพนักงานที่มีบัญชีในระบบ
- ปลดล็อคบัญชีพนักงาน (ในกรณีที่ Auto-Lock ค้าง)
- เปลี่ยนสถานะ Active/Inactive
- **ไม่ใช่หน้าสร้างบัญชีโดยตรง** — บัญชีถูกสร้างผ่านหน้า Human Resource (สร้าง User Account จากข้อมูลพนักงาน)

### 3.7 Dashboard

แสดงภาพรวมยอดขาย — 4 รายงาน:
1. **Overview**: KPI วันนี้ vs เมื่อวาน (ยอดขาย, จำนวนออเดอร์, จำนวนลูกค้า, ยอดเฉลี่ย/ออเดอร์) + กราฟแนวโน้ม 7/30 วัน
2. **Top Selling**: Top 5 เมนูขายดีแยกประเภท (อาหาร/เครื่องดื่ม/ของหวาน)
3. **Peak Hours**: ช่วงเวลาขายดีของวัน (จำนวนออเดอร์ต่อชั่วโมง 0-23)
4. **Sales Report**: รายงานยอดขายช่วงเวลา (ระบุ from-to ได้สูงสุด 365 วัน)

> ดึงข้อมูลจาก TbOrderBill (Status=Paid), TbOrderItem (ไม่รวม Voided/Cancelled), TbOrder

### 3.8 File Management

- ใช้ Object Storage (MinIO/S3) เก็บไฟล์รูป
- ในฐานข้อมูลเก็บแค่ **metadata** (FileName, MimeType, Size, S3Key)
- ใช้ร่วมกันโดย Menu (รูปเมนู), HumanResource (รูปพนักงาน), ShopSettings (โลโก้/QR), Order (สลิป)
- การอัพโหลด: API หลัก (Menu/HR/ShopSettings) เรียก FileService อัพโหลด → ได้ FileId → เก็บ FileId ใน entity หลัก

## 4. Workflow การทำงานจริง

### Workflow A — พนักงานเปิดร้านตอนเช้า

```
1. พนักงานเปิดเบราว์เซอร์ → /auth/login
2. กรอก Username/Password + ผ่าน reCAPTCHA → กดเข้าสู่ระบบ
3. ระบบส่ง JWT Token + รายการสิทธิ์
4. Redirect ไปหน้า Welcome → เห็นโลโก้ร้านและชื่อร้าน (ดึงจาก ShopSettings)
5. Sidebar แสดงเมนูตามสิทธิ์ของตำแหน่งงาน
```

### Workflow B — พนักงานลืมรหัสผ่าน

```
1. หน้า Login → กด "ลืมรหัสผ่าน"
2. กรอก Username/อีเมล → ระบบส่ง OTP 6 หลักไปอีเมล (3 นาที)
3. กรอก OTP → ระบบออก Reset Token (30 นาที)
4. ตั้งรหัสผ่านใหม่ → ระบบเช็คว่าไม่ซ้ำ 3 รหัสล่าสุด
5. รหัสใหม่บันทึก + กลับไปหน้า Login
```

### Workflow C — เจ้าของร้านตั้งค่าร้านใหม่

```
1. เข้าเมนู "ตั้งค่าร้าน" (admin-setting/shop-settings)
2. กรอกข้อมูล: ชื่อร้านไทย/อังกฤษ, ที่อยู่, เลขประจำตัวผู้เสียภาษี
3. อัพโหลดโลโก้ร้าน + QR ชำระเงิน (.png) → ระบบเก็บใน MinIO
4. ตั้งเวลาเปิด-ปิดร้าน 7 วัน (เช่น จันทร์-ศุกร์: 11:00-22:00, เสาร์-อาทิตย์: 10:00-23:00)
5. กรอกเลขบัญชีธนาคาร + เบอร์ PromptPay + WiFi (SSID+Password)
6. บันทึก → ระบบใช้ข้อมูลนี้ทั่วระบบ (Header, ใบเสร็จ, Mobile Web ลูกค้า, OCR ตรวจสลิป)
```

### Workflow D — เจ้าของร้านดู Dashboard ตอนปิดร้าน

```
1. เข้าเมนู "Dashboard" → /dashboard
2. ระบบแสดง:
   - ยอดขายวันนี้: 25,400 บาท (เทียบเมื่อวาน +12%)
   - จำนวนออเดอร์: 87 ออเดอร์ (เทียบเมื่อวาน +5%)
   - จำนวนลูกค้า: 156 คน (ยอดเฉลี่ย 163 บาท/คน)
   - กราฟแนวโน้มยอดขาย 7 วันย้อนหลัง
   - กราฟสัดส่วนยอดขาย: อาหาร 60% / เครื่องดื่ม 30% / ของหวาน 10%
   - กราฟช่วงเวลาขายดี (Peak Hours)
3. ดู "เมนูขายดี" → กดเข้า /dashboard/sales เพื่อดูรายงานช่วงเวลายาว
4. เลือกช่วงวันที่ → ดูยอดเปรียบเทียบ + breakdown ตามหมวด
```

### Workflow E — ตั้งค่า Service Charge สำหรับช่วงเทศกาล

```
1. เข้าเมนู "ค่าบริการ" → /admin-setting/service-charges
2. กด "เพิ่มค่าบริการใหม่"
3. กรอก: ชื่อ "ค่าบริการเทศกาลปีใหม่ 12%", อัตรา 12%
4. ตั้งช่วงวันที่: 24 ธ.ค. 2026 - 2 ม.ค. 2027
5. เปิด Active → บันทึก
6. ในช่วงวันที่กำหนด → API `/dropdown` จะคืนค่า Service Charge นี้ในรายการที่เลือกได้ตอนแคชเชียร์ปิดบิล (แคชเชียร์เลือกเอง)
```

## 5. ข้อดี

| ข้อดี | คำอธิบาย |
| --- | --- |
| **ปลอดภัยตามมาตรฐาน** | JWT + Refresh Token + BCrypt + reCAPTCHA + Auto-Lock — ปลอดภัยตามมาตรฐาน OWASP |
| **เก็บไฟล์แยกไม่ปลอดภัยที่เซิร์ฟเวอร์** | ใช้ S3/MinIO เก็บภาพ ขยายได้ง่าย กู้คืนได้ |
| **Singleton ShopSettings ไม่ซ้ำ** | ข้อมูลร้านที่ "เป็นความจริงเดียว" — เปลี่ยนที่นี่ ระบบทั้งหมดใช้ค่าใหม่ |
| **Service Charge รองรับช่วงเวลา** | ตั้งล่วงหน้าได้พร้อม StartDate/EndDate — API `/dropdown` กรองเฉพาะที่ Active และอยู่ในช่วงวันที่ปัจจุบัน |
| **Dashboard Real-time** | ไม่ต้องส่งออก Excel มานับเอง — เห็นทันที |
| **Forgot Password ทำเองได้** | ไม่ต้องรอเจ้าของร้าน — พนักงานจัดการได้ผ่านอีเมล |
| **Password History** | บังคับเปลี่ยนรหัสจริง (กันใช้ของเดิม) |
| **PIN Code สำหรับงานเฉพาะ** | ไม่ต้องกรอกรหัสยาวๆ ทุกครั้ง — ใส่ PIN 6 หลักพอ |

## 6. ข้อเสีย / ข้อจำกัด

| ข้อจำกัด | ผลกระทบ + วิธีรับมือ |
| --- | --- |
| **อีเมลต้องใช้ได้จริง** | ระบบ Forgot Password พึ่งอีเมล — ถ้าพนักงานไม่มีอีเมล หรืออีเมลใช้ไม่ได้ ต้องให้เจ้าของร้านรีเซ็ตเอง |
| **OTP 3 นาทีอาจสั้นเกินไป** | บางครั้งอีเมลส่งช้า → ผู้ใช้ต้องขอ OTP ใหม่ |
| **เวลาทำการ 2 ช่วง/วันเท่านั้น** | ร้านที่เปิด 3 ช่วงต่อวัน (เช่น เช้า-กลางวัน-เย็น) ต้องเลือกเปิดแค่ 2 ช่วง |
| **MinIO ต้องดูแลแยก** | ไฟล์เก็บใน MinIO ถ้า MinIO ล่ม → รูปทั้งหมดหาย ต้องสำรองข้อมูลด้วย |
| **Dashboard นับจาก OrderBill (Status=Paid) เท่านั้น** | บิลที่ยังไม่ Paid (รอชำระ) ยังไม่นับ — เจ้าของร้านต้องเข้าใจตัวเลข |
| **Service Charge ห้ามทับซ้อนกัน** | ในช่วงวันที่หนึ่งควรมี Service Charge Active เดียว — ถ้ามีหลายตัว ระบบเสนอตัวแรกที่เจอ |
| **ปลดล็อคบัญชีจากเจ้าของร้านมีดีเลย์** | ถ้าพนักงานติดล็อค ต้องรอเจ้าของร้านเข้ามา unlock — ในร้านที่เจ้าของไม่อยู่อาจเสียเวลา |
| **PIN ลืม ต้องรีเซ็ตด้วยรหัสผ่าน** | ถ้าลืมทั้งคู่ ต้องผ่าน Forgot Password ก่อน |

## 7. ความสัมพันธ์กับ Module อื่น

### Module นี้ส่งข้อมูลไปให้ใคร

| Module ปลายทาง | ส่งอะไรไป | ใช้ทำอะไร |
| --- | --- | --- |
| **ทุก Module** | JWT Token (UserId, EmployeeId, PositionId) | ตรวจตัวตน + ตรวจสิทธิ์ |
| **Authorization** | UserId ของผู้ล็อกอิน | หาว่าสิทธิ์อะไรบ้าง |
| **Order** | Service Charge (ของช่วงวันที่ปัจจุบัน) | ใช้คำนวณยอดบิล |

## 8. สรุปสำหรับรายงาน (1 ย่อหน้า)

> Module Admin เป็นกลุ่มของบริการพื้นฐานที่ทุกระบบใน RBMS-POS ต้องใช้ ประกอบด้วยระบบยืนยันตัวตน (Authentication ด้วย JWT + BCrypt + reCAPTCHA), การจัดการบัญชีผู้ใช้พร้อมระบบล็อคอัตโนมัติเมื่อกรอกรหัสผิดเกินกำหนด, ระบบ Forgot Password ผ่านอีเมล OTP, การตั้งค่าข้อมูลร้านแบบ Singleton ที่รวมข้อมูลร้าน-เวลาทำการ-โลโก้-QR ชำระเงิน-ข้อมูลธนาคาร-WiFi-PromptPay, การจัดการค่าบริการ (Service Charge) ที่รองรับการกำหนดช่วงวันที่ใช้งาน, แดชบอร์ดสรุปยอดขายและเมนูขายดีแบบ Real-time, และระบบจัดเก็บไฟล์รูปภาพบน Object Storage (MinIO/S3) ซึ่งช่วยให้ร้านอาหารมีรากฐานการทำงานที่ปลอดภัย ยืดหยุ่นในการปรับเปลี่ยน และเห็นภาพรวมธุรกิจได้ตลอดเวลา
