# บทที่ 5 บทสรุปผล

> เนื้อหาพร้อมใช้ — ใช้การบรรยายเชิงคุณภาพแทนตัวเลขเชิงปริมาณ เนื่องจากไม่ได้ทำ Load Test จริง

---

ในบทนี้เป็นการสรุปผลการดำเนินงาน อภิปรายผล ปัญหาและอุปสรรคในการดำเนินงาน วิธีแก้ปัญหา รวมถึงข้อเสนอแนะสำหรับโครงงานระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS ซึ่งมีรายละเอียดดังนี้

---

## 5.1 สรุปผลการดำเนินงาน

จากการพัฒนาระบบ พบว่าระบบสามารถทำงานได้ครบถ้วนตามขอบเขตที่กำหนดไว้ โดยแบ่งผลการดำเนินงานออกเป็นส่วนหลักดังนี้

- **ส่วนของผู้ดูแลระบบ (Admin)**: สามารถจัดการเมนูอาหาร หมวดหมู่และตัวเลือกเสริม ตำแหน่งงานพร้อมสิทธิ์การเข้าถึงผ่าน Permission Matrix แบบไดนามิก ข้อมูลพนักงานพร้อมประวัติส่วนตัว โต๊ะและผังร้านแบบ Drag-and-Drop รวมถึงการเรียกดู Dashboard และรายงานยอดขาย

- **ส่วนของพนักงาน (Staff)**: สามารถรับออเดอร์ที่โต๊ะ จัดการสถานะรายการอาหารผ่าน State Machine ที่มี 7 สถานะ จัดการสถานะโต๊ะ จองโต๊ะและผูกโต๊ะของลูกค้ากลุ่มใหญ่ แยกบิลทั้งแบบรายการและจำนวนเงิน รับชำระเงินทั้งเงินสดและ QR Code พร้อมระบบ OCR ตรวจสอบสลิป รวมถึงการเปิด-ปิด Cashier Session ที่ตรวจสอบลิ้นชักเงินสดของแต่ละกะ

- **ส่วนของลูกค้า (Customer Self-Order)**: สามารถสแกน QR Code ที่โต๊ะเพื่อสั่งอาหารด้วยตนเองผ่าน Mobile Web โดยมีระบบ Bill Claim Token ป้องกันการสั่งซ้ำซ้อนจากหลายอุปกรณ์ ระบบติดตามสถานะอาหารแบบ Real-time การเรียกพนักงานและการขอชำระเงินผ่านการกดปุ่มบนหน้าจอ

- **ระบบแจ้งเตือนแบบ Real-time (Notification)**: สามารถกระจาย Event ผ่าน SignalR Hub จำนวน 2 ตัว ตาม Group ของบทบาทผู้ใช้งาน (Kitchen, Floor, Cashier, Manager) พร้อมแสดงผลผ่าน Toast และเก็บประวัติใน Notification Drawer

ระบบประกอบด้วย 8 Business Module ที่เชื่อมโยงกัน รวมเป็น 37 Entity ในฐานข้อมูล โดยมี API Endpoint จำนวนประมาณ 215 จุด และรองรับการ Deploy ผ่าน Docker

## 5.2 อภิปรายผล

จากการนำระบบไปทดลองใช้งานเบื้องต้น พบว่าระบบมีฟังก์ชันที่ครอบคลุมและสามารถแก้ไขปัญหาของกระบวนการทำงานแบบเดิมได้อย่างเป็นรูปธรรม ดังนี้

- **ลดเวลารอของลูกค้าและความผิดพลาดในการสั่งอาหาร**: ระบบ Self-Order ผ่าน QR Code ช่วยให้ลูกค้าสั่งอาหารได้ด้วยตนเองโดยไม่ต้องเรียกพนักงาน ทำให้ลดภาระงานของพนักงานเสริฟ และลดความผิดพลาดจากการฟังออเดอร์ผิดเนื่องจากลูกค้าเลือกเองทุกขั้นตอน

- **เพิ่มประสิทธิภาพการสื่อสารระหว่างหน้าร้านและครัว**: ระบบ Kitchen Display ที่ทำงานผ่าน SignalR สามารถส่งข้อมูลออเดอร์ไปยังครัวได้ทันทีโดยอาศัยช่องทาง WebSocket ที่เปิดค้างไว้ระหว่าง Client และ Server โดยไม่ต้องอาศัยการสอบถามซ้ำจากฝั่ง Client เมื่อเปรียบเทียบกับการใช้ใบออเดอร์กระดาษที่อาจสูญหายหรืออ่านลายมือไม่ออก ระบบนี้ลดความผิดพลาดในกระบวนการสื่อสารระหว่างหน้าร้านและครัวลงอย่างมีนัยสำคัญ

- **ลดเวลาและความผิดพลาดในการตรวจสอบสลิปโอน**: ระบบ OCR Slip Verification สามารถอ่านยอดเงินจากสลิปและเปรียบเทียบกับยอดที่ต้องชำระโดยอัตโนมัติ พร้อมรองรับ Manual Verification ในกรณีที่ OCR ไม่สามารถอ่านสลิปได้ชัดเจน ลดภาระงานของแคชเชียร์ในการตรวจสลิปด้วยตาเปล่า

- **ความยืดหยุ่นในการบริหารร้าน**: ระบบ Permission Matrix แบบไดนามิกทำให้ผู้ดูแลระบบสามารถปรับเปลี่ยนสิทธิ์ตามตำแหน่งงานได้เองโดยไม่ต้องแก้ไขโค้ด รองรับการสร้างตำแหน่งใหม่ที่หลากหลายตามโครงสร้างของแต่ละร้าน

- **ระบบจัดการครบในที่เดียว**: ระบบรวมการจัดการเมนู พนักงาน โต๊ะ ออเดอร์ การชำระเงิน และการแจ้งเตือนไว้ในแอปพลิเคชันเดียว ทำให้เจ้าของร้านไม่ต้องใช้หลายระบบแยกกัน

> **หมายเหตุ**: การอภิปรายผลในรายงานนี้อ้างอิงจากการทดสอบเชิงฟังก์ชัน (Functional Testing) ในสภาพแวดล้อมของทีมพัฒนาเท่านั้น มิใช่การทดสอบโหลด (Load Test) ในร้านจริง ประสิทธิภาพในสภาพแวดล้อมการใช้งานจริงอาจแตกต่างตามขนาดของร้าน คุณภาพของเครือข่าย และจำนวนผู้ใช้งานพร้อมกัน

## 5.3 ปัญหาและอุปสรรค

ในระหว่างการพัฒนาและทดสอบระบบ คณะผู้จัดทำพบปัญหาและอุปสรรคดังนี้

- **การจัดการ Real-time Connection ของ SignalR ในสภาวะเครือข่ายไม่เสถียร**: ในช่วงเริ่มต้นของการพัฒนา เมื่อ Client หลุดการเชื่อมต่อชั่วคราว ระบบไม่สามารถ Reconnect และ Sync ข้อมูลล่าสุดได้อัตโนมัติ ทำให้หน้าจอ Kitchen Display ค้างและไม่อัปเดต Order ใหม่ ได้แก้ไขปัญหาโดยการเพิ่มกลไก Automatic Reconnection ของ SignalR Client ร่วมกับการดึงข้อมูลล่าสุดเมื่อเชื่อมต่อใหม่สำเร็จ

- **ปัญหาความเข้ากันได้ของ SignalR บนระบบปฏิบัติการ iOS**: ในช่วงพัฒนาพบว่ามือถือบนระบบปฏิบัติการ iOS ไม่สามารถใช้งาน SignalR ผ่าน WebSocket ได้อย่างถูกต้อง ทำให้สถานะต่าง ๆ ไม่อัปเดตแบบ Real-time ในขณะที่มือถือ Samsung บนระบบปฏิบัติการ Android สามารถใช้งานได้ตามปกติ ได้แก้ไขปัญหาดังกล่าวเรียบร้อยแล้ว ส่งผลให้ระบบสามารถใช้งานได้ครอบคลุมทั้งสองระบบปฏิบัติการ

- **ความแม่นยำของระบบ OCR ในการตรวจสอบสลิปโอน**: ระบบ OCR ในระยะแรกพบปัญหากับสลิปจากบางธนาคารที่มีการจัดวางตำแหน่งข้อความและรูปแบบตัวอักษรไม่เป็นมาตรฐาน ทำให้อ่านยอดเงินผิดพลาด ได้แก้ไขปัญหาดังกล่าวด้วยการเพิ่มสถานะ Manual Verification ให้แคชเชียร์สามารถตรวจสลิปด้วยตาเปล่าและยืนยันได้เองในกรณีที่ OCR ไม่สามารถอ่านได้ชัดเจน

- **การจัดการ Race Condition ใน Multi-Device ของ Customer Self-Order**: ในกรณีที่ลูกค้าหลายคนสแกน QR Code เดียวกันจากมือถือหลายเครื่อง อาจทำให้เกิดปัญหาในการสั่งและปิดบิลพร้อมกัน ได้แก้ไขปัญหาดังกล่าวด้วยการออกแบบ Bill Claim Token แบบ Exclusive Lock ที่อนุญาตให้เครื่องที่ Claim Token ก่อนเป็นเครื่องเดียวที่สามารถทำธุรกรรมที่กระทบสถานะของบิลได้

## 5.4 ข้อเสนอแนะสำหรับการพัฒนาต่อยอด

เพื่อให้ระบบมีความสมบูรณ์และครอบคลุมการใช้งานในขอบเขตที่กว้างขึ้นในอนาคต มีข้อเสนอแนะดังนี้

- **ระบบหลายสาขา (Multi-Branch)**: ควรขยายระบบให้รองรับการบริหารหลายสาขาภายใต้องค์กรเดียวกัน พร้อม Dashboard ที่เปรียบเทียบยอดขายและประสิทธิภาพการทำงานระหว่างสาขาต่าง ๆ เพื่อรองรับการขยายธุรกิจของลูกค้า

- **ระบบสมาชิกและการสะสมแต้ม (Customer Loyalty Program)**: ควรเพิ่มฟังก์ชันการสมัครสมาชิกของลูกค้า การสะสมแต้ม คูปองส่วนลด และโปรโมชั่นพิเศษ เพื่อกระตุ้นให้ลูกค้ากลับมาใช้บริการซ้ำและช่วยให้ร้านสามารถวิเคราะห์พฤติกรรมการบริโภคของลูกค้าได้

- **การเชื่อมต่อกับ Hardware**: ควรเพิ่มการเชื่อมต่อกับ Hardware ที่ใช้ในร้านอาหาร เช่น เครื่องพิมพ์ใบเสร็จแบบ Thermal Printer ตาชั่งดิจิทัล และลิ้นชักเงินสดไฟฟ้า ผ่านการสื่อสารแบบ USB หรือ Bluetooth เพื่อให้ระบบสามารถนำไปใช้ในร้านอาหารได้อย่างสมบูรณ์

- **การพัฒนาเป็น Product เชิงพาณิชย์**: ในระยะยาว 3-5 ปีข้างหน้า ระบบมีโอกาสพัฒนาจากโครงการรหัสเปิด (Open Source) ไปเป็น Product เชิงพาณิชย์ที่นำเสนอบริการให้แก่ร้านอาหารจริง โดยอาจมี Community ที่ร่วมพัฒนาควบคู่กันไปเพื่อให้ระบบเติบโตอย่างยั่งยืน

อย่างไรก็ตาม ในการนำระบบไปใช้งานจริงในร้านอาหาร ยังมีข้อจำกัดที่ต้องคำนึงถึง ได้แก่ ค่าใช้จ่ายเริ่มต้นในการลงทุน Hardware (PC หรือ Tablet สำหรับแคชเชียร์ ครัว และพนักงานเสริฟ) ความซับซ้อนในการเรียนรู้การทำงานของระบบสำหรับพนักงานที่ไม่คุ้นเคยกับเทคโนโลยี และการที่ระบบต้องการเครือข่าย Wi-Fi ที่เสถียรเพื่อรองรับการสื่อสารแบบ Real-time ซึ่งอาจเป็นอุปสรรคในพื้นที่ที่อินเทอร์เน็ตไม่ดี
