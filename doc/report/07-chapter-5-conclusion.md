# บทที่ 5 บทสรุปผล

> เนื้อหาพร้อมใช้ — โครงสร้างตามแม่แบบ Primary (5.1 สรุปผล / 5.2 ปัญหา / 5.3 วิธีแก้ / 5.4 ข้อเสนอแนะ) ใช้การบรรยายเชิงคุณภาพแทนตัวเลขเชิงปริมาณ เนื่องจากไม่ได้ทำ Load Test จริง

---

ในบทนี้จะกล่าวถึงการสรุปผลการดำเนินงานของระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS โดยแบ่งเนื้อหาออกเป็นสี่ส่วนหลัก ได้แก่ สรุปผลการดำเนินงานของระบบในมุมของผู้ใช้งานแต่ละบทบาท ปัญหาและอุปสรรคที่พบในระหว่างการพัฒนา แนวทางการแก้ไขปัญหาที่คณะผู้จัดทำได้ดำเนินการ และข้อเสนอแนะสำหรับการพัฒนาต่อยอดในอนาคต

---

## 5.1 สรุปผลการดำเนินงาน

ผลการดำเนินงานของระบบในแต่ละบทบาทของผู้ใช้งานสามารถสรุปได้ดังนี้

- **ส่วนของผู้ดูแลระบบ (Admin)**: สามารถจัดการข้อมูลพื้นฐานของระบบได้ครบถ้วน ตั้งแต่ข้อมูลร้านและการตั้งค่าค่าบริการตามช่วงวันที่ ข้อมูลพนักงานพร้อมการสร้างบัญชีผู้ใช้งานอัตโนมัติผ่านอีเมล ตำแหน่งงานพร้อมสิทธิ์การเข้าถึงผ่านระบบเมทริกซ์สิทธิ์ (Permission Matrix) แบบไดนามิก เมนูอาหาร หมวดหมู่และตัวเลือกเสริมในโครงสร้างลำดับชั้นสามระดับ ตลอดจนโต๊ะและผังร้านในรูปแบบลากและวาง (Drag-and-Drop)

- **ส่วนของพนักงาน (Staff)**: สามารถดูภาพรวมของร้านและสถานะของโต๊ะแบบเวลาจริงจากผังร้านที่ใช้งานจริง รับออเดอร์ที่โต๊ะของลูกค้า จัดการสถานะรายการอาหารผ่านกลไกการเปลี่ยนสถานะ (State Machine) ที่มี 7 สถานะ ตลอดจนรองรับการจองโต๊ะล่วงหน้าและการเชื่อมโต๊ะหลายโต๊ะรวมเป็นออเดอร์เดียวสำหรับลูกค้ากลุ่มใหญ่ แยกบิลทั้งแบบรายการอาหารและจำนวนเงิน รับชำระเงินทั้งเงินสดและคิวอาร์โค้ดพร้อมระบบรู้จำตัวอักษรด้วยภาพ (OCR) สำหรับตรวจสอบสลิป รวมถึงการเปิด-ปิดรอบแคชเชียร์ที่ตรวจสอบลิ้นชักเงินสดของแต่ละกะ

- **ส่วนของลูกค้า (Customer Self-Order)**: สามารถสแกนคิวอาร์โค้ดที่โต๊ะเพื่อสั่งอาหารด้วยตนเองผ่านเว็บบนอุปกรณ์เคลื่อนที่ (Mobile Web) โดยมีโทเค็นยึดบิล (Bill Claim Token) ป้องกันการสั่งซ้ำซ้อนจากหลายอุปกรณ์ ระบบติดตามสถานะอาหารแบบเวลาจริง การเรียกพนักงานและการขอชำระเงินผ่านการกดปุ่มบนหน้าจอ

จากผลการดำเนินงานข้างต้นแสดงให้เห็นว่า ระบบสามารถรองรับกระบวนการให้บริการของร้านอาหารได้อย่างครบถ้วน ตั้งแต่ขั้นตอนการเตรียมความพร้อมของระบบ การให้บริการลูกค้า ตลอดจนการรับชำระเงินและการสรุปยอดในแต่ละรอบการขาย โดยทุกฟังก์ชันได้รับการออกแบบให้เชื่อมโยงกันในระดับข้อมูลและการสื่อสารระหว่างผู้ใช้งานในแต่ละบทบาท ทำให้พนักงานในร้านได้รับข้อมูลที่ตรงกันโดยไม่ต้องอาศัยการสื่อสารด้วยกระดาษหรือคำพูดในการประสานงาน ซึ่งช่วยลดข้อผิดพลาดในการให้บริการและเพิ่มความรวดเร็วในการทำงานของร้านโดยรวม

## 5.2 ปัญหาและอุปสรรค

ในระหว่างการพัฒนาและทดสอบระบบ คณะผู้จัดทำพบปัญหาและอุปสรรคดังนี้

1. **การจัดการการเชื่อมต่อแบบเวลาจริงผ่าน SignalR ในสภาวะเครือข่ายไม่เสถียร** — ในช่วงเริ่มต้นของการพัฒนา เมื่อ Client หลุดการเชื่อมต่อชั่วคราว ระบบไม่สามารถเชื่อมต่อใหม่ (Reconnect) และซิงค์ข้อมูลล่าสุดได้อัตโนมัติ ทำให้หน้าจอแสดงรายการอาหารในครัว (Kitchen Display) ค้างและไม่อัพเดตออเดอร์ใหม่ ส่งผลให้พนักงานครัวพลาดการรับออเดอร์ในช่วงที่เครือข่ายไม่เสถียร

2. **ปัญหาความเข้ากันได้ของ SignalR บนระบบปฏิบัติการ iOS** — ในช่วงการพัฒนาพบว่ามือถือบนระบบปฏิบัติการ iOS ไม่สามารถใช้งาน SignalR ผ่าน WebSocket ได้อย่างถูกต้อง ทำให้สถานะต่าง ๆ ไม่อัพเดตแบบเวลาจริงบนเครื่อง iPhone ในขณะที่มือถือบนระบบปฏิบัติการ Android สามารถใช้งานได้ตามปกติ ส่งผลให้ประสบการณ์การใช้งานของลูกค้าที่ใช้เครื่อง iPhone ไม่เทียบเท่ากับเครื่อง Android

3. **ความแม่นยำของระบบรู้จำตัวอักษรด้วยภาพ (OCR) ในการตรวจสอบสลิปการโอนเงิน** — ในระยะแรกระบบ OCR พบปัญหากับสลิปจากบางธนาคารที่มีการจัดวางตำแหน่งข้อความและรูปแบบตัวอักษรไม่เป็นมาตรฐาน ทำให้อ่านยอดเงินผิดพลาด ส่งผลให้สถานะการตรวจสอบสลิปไม่ตรงกับยอดที่ต้องชำระจริง

4. **การจัดการเหตุการณ์แย่งทรัพยากร (Race Condition) ของการสั่งอาหารด้วยตนเองจากหลายอุปกรณ์** — ในกรณีที่ลูกค้าหลายคนสแกนคิวอาร์โค้ดเดียวกันจากมือถือหลายเครื่อง อาจทำให้เกิดปัญหาในการสั่งและปิดบิลพร้อมกัน ทำให้ออเดอร์ซ้ำซ้อนและสถานะของบิลสับสน

## 5.3 วิธีแก้ปัญหา

จากปัญหาและอุปสรรคที่กล่าวมาในหัวข้อ 5.2 คณะผู้จัดทำได้ดำเนินการแก้ไขดังนี้

1. ออกแบบกลไกการเชื่อมต่อใหม่อัตโนมัติ (Automatic Reconnection) ของ SignalR Client ร่วมกับการดึงข้อมูลล่าสุด (Initial Fetch) เมื่อเชื่อมต่อใหม่สำเร็จ เพื่อให้หน้าจอแสดงรายการอาหารในครัวสามารถซิงค์ข้อมูลที่อาจตกหล่นในช่วงหลุดการเชื่อมต่อได้อย่างครบถ้วน ส่งผลให้ระบบยังคงทำงานได้ต่อเนื่องแม้ในสภาวะเครือข่ายไม่เสถียร

2. เพิ่มกลไกการเชื่อมต่อใหม่ (Reconnect Logic) ใน SignalR Client พร้อม Polyfill สำหรับ iOS Safari เพื่อให้รองรับ WebSocket API ได้อย่างครบถ้วน โดยปรับกลยุทธ์ของช่องทางการสื่อสาร (Transport Strategy) ให้สอดคล้องกับข้อจำกัดของระบบปฏิบัติการ iOS ส่งผลให้ระบบสามารถใช้งานได้ครอบคลุมทั้งระบบปฏิบัติการ iOS และ Android อย่างเท่าเทียมกัน

3. เพิ่มสถานะการตรวจสอบแบบกำหนดเอง (Manual Verification) เป็นเส้นทางสำรองสำหรับกรณีที่ระบบ OCR ไม่สามารถอ่านยอดเงินจากสลิปได้อย่างมั่นใจ โดยให้แคชเชียร์ตรวจสอบและยืนยันยอดเองในฟอร์มที่ระบบแสดง พร้อมเก็บบันทึกการตรวจสอบย้อนหลัง (Audit Log) เพื่อให้สามารถตรวจสอบความถูกต้องในภายหลังได้

4. ออกแบบโทเค็นยึดบิล (Bill Claim Token) แบบล็อกแบบครอบครองสิทธิ์เดียว (Exclusive Lock) ที่อนุญาตให้เฉพาะอุปกรณ์ที่ Claim Token ก่อนเป็นเครื่องเดียวที่สามารถทำธุรกรรมที่กระทบต่อสถานะของบิลได้ ส่งผลให้การสั่งและการปิดบิลจากหลายอุปกรณ์พร้อมกันไม่เกิดความขัดแย้งของข้อมูล

---

## 5.4 ข้อเสนอแนะสำหรับการพัฒนาต่อยอด

เพื่อให้ระบบครอบคลุมการใช้งานในขอบเขตที่กว้างขึ้นในอนาคต คณะผู้จัดทำมีข้อเสนอแนะดังนี้

1. ควรขยายระบบให้รองรับการบริหารหลายสาขา (Multi-Branch) ในระบบเดียวกัน พร้อมแดชบอร์ดที่เปรียบเทียบยอดขายและประสิทธิภาพการทำงานระหว่างสาขาต่าง ๆ เพื่อรองรับการขยายธุรกิจของผู้ประกอบการที่มีหลายสาขาภายใต้องค์กรเดียวกัน

2. ควรเพิ่มระบบสมาชิกและการสะสมแต้ม (Customer Loyalty Program) ที่รองรับการสมัครสมาชิก การสะสมแต้มจากยอดซื้อ คูปองส่วนลด และโปรโมชั่นพิเศษ เพื่อกระตุ้นให้ลูกค้ากลับมาใช้บริการซ้ำและช่วยให้ร้านสามารถวิเคราะห์พฤติกรรมการบริโภคของลูกค้าได้

3. ควรเพิ่มการเชื่อมต่อกับอุปกรณ์ฮาร์ดแวร์ที่ใช้ในร้านอาหาร เช่น เครื่องพิมพ์ใบเสร็จแบบ Thermal Printer ตาชั่งดิจิทัล และลิ้นชักเงินสดไฟฟ้า ผ่านการสื่อสารแบบ USB หรือ Bluetooth เพื่อลดความผิดพลาดจากการป้อนข้อมูลด้วยมือและให้ระบบสามารถนำไปใช้ในร้านอาหารได้อย่างสมบูรณ์

4. ควรพัฒนาระบบจากโครงการรหัสเปิด (Open Source) ไปสู่ผลิตภัณฑ์เชิงพาณิชย์ (Product) ที่ให้บริการแก่ร้านอาหารจริงในระยะ 3-5 ปีข้างหน้า โดยมีชุมชนนักพัฒนา (Community) ที่ร่วมพัฒนาควบคู่กันไป เพื่อให้ระบบเติบโตได้อย่างยั่งยืนและตอบสนองความต้องการของผู้ใช้งานที่หลากหลาย

อย่างไรก็ตาม ในการนำระบบไปใช้งานจริงในร้านอาหาร ยังมีข้อจำกัดที่ต้องคำนึงถึง ได้แก่ ค่าใช้จ่ายเริ่มต้นในการลงทุนอุปกรณ์ฮาร์ดแวร์ (เครื่องคอมพิวเตอร์หรือแท็บเล็ตสำหรับแคชเชียร์ ครัว และพนักงานเสริฟ) ความซับซ้อนในการเรียนรู้การทำงานของระบบสำหรับพนักงานที่ไม่คุ้นเคยกับเทคโนโลยี และความจำเป็นที่ระบบต้องอาศัยเครือข่าย Wi-Fi ที่เสถียรเพื่อรองรับการสื่อสารแบบเวลาจริง ซึ่งอาจเป็นอุปสรรคในพื้นที่ที่อินเทอร์เน็ตไม่ดี
