ในบทนี้จะกล่าวถึงทฤษฎี แนวคิด และเทคโนโลยีที่เกี่ยวข้องกับการพัฒนาระบบบริหารธุรกิจร้านอาหารผ่านเว็บพร้อมระบบ POS ประกอบด้วยทฤษฎีและแนวคิดที่ใช้ในการออกแบบ ตลอดจนเครื่องมือและเทคโนโลยีที่ใช้ในการพัฒนา ซึ่งมีรายละเอียดดังนี้

## 2.1 อุตสาหกรรมร้านอาหารและปัญหาของระบบบริหารแบบดั้งเดิม

ธุรกิจร้านอาหารเป็นหนึ่งในอุตสาหกรรมที่มีการแข่งขันสูงและมีความหลากหลายของรูปแบบการให้บริการ [1] ประเภทของร้านอาหารที่ปรากฏในตลาดสามารถจำแนกได้หลายรูปแบบ เช่น ร้านอาหารตามสั่ง (À la carte) ที่เน้นการสั่งอาหารจากเมนูแบบรายจาน ร้านอาหารญี่ปุ่นและเกาหลีแบบบุฟเฟ่ต์ (Buffet) ที่ลูกค้าสามารถสั่งอาหารได้ไม่จำกัดในเวลาที่กำหนด ร้านชาบูและสุกี้ที่มีรูปแบบการสั่งซ้ำเป็นรอบ ตลอดจนร้านกาแฟและคาเฟ่ที่ลูกค้าใช้เวลาในร้านนาน รูปแบบที่แตกต่างกันส่งผลให้แต่ละร้านมีกระบวนการรับออเดอร์ การจัดการครัว และการชำระเงินที่แตกต่างกันออกไป

จากการศึกษาสภาพการดำเนินงานของร้านอาหารในปัจจุบัน พบว่าระบบบริหารแบบดั้งเดิมยังคงมีปัญหาสำคัญหลายประการ ซึ่งส่งผลต่อประสบการณ์การให้บริการและประสิทธิภาพในการบริหารจัดการ โดยสามารถสรุปปัญหาหลักได้ดังต่อไปนี้

1. **ความล่าช้าในการรับออเดอร์**: ลูกค้าต้องเรียกพนักงานเพื่อขอเมนูและจดรายการ ทำให้เกิดเวลารอที่ยาวนานในช่วงที่ร้านมีผู้ใช้บริการจำนวนมาก
2. **ความผิดพลาดของการสื่อสารระหว่างหน้าร้านและครัว**: การจดออเดอร์ผ่านกระดาษทำให้เกิดปัญหาครัวอ่านลายมือไม่ออก ใบออเดอร์หาย หรือตกหล่นรายการในกระบวนการส่งต่อ
3. **ความช้าและความผิดพลาดในการตรวจสอบสลิปโอนเงิน**: การตรวจสลิปด้วยตาเปล่าทำให้แคชเชียร์ใช้เวลามากและมีความเสี่ยงในการอ่านยอดเงินผิด
4. **ความซับซ้อนในการแยกบิลของลูกค้ากลุ่ม**: เมื่อลูกค้าต้องการแยกชำระตามรายการหรือตามจำนวนเงิน การคำนวณด้วยมือสร้างความสับสนและใช้เวลานาน
5. **ข้อจำกัดของระบบ POS ในตลาด**: ระบบ POS ที่มีอยู่ส่วนใหญ่ให้บริการในรูปแบบ Software-as-a-Service (SaaS) ที่มีค่าใช้จ่ายรายเดือนต่อเนื่อง และไม่ยืดหยุ่นต่อการปรับแต่งให้เหมาะกับโครงสร้างของร้านอาหารแต่ละประเภท

อย่างไรก็ตาม การนำเทคโนโลยีสารสนเทศมาใช้ในร้านอาหารยังคงมีอุปสรรคและความเสี่ยงในการดำเนินงานจริง [2] เช่น ค่าใช้จ่ายเริ่มต้นด้านอุปกรณ์ฮาร์ดแวร์และการติดตั้งระบบ ความซับซ้อนในการเรียนรู้การใช้งานของพนักงาน และเสถียรภาพของเครือข่ายอินเทอร์เน็ตในบางพื้นที่ ซึ่งล้วนเป็นปัจจัยที่ต้องคำนึงถึงในการออกแบบระบบให้รองรับการใช้งานในสภาพแวดล้อมที่แตกต่างกัน

## 2.2 ระบบจุดขาย (Point of Sale: POS) — แนวคิดและองค์ประกอบหลัก

ระบบจุดขาย หรือ Point of Sale (POS) [3] คือระบบสารสนเทศที่ใช้บริหารจัดการกระบวนการซื้อขายสินค้าและบริการ ณ จุดที่ลูกค้าทำการชำระเงิน ในบริบทของธุรกิจร้านอาหาร ระบบ POS ทำหน้าที่ครอบคลุมตั้งแต่การรับรายการสั่งอาหาร การส่งรายการไปยังครัว การคำนวณยอดรวมและภาษีมูลค่าเพิ่ม การจัดการสถานะของโต๊ะ ไปจนถึงการรับชำระเงินและการบันทึกข้อมูลการขาย

ระบบ POS ในธุรกิจร้านอาหารโดยทั่วไปประกอบด้วยองค์ประกอบหลัก 6 องค์ประกอบ ดังนี้

1. **ระบบจัดการคำสั่งซื้อ (Order Management)**: เป็นกระบวนการรับและจัดเก็บรายการสั่งอาหารของลูกค้า โดยทั่วไปจะผูกออเดอร์ (Order) เข้ากับโต๊ะ (Table) ที่ใช้บริการ และจัดเก็บรายการอาหารแต่ละชิ้น (OrderItem) พร้อมตัวเลือก (Option) ของรายการ เพื่อใช้ในการประมวลผลและส่งต่อไปยังครัว

2. **ระบบบริหารบิล (Billing)**: เป็นกระบวนการคำนวณยอดเงินตามรายการที่สั่ง โดยทั่วไปจะรองรับการแยกบิล (Split Bill) ในกรณีที่ลูกค้ากลุ่มต้องการชำระเงินแยก พร้อมคำนวณค่าบริการ (Service Charge) และภาษีมูลค่าเพิ่ม (VAT) ตามการตั้งค่าของร้านโดยอัตโนมัติ

3. **ระบบจัดการโต๊ะและผังร้าน (Table Management)**: เป็นการบริหารสถานะของโต๊ะในร้าน เพื่อให้พนักงานสามารถจัดการที่นั่งของลูกค้าได้อย่างมีประสิทธิภาพ โดยทั่วไประบบจะรองรับการแบ่งโต๊ะตามโซน (Zone) และการกำหนดสถานะของโต๊ะ เช่น พร้อมใช้งาน กำลังใช้งาน รอชำระเงิน และอยู่ในระหว่างการทำความสะอาด

4. **ระบบครัว (Kitchen Display System: KDS)**: เป็นหน้าจอแสดงผลในครัวที่แสดงรายการอาหารที่ลูกค้าสั่งเข้ามา โดยทั่วไประบบจะแยกการแสดงผลตามสถานี (Station) ของครัว เช่น สถานีอาหาร สถานีเครื่องดื่ม และสถานีของหวาน เพื่อให้พนักงานครัวแต่ละสถานีโฟกัสกับรายการที่ตนรับผิดชอบโดยตรง

5. **ระบบรับชำระเงิน (Payment)**: เป็นกระบวนการรับเงินจากลูกค้า โดยทั่วไปรองรับการชำระเงินสด การชำระผ่านคิวอาร์โค้ด (QR Code) และในบางระบบรองรับการตรวจสอบสลิปโอนเงินด้วยระบบรู้จำตัวอักษรด้วยภาพ (OCR) นอกจากนี้ ระบบรับชำระเงินมักรวมกลไกการจัดการกะของแคชเชียร์ (Cashier Session) ที่ใช้บริหารลิ้นชักเงินสดและการตรวจสอบยอดเมื่อสิ้นกะ

6. **ระบบแจ้งเตือนแบบเวลาจริง (Real-time Notification)**: เป็นกลไกการสื่อสารข้อมูลระหว่างหน้าร้าน ครัว และลูกค้า เพื่อให้ทุกฝ่ายได้รับข้อมูลสถานะของออเดอร์อย่างทันท่วงที โดยอาศัยเทคโนโลยีการสื่อสารแบบเวลาจริง (Real-time Communication) ซึ่งจะอธิบายในรายละเอียดเพิ่มเติมในหัวข้อ 2.4

## 2.3 กลไกการเปลี่ยนสถานะ (State Machine)

กลไกการเปลี่ยนสถานะ หรือ State Machine [4] เป็นแนวคิดทางวิศวกรรมซอฟต์แวร์ที่ใช้ในการอธิบายและควบคุมพฤติกรรมของระบบที่มีสถานะที่ชัดเจนและจำกัด โดยกำหนดว่าระบบจะอยู่ในสถานะใดสถานะหนึ่งในช่วงเวลาหนึ่ง และสามารถเปลี่ยนจากสถานะหนึ่งไปยังอีกสถานะหนึ่งได้ก็ต่อเมื่อเกิดเหตุการณ์ (Event) ที่เป็นไปตามเงื่อนไขที่กำหนดไว้เท่านั้น

แนวคิดนี้เหมาะกับการออกแบบกระบวนการในระบบจุดขาย เนื่องจากออเดอร์และรายการอาหารแต่ละชิ้นต้องผ่านขั้นตอนการประมวลผลที่ลำดับชัดเจน ตั้งแต่การรับคำสั่งซื้อ การส่งไปยังครัว การปรุงอาหาร การเสริฟ ไปจนถึงการชำระเงินหรือการยกเลิกรายการ การประยุกต์ State Machine กับกระบวนการเหล่านี้ช่วยป้องกันการเปลี่ยนสถานะที่ไม่ถูกต้อง เช่น การยกเลิกรายการที่ปรุงเสร็จแล้ว หรือการเปิดออเดอร์ซ้ำหลังจากชำระเงินเรียบร้อย

## 2.4 การสื่อสารแบบเวลาจริง (Real-time Communication)

การสื่อสารแบบเวลาจริง หรือ Real-time Communication [5] เป็นรูปแบบการแลกเปลี่ยนข้อมูลระหว่างเครื่องลูกข่าย (Client) และเซิร์ฟเวอร์ (Server) ที่ข้อมูลถูกส่งและแสดงผลภายในเวลาที่สั้นมากจนแทบรู้สึกได้ทันที โดยทั่วไปสามารถดำเนินการได้สองรูปแบบหลัก ได้แก่ การที่ Client สอบถามเซิร์ฟเวอร์ซ้ำเป็นช่วง ๆ (Polling) ซึ่งสร้างภาระให้กับเซิร์ฟเวอร์โดยไม่จำเป็น และการใช้โปรโตคอลที่รองรับการเปิดช่องทางการสื่อสารแบบสองทาง (Bidirectional) เช่น WebSocket ที่อนุญาตให้เซิร์ฟเวอร์ส่งข้อมูลไปยัง Client ได้โดยอัตโนมัติ

นอกจาก WebSocket แล้ว ยังมีโปรโตคอลและเทคนิคที่ใช้สำหรับการสื่อสารแบบเวลาจริงในเว็บแอปพลิเคชัน เช่น Server-Sent Events (SSE) ที่อนุญาตให้เซิร์ฟเวอร์ส่งข้อมูลไปยัง Client ทางเดียว และ Long Polling ที่ Client เปิดการเชื่อมต่อค้างไว้จนกว่าเซิร์ฟเวอร์จะมีข้อมูลใหม่ส่งกลับ ในทางปฏิบัติ ไลบรารีที่ใช้จัดการการสื่อสารแบบเวลาจริงมักรองรับการเลือกโปรโตคอลที่เหมาะสมที่สุดให้อัตโนมัติ โดยใช้ WebSocket เป็นทางเลือกแรกและใช้ทางเลือกอื่นเป็นกลไกสำรอง (Fallback) ในกรณีที่สภาพแวดล้อมเครือข่ายไม่รองรับ

## 2.5 การควบคุมการเข้าถึงตามบทบาท (RBAC)

การควบคุมการเข้าถึงตามบทบาท หรือ Role-Based Access Control (RBAC) [6] เป็นแนวคิดการจัดการสิทธิ์การเข้าถึงทรัพยากรในระบบสารสนเทศ ที่ใช้บทบาท (Role) เป็นตัวกลางในการกำหนดสิทธิ์แทนการกำหนดสิทธิ์ให้กับผู้ใช้งานรายบุคคลโดยตรง แนวคิดนี้ทำให้การบริหารสิทธิ์ในองค์กรขนาดกลางและขนาดใหญ่มีความเป็นระบบ ลดความซ้ำซ้อนของการกำหนดสิทธิ์ และง่ายต่อการปรับเปลี่ยนเมื่อโครงสร้างองค์กรเปลี่ยนแปลง

การออกแบบ Permission Matrix ในระบบ RBAC โดยทั่วไปประกอบด้วยสามระดับ คือ ระดับโมดูล (Module) ที่กำหนดขอบเขตของฟังก์ชันการทำงาน ระดับการกระทำ (Action) ที่กำหนดประเภทของการดำเนินการ เช่น การอ่าน (Read) การสร้าง (Create) การแก้ไข (Update) และการลบ (Delete) และระดับบทบาทหรือตำแหน่งงาน (Role/Position) ที่เชื่อมโยงผู้ใช้งานกับเมทริกซ์ของ Module × Action การตรวจสอบสิทธิ์มักดำเนินการในสองชั้น ได้แก่ ชั้นหน้าบ้าน (Frontend) ที่ซ่อนปุ่มหรือเมนูที่ผู้ใช้ไม่มีสิทธิ์ และชั้นหลังบ้าน (Backend) ที่ปฏิเสธคำขอ API ที่ไม่ได้รับอนุญาต เพื่อให้การควบคุมสิทธิ์มีความน่าเชื่อถือทั้งในด้านประสบการณ์ผู้ใช้และด้านความปลอดภัย

## 2.6 การรู้จำตัวอักษรด้วยภาพ (OCR)

การรู้จำตัวอักษรด้วยภาพ หรือ Optical Character Recognition (OCR) [7] เป็นเทคโนโลยีที่แปลงตัวอักษรในไฟล์ภาพหรือเอกสารที่ถูกสแกนให้กลายเป็นข้อมูลตัวอักษรที่คอมพิวเตอร์สามารถอ่านและประมวลผลได้ เทคโนโลยีนี้นิยมใช้ในกระบวนการบันทึกข้อมูลจากเอกสาร การตรวจสอบใบเสร็จ และการประมวลผลสลิปการโอนเงิน

เมื่อนำมาประยุกต์กับการตรวจสอบสลิปโอนเงินในระบบจุดขาย เทคโนโลยี OCR จะวิเคราะห์ภาพสลิปและดึงข้อมูลสำคัญออกมา เช่น ยอดเงินที่โอน วันที่และเวลาในการโอน และเลขบัญชีปลายทาง เพื่อเปรียบเทียบกับข้อมูลที่ระบบจัดเก็บไว้ อย่างไรก็ตาม ความแม่นยำของ OCR อาจลดลงในกรณีที่ภาพสลิปไม่ชัดเจนหรือฟอนต์ของธนาคารไม่เป็นมาตรฐาน ระบบที่ออกแบบมารองรับสถานการณ์ดังกล่าวจึงมักมีกลไกการยืนยันด้วยตนเอง (Manual Verification) ของผู้ปฏิบัติงานเป็นทางเลือกสำรอง เพื่อให้กระบวนการรับชำระเงินดำเนินต่อไปได้แม้ในสภาวะที่ OCR ไม่สามารถอ่านข้อมูลได้ครบถ้วน

## 2.8 ภาษา C#

ภาษา C# [9] คือภาษาโปรแกรมระดับสูงเชิงวัตถุ (Object-Oriented Programming Language) ที่พัฒนาโดยบริษัทไมโครซอฟท์ ทำงานบนแพลตฟอร์ม .NET Runtime ที่สามารถประมวลผลข้ามระบบปฏิบัติการได้ ออกแบบมาเพื่อรองรับการพัฒนาแอปพลิเคชันที่มีความซับซ้อนและขนาดใหญ่ มีคุณสมบัติและหลักการทำงานที่สำคัญ ดังต่อไปนี้

1. **ระบบชนิดข้อมูลที่เข้มงวด (Strong Typing)**: ภาษา C# กำหนดให้นักพัฒนาระบุชนิดของตัวแปรอย่างชัดเจน ระบบจะตรวจสอบความถูกต้องของชนิดข้อมูลในขั้นตอน Compile-time ทำให้สามารถค้นพบข้อผิดพลาดได้ตั้งแต่เนิ่น ๆ ก่อนที่โปรแกรมจะถูกนำไปประมวลผลจริง

2. **การประมวลผลแบบไม่ประสานเวลา (Async / Await)**: ภาษา C# รองรับการเขียนโปรแกรมแบบ Asynchronous ผ่าน Keyword `async` และ `await` ทำให้สามารถจัดการกับงาน I/O ได้อย่างมีประสิทธิภาพโดยไม่ต้อง Block Thread หลัก เหมาะสำหรับการพัฒนาระบบที่ต้องรองรับคำขอจำนวนมากพร้อมกัน

3. **ระบบ LINQ (Language Integrated Query)**: ภาษา C# มีระบบ LINQ ที่ช่วยให้นักพัฒนาสามารถเขียนคำสั่งสอบถาม (Query) บนข้อมูลในรูปแบบที่ใกล้เคียงกับภาษา SQL ได้ภายในตัวภาษาเอง ทำให้การจัดการข้อมูลในหน่วยความจำและฐานข้อมูลมีความสะดวกและอ่านง่าย

4. **การเขียนโปรแกรมเชิงวัตถุครบรูปแบบ**: ภาษา C# รองรับหลักการเชิงวัตถุครบทั้ง 4 ข้อ ได้แก่ Encapsulation, Inheritance, Polymorphism และ Abstraction รวมถึงคุณสมบัติเพิ่มเติม เช่น Interface, Generic, Delegate และ Event ทำให้เหมาะกับการออกแบบสถาปัตยกรรมระบบที่มีความซับซ้อน

## 2.9 ASP.NET Core 9.0

ASP.NET Core [10] คือเฟรมเวิร์กแบบโอเพนซอร์ส (Open-source) สำหรับการพัฒนาเว็บแอปพลิเคชันและบริการ Web API ที่พัฒนาโดยบริษัทไมโครซอฟท์ ทำงานบน .NET Runtime ที่รองรับการทำงานข้ามระบบปฏิบัติการได้ทั้ง Windows, macOS และ Linux เวอร์ชัน 9.0 เป็นเวอร์ชันที่นำเสนอประสิทธิภาพและคุณสมบัติใหม่ที่เหมาะสมกับการพัฒนา API สมัยใหม่ โดยรองรับการประมวลผลคำขอจำนวนมากพร้อมกัน (High Concurrency)

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ ASP.NET Core 9.0 ประกอบด้วย

1. **ประสิทธิภาพสูง (High Performance)**: ASP.NET Core ถูกออกแบบให้รองรับการประมวลผลแบบ Async/Await โดยตรง ทำให้สามารถรองรับคำขอจำนวนมากพร้อมกันได้อย่างมีประสิทธิภาพ เหมาะสำหรับระบบที่ต้องตอบสนองแบบเวลาจริง

2. **ระบบฉีดความสัมพันธ์ในตัว (Built-in Dependency Injection)**: เฟรมเวิร์กมาพร้อมระบบ Dependency Injection (DI) Container ในตัว ช่วยให้นักพัฒนาสามารถจัดการความสัมพันธ์ระหว่าง Service, Repository และ Controller ได้อย่างเป็นระบบ และส่งเสริมหลักการ SOLID เพื่อให้โค้ดมีความยืดหยุ่นและทดสอบง่าย

3. **ระบบ Middleware Pipeline**: การประมวลผลคำขอใน ASP.NET Core ใช้รูปแบบ Pipeline ที่ประกอบด้วย Middleware หลายชั้น เช่น Authentication, Authorization, Exception Handling และ CORS ทำให้สามารถปรับแต่งการประมวลผลคำขอได้อย่างยืดหยุ่น และสามารถเพิ่ม Middleware กำหนดเองได้เมื่อจำเป็น

4. **รองรับการสร้าง API Documentation อัตโนมัติ**: ASP.NET Core สามารถผสาน OpenAPI (Swagger) เพื่อสร้างเอกสาร API ที่อัปเดตอัตโนมัติตามโค้ดได้ ลดภาระในการเขียนเอกสารด้วยมือและช่วยให้ทีมหน้าบ้านสามารถสร้างรหัสคำสั่งที่เชื่อมต่อ API ได้โดยอัตโนมัติ

## 2.11 SQL Server

SQL Server [12] คือระบบจัดการฐานข้อมูลเชิงสัมพันธ์ (Relational Database Management System หรือ RDBMS) ที่พัฒนาและบำรุงรักษาโดยบริษัทไมโครซอฟท์ ออกแบบมาเพื่อรองรับการจัดเก็บข้อมูลในระดับองค์กร (Enterprise) มีคุณสมบัติสำคัญในด้านความเสถียร ความปลอดภัย และประสิทธิภาพในการประมวลผลข้อมูลปริมาณมาก รองรับการประมวลผลธุรกรรม (Transaction) ที่มีความน่าเชื่อถือสูง

SQL Server รองรับภาษาคำสั่ง T-SQL (Transact-SQL) ซึ่งเป็นภาษาส่วนขยายของ SQL มาตรฐาน รวมถึงมีเครื่องมือเสริม เช่น SQL Server Management Studio (SSMS) สำหรับจัดการฐานข้อมูล และ Azure Data Studio สำหรับการพัฒนาแบบ Cross-platform นอกจากนี้ยังให้บริการในหลายรูปแบบ ตั้งแต่ Express Edition ที่ใช้งานได้ฟรีสำหรับโครงงานขนาดเล็ก ไปจนถึง Enterprise Edition สำหรับองค์กรขนาดใหญ่ ทำให้เป็นทางเลือกที่ยืดหยุ่นในการนำมาใช้กับระบบที่มีความต้องการในระดับต่าง ๆ

## 2.12 SignalR

SignalR [13] คือไลบรารีโอเพนซอร์สสำหรับการสื่อสารแบบเวลาจริงระหว่างเซิร์ฟเวอร์และเครื่องลูกข่าย (Client) ที่พัฒนาโดยบริษัทไมโครซอฟท์ ออกแบบมาเพื่อรองรับการส่งข้อมูลแบบ Server-to-Client โดยอัตโนมัติ โดยไม่ต้องอาศัยการสอบถามซ้ำ ๆ จากฝั่ง Client (Polling) ซึ่งช่วยลดภาระของเซิร์ฟเวอร์และเพิ่มประสิทธิภาพการตอบสนอง

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ SignalR ประกอบด้วย

1. **การเลือก Transport อัตโนมัติ**: SignalR สามารถเลือก Transport ที่เหมาะสมที่สุดได้อัตโนมัติ ทั้ง WebSocket, Server-Sent Events (SSE) และ Long Polling โดย WebSocket เป็น Transport ที่ให้ประสิทธิภาพสูงสุด ส่วน SSE และ Long Polling จะถูกใช้เป็นทางเลือกสำรองเมื่อเครือข่ายไม่รองรับ WebSocket

2. **กลไกการเชื่อมต่ออัตโนมัติ (Automatic Reconnection)**: SignalR มีกลไกในการเชื่อมต่อใหม่อัตโนมัติเมื่อการเชื่อมต่อขาดหาย ช่วยให้ระบบสามารถทำงานต่อเนื่องได้แม้ในสภาวะเครือข่ายไม่เสถียร

3. **ระบบ Group Management**: SignalR รองรับการแบ่งกลุ่มของ Client (Group) ทำให้สามารถส่งข้อมูลไปยังกลุ่มผู้ใช้งานที่กำหนดได้อย่างเฉพาะเจาะจง

4. **รูปแบบการเขียนแบบ Hub**: SignalR ใช้รูปแบบ Hub ที่ทำให้การเรียกเมธอดข้ามฝั่ง (Client-to-Server หรือ Server-to-Client) มีความเป็นธรรมชาติเหมือนการเรียกเมธอดในโค้ดปกติ ช่วยลดความซับซ้อนของการเขียนรหัสคำสั่งสำหรับการสื่อสารแบบเวลาจริง

[ใส่รูปที่ 2.6 สัญลักษณ์ SignalR]
(ที่มา: https://learn.microsoft.com/en-us/aspnet/core/signalr/)

## 2.13 JSON Web Token (JWT) และ BCrypt

JSON Web Token (JWT) [14] คือมาตรฐานเปิด (RFC 7519) สำหรับการสร้าง Token ที่ใช้แลกเปลี่ยนข้อมูลระหว่างระบบในรูปแบบ JSON ที่มีการลงนามด้วย Digital Signature เพื่อยืนยันความถูกต้องของข้อมูล มาตรฐานนี้นิยมใช้ในการยืนยันตัวตน (Authentication) ของระบบเว็บแอปพลิเคชันสมัยใหม่ โดย Token จะถูกส่งกลับให้ Client หลังจากการยืนยันตัวตนสำเร็จ และ Client จะแนบ Token นี้ในทุกคำขอถัดไป

BCrypt [15] คืออัลกอริทึมการแฮชรหัสผ่าน (Password Hashing Algorithm) ที่ออกแบบมาให้มีความต้านทานต่อการโจมตีแบบ Brute Force ผ่านการเพิ่มค่า Cost Factor ที่ปรับได้ ทำให้ใช้เวลาในการคำนวณนานพอที่จะป้องกันการเดารหัสผ่านด้วยคอมพิวเตอร์ความเร็วสูง อัลกอริทึมนี้ยังผสาน Salt แบบสุ่มเข้ากับรหัสผ่านในกระบวนการแฮช ซึ่งป้องกันการโจมตีด้วย Rainbow Table ได้อย่างมีประสิทธิภาพ

## 2.14 ภาษา TypeScript

ภาษา TypeScript [16] คือภาษาโปรแกรมระดับสูงแบบโอเพนซอร์สที่พัฒนาและบำรุงรักษาโดยบริษัทไมโครซอฟท์ ภาษา TypeScript ถูกสร้างขึ้นโดยการเพิ่มระบบการกำหนดชนิดข้อมูลแบบสถิต (Static Typing) เข้าไปในภาษาจาวาสคริปต์ (JavaScript) และมีสถานะเป็น "ซูเปอร์เซตแบบเคร่งครัดทางไวยากรณ์" (Strict Syntactical Superset) ของภาษาจาวาสคริปต์ ซึ่งหมายความว่ารหัสคำสั่งใด ๆ ที่เขียนด้วยภาษาจาวาสคริปต์ได้อย่างถูกต้องจะถือว่าเป็นโปรแกรม TypeScript ที่ถูกต้องด้วยเช่นกัน

คุณสมบัติและหลักการทำงานที่สำคัญของภาษา TypeScript ประกอบด้วย

1. **กระบวนการแปลงรหัสคำสั่ง (Transcompilation)**: เนื่องจากสภาพแวดล้อมการประมวลผลทั่วไปไม่สามารถอ่านภาษา TypeScript ได้โดยตรง รหัสคำสั่งจะต้องผ่านกระบวนการแปลงเป็นภาษาจาวาสคริปต์มาตรฐานก่อน จึงจะสามารถนำไปประมวลผลได้ทั้งในฝั่ง Client (เว็บเบราว์เซอร์) และฝั่ง Server (Node.js)

2. **การระบุชนิดข้อมูลและตรวจสอบขณะคอมไพล์ (Type Annotations and Compile-time Type Checking)**: นักพัฒนาสามารถระบุชนิดของตัวแปร พารามิเตอร์ และค่าส่งกลับของฟังก์ชันได้อย่างชัดเจน ซึ่งระบบจะตรวจสอบในขั้นตอน Compile-time ช่วยให้สามารถค้นพบข้อผิดพลาดได้ก่อนการนำไปใช้งานจริง ลดความเสี่ยงของ Runtime Error ในระบบขนาดใหญ่

3. **การรองรับโครงสร้างขั้นสูง (Advanced Types and OOP Features)**: ภาษา TypeScript ได้เพิ่มคุณสมบัติระดับสูง เช่น Interface, Enum, Generics, Namespace และ Tuple เพื่อช่วยให้การจัดโครงสร้างซอร์สโค้ดมีระเบียบและง่ายต่อการบำรุงรักษา เหมาะสำหรับโครงการขนาดใหญ่ที่มีการพัฒนาในทีมหลายคน

[ใส่รูปที่ 2.8 สัญลักษณ์ภาษา TypeScript]
(ที่มา: https://www.typescriptlang.org/)

## 2.15 เฟรมเวิร์ก Angular 19.1

Angular [17] คือเฟรมเวิร์กสำหรับการพัฒนาเว็บแอปพลิเคชันแบบ Single Page Application (SPA) ที่พัฒนาและบำรุงรักษาโดยบริษัท Google เขียนด้วยภาษา TypeScript และใช้รูปแบบสถาปัตยกรรมแบบ Component-Based ที่แบ่งหน้าเว็บออกเป็นชิ้นส่วนย่อยที่สามารถนำกลับมาใช้ใหม่ได้

คุณสมบัติและรูปแบบการทำงานที่โดดเด่นของ Angular ประกอบด้วย

1. **สถาปัตยกรรมแบบ Component-Based**: Angular แบ่งหน้าเว็บออกเป็น Component ย่อย ๆ ที่สามารถนำกลับมาใช้ใหม่ได้ ทำให้การพัฒนาและบำรุงรักษามีความเป็นระบบ และง่ายต่อการทดสอบแยกเป็นส่วน

2. **Angular Signals (Reactive State)**: Angular เวอร์ชันใหม่ได้เพิ่มระบบ Signals ที่เป็นกลไกการจัดการสถานะแบบ Reactive ทำให้การปรับปรุงหน้าเว็บเมื่อข้อมูลเปลี่ยนแปลงมีประสิทธิภาพสูงขึ้น โดย Component ที่อ้างอิงสัญญาณจะถูก Re-render เฉพาะเมื่อค่าของสัญญาณเปลี่ยนแปลงจริงเท่านั้น

3. **ระบบ Dependency Injection**: Angular มีระบบ DI ในตัวที่ช่วยให้สามารถจัดการความสัมพันธ์ระหว่าง Service และ Component ได้อย่างเป็นระบบ ช่วยให้สามารถแยกตรรกะทางธุรกิจออกจากการแสดงผลได้อย่างชัดเจน

4. **ระบบจัดการเส้นทาง (Routing) แบบ Lazy Load**: Angular รองรับการแบ่ง Feature Module ที่โหลดเมื่อจำเป็น (Lazy Loading) ทำให้แอปพลิเคชันมีความเร็วในการเริ่มต้น และเหมาะสำหรับการพัฒนาเว็บแอปพลิเคชันที่มีหลายส่วนการทำงานในโครงงานเดียว

## 2.17 เฟรมเวิร์ก Tailwind CSS

Tailwind CSS [19] คือเฟรมเวิร์ก CSS แบบโอเพนซอร์สที่ใช้แนวคิด Utility-First ออกแบบมาเพื่อช่วยให้นักพัฒนาและนักออกแบบส่วนติดต่อผู้ใช้งานสามารถสร้างหน้าเว็บได้อย่างรวดเร็วโดยการประกอบ Class ย่อยที่มีหน้าที่เฉพาะ (เช่น `bg-blue-500`, `p-4`, `text-center`) เข้าไปในโครงสร้าง HTML โดยไม่ต้องเขียนไฟล์ CSS แยกต่างหาก

จุดเด่นและหลักการทำงานที่สำคัญของ Tailwind CSS ประกอบด้วย

1. **สถาปัตยกรรมแบบเน้นอรรถประโยชน์ (Utility-First Architecture)**: Tailwind CSS เตรียม Class ย่อยจำนวนมากให้นักพัฒนานำมาประกอบเข้ากับ HTML โดยตรง ทำให้สามารถสร้าง UI ที่มีรูปแบบเฉพาะตัวได้อย่างอิสระ โดยไม่ต้องเขียน CSS ที่ซ้ำซ้อน

2. **ความสม่ำเสมอของการออกแบบ (Design Consistency)**: Tailwind CSS มีการกำหนดค่ามาตรฐานสำหรับระบบสี (Color Palette) ระยะห่าง (Spacing) และขนาดตัวอักษร (Typography) ไว้เป็นระบบ ช่วยควบคุมให้การแสดงผลในทุกหน้าจอเป็นไปในทิศทางเดียวกัน

3. **กระบวนการคอมไพล์แบบ JIT (Just-In-Time)**: Tailwind CSS รองรับการคอมไพล์เฉพาะ Class ที่ใช้งานจริง ทำให้ขนาดไฟล์ CSS สุดท้ายมีขนาดเล็ก เหมาะสำหรับการ Deploy บน Production ที่ต้องการประสิทธิภาพในการโหลดหน้าเว็บ

## 2.18 MinIO

## 2.19 Docker และ Docker Compose

Docker [21] คือแพลตฟอร์มสำหรับการสร้างและจัดการคอนเทนเนอร์ (Container) ที่ช่วยให้นักพัฒนาสามารถแพ็คเกจแอปพลิเคชันและ Dependencies ทั้งหมดไว้ในคอนเทนเนอร์เดียว ทำให้สามารถ Deploy ระบบในสภาพแวดล้อมที่หลากหลายได้โดยไม่ต้องกังวลเรื่องความแตกต่างของระบบปฏิบัติการหรือไลบรารีที่ติดตั้ง คอนเทนเนอร์ของ Docker ทำงานในรูปแบบที่เบากว่า Virtual Machine แบบดั้งเดิม โดยใช้ทรัพยากรร่วมกันกับระบบปฏิบัติการแม่

Docker Compose เป็นเครื่องมือเสริมที่ใช้ในการจัดการคอนเทนเนอร์หลายตัวพร้อมกันผ่านไฟล์ YAML ทำให้สามารถกำหนด Dependencies และความสัมพันธ์ระหว่างคอนเทนเนอร์ได้อย่างเป็นระบบ เหมาะสำหรับระบบที่ประกอบด้วยหลายบริการ เช่น เว็บเซิร์ฟเวอร์ ฐานข้อมูล และระบบจัดเก็บไฟล์ ที่ต้องทำงานร่วมกันภายในสภาพแวดล้อมเดียวกัน

## 2.20 Swagger / OpenAPI

Swagger / OpenAPI [22] คือมาตรฐานเปิดสำหรับการอธิบาย Web API ในรูปแบบ JSON หรือ YAML ที่ช่วยให้นักพัฒนาสามารถสร้างเอกสาร API ที่อ่านได้ทั้งโดยมนุษย์และเครื่องจักร เครื่องมือในชุด Swagger ประกอบด้วย Swagger UI สำหรับแสดงเอกสาร API บนเว็บบราวเซอร์ในรูปแบบ Interactive ที่ทดสอบการเรียก API ได้โดยตรง และ Swagger Codegen สำหรับสร้างโค้ดของ Client โดยอัตโนมัติ

นอกจากนี้ ในระบบนิเวศของ Angular ยังมีเครื่องมือ Code Generator อย่าง ng-openapi-gen [23] ที่อ่านเอกสาร OpenAPI Specification แล้วสร้าง TypeScript Client สำหรับ Angular โดยอัตโนมัติ ช่วยลดเวลาในการเขียนโค้ดเชื่อมต่อ API ฝั่งหน้าบ้าน และช่วยให้ฝั่งหน้าบ้านได้รับ Type ที่ตรงกับ API ที่หลังบ้านกำหนดไว้เสมอ ทำให้ลดความผิดพลาดที่อาจเกิดจากการเขียน Client ด้วยมือได้อย่างมีนัยสำคัญ
